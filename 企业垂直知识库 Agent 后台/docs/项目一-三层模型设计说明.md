# 项目一 · 三层模型设计说明（向量化 / 对话生成 / 评测判分）

> 对应代码：`app/rag/embeddings.py`、`app/rag/retriever.py`、`app/rag/vector_store.py`、`app/llm/factory.py`、`app/llm/mock.py`、`app/eval/metrics.py`、`app/services/eval_service.py`
> 实测环境：`EMBEDDING_PROVIDER=openai`（硅基流动 `BAAI/bge-m3`，1024 维）、`LLM_PROVIDER=mock`、KB#6（49 块）

## 一、三层总览

| 层 | 用途 | 实现 | 关键配置键 | 当前生效值 | 失败时的表现 |
|---|---|---|---|---|---|
| **向量化层** | 分块入库、语义召回、rerank 打分 | `hash`（本地特征哈希）/ `openai`（OpenAI 兼容） | `embedding_provider` `embedding_model` `embedding_api_base` `embedding_dim` | `openai` / `BAAI/bge-m3` / 1024 | 检索降级为空、rerank 失效 |
| **对话生成层** | 路由判定、问答合成、对比总结、报表叙述 | 统一工厂 `get_chat_model()`，`mock` / `openai` / `anthropic` | `llm_provider` `llm_model` `llm_api_base` `llm_temperature` | `mock`（未调真实模型） | 答案退化为模板 |
| **评测层** | RAGAS 四指标判分 | `RagasEvaluator`（judge LLM 走同一工厂 + 同一 Embedding） | `eval_llm_timeout` `eval_llm_max_retries` `eval_ragas_timeout` `eval_max_concurrency` | 120s / 3 次 / 600s / 4 并发 | 指标为 `None` 或整条 run 失败 |

三层共享同一条配置取值规则：**系统配置页覆盖值（`runtime_config`）> `.env` > 代码默认**，且**每次调用时实时读取**，所以后台改完不需要重启。

## 二、向量化层

### 2.1 两条实现，一个出口

`embed_texts(texts)` 是唯一入口，按 `embedding_provider` 分流（`embeddings.py:33-43`）：

**① `hash` —— 本地特征哈希（免密钥）**

```python
for n in (1, 2, 3):                       # 字符 1~3 gram
    for i in range(len(text) - n + 1):
        digest = md5(gram)                 # 每 gram 取 md5
        idx = digest[:4] % dim             # 前 4 字节定位桶
        sign = +1 / -1  (digest[4] & 1)    # 第 5 字节决定符号（signed hashing）
        vec[idx] += sign
L2 归一化
```

- **有局部词形相似、没有语义相似**：`退货率` 和 `退货比例` 不相似，但字面重合度高的块会接近。
- 用途：断网/无密钥时跑通链路、CI 断言稳定。
- 维度由 `EMBEDDING_DIM` 控制（默认 384，当前 .env 是 1024）。

**② `openai` —— OpenAI 兼容 Embedding 接口**

- 走官方 `openai` SDK，`base_url` 指向任意兼容网关（现用硅基流动）。
- 模型名、密钥、地址全部支持热更新；密钥走 `runtime_config.get_secret()`（敏感字段，接口返回打码）。
- 当前 `BAAI/bge-m3`，**1024 维，中文语义强**，这是检索质量的主要来源。

### 2.2 入库链路（`document_service.py:82-120`）

```
extract_text → split_text（500/50，表格感知 + 表头回填）
  → 按 16 条一批 embed_texts（_EMBED_BATCH=16，避免单次请求过大）
  → vector_store.add_chunks（chroma kb_{id}，hnsw:space=cosine）
  → 写 document_chunks（chroma_id = "{doc_id}:{chunk_index}"）
  → 失败回滚向量（先向量后 DB，防止「有分块无向量」脏数据）
  → invalidate_bm25(kb_id)（BM25 索引缓存失效）
```

### 2.3 检索链路（`retriever.hybrid_retrieve`）

```
问题 → embed_texts → chroma 向量召回 top_k
                     ┐
问题 → BM25 召回 top_k ┘→ RRF 融合（k=60，按排名而非分数加权）
                            → [可选] rerank：取前 top_k×3 候选，
                               用余弦重算并按阈值过滤
                            → 取 top_k 返回
```

四个设计要点：

1. **RRF 而不是分数加权**：向量距离和 BM25 分数量纲不可比，`1/(60+rank)` 只吃排名，天然免疫量纲问题。代价是**丢掉了分数信息**。
2. **BM25 中文按单字切**（`_TOKEN_RE = [A-Za-z0-9_]+|[一-鿿]`）：不依赖分词器，但「退货率」会被切成「退/货/率」，靠 IDF 与共现撑住。
3. **BM25 索引是进程内内存缓存**（`_bm25_cache`），首次检索全量构建，增删文档时 `invalidate_bm25` 失效。
4. **rerank 不是独立模型**，而是拿同一套 embedding 重算余弦——本质是「用精确相似度纠正 RRF 的排名偏差」。

### 2.4 实测：rerank 阈值的真实行为（重要）

以「P1 的响应时限是多久？」为例（KB#6，top_k=5）：

| rerank_threshold | 返回 | 说明 |
|---|---|---|
| 0（关） | doc14 块3、块2、块1、**doc6 块0(0.0164)**、doc6 块3 | 纯 RRF |
| 0.40 | doc14 块3(0.566)、块2、块1、doc14 块11(0.527)、doc6 块4(0.511) | 按余弦重排，**doc6 块3 被挤出** |
| 0.50 | 同上，仅分数微调 | 与 0.40 结果一致 |
| **0.60** | **召回为空** | 最高余弦仅 0.5658 < 0.6，全部被过滤 |

三条结论：

1. **bge-m3 的余弦分布是 0.43~0.75，不是 0~1 均匀分布**。阈值 0.3 等于不过滤；**0.6 会让整题答不出话**。
2. **RRF 排名与余弦排名不一致**：doc6 块0 在 RRF 里排第 4（0.0164），余弦只有 0.365；doc6 块3 在 RRF 里排第 5（0.0161），余弦 0.476 反而更高。开 rerank 后排序会变——**这是一种「换召回集」，不是单纯的「变好」**。
3. 「公司年会预算」（负例）的余弦是 **0.515**，正例题 top1 是 **0.565**，**区间重叠**。任何单一阈值都无法同时做到「保留正例、滤掉负例」——拒答必须放生成层。

## 三、对话生成层

### 3.1 唯一出口：`app/llm/factory.py`

改造前有三份各自为政的实现（`agent/llm.py` 恒 ChatOpenAI、`rag/llm.py` 自己分支、`eval/metrics.py` 又 new 一个），导致 `LLM_PROVIDER=mock` 只对其中一个接口生效。现在全部收口到：

```python
get_chat_model(purpose="chat" | "eval", temperature=None, timeout=None, max_retries=None)
generate_text(prompt, system=None)     # 单轮便捷入口
get_provider()                          # 白名单校验，非法值降级 mock
reset_cache()                           # 测试用
```

**四个设计点**：

1. **白名单降级**：`PROVIDERS = (mock, openai, anthropic)`，配置写了别的一律回退 `mock` 并打 warning——宁可降级也不让整个服务起不来。
2. **签名缓存**：缓存键 = `(provider, model, 温度, api_base, 密钥 sha256 前12位, timeout, max_retries)`。**密钥只以指纹进键**，不落明文；任一项变化即自动重建客户端，这就是「配置热更新」的实现方式。
3. **purpose 预设**：`chat` = 60s/2 次重试；`eval` = `EVAL_LLM_TIMEOUT`/`EVAL_LLM_MAX_RETRIES`（120s/3 次）。业务代码只说「我是用来聊天的还是判分的」，不关心 provider 差异。
4. **模型名解析**：配置页覆盖值 > `.env` > 内置默认（`deepseek-chat` / `claude-sonnet-4-5`）。

### 3.2 两条生成链路，两套 prompt

| 链路 | 入口 | prompt 形态 | 特点 |
|---|---|---|---|
| **纯知识库问答** | `/kbs/{id}/query` → `rag/llm.py::answer` | 单条字符串：`你是企业内部知识库助手… 【资料】… 【问题】… 【回答】` | 无历史、无工具，最轻 |
| **Agent 对话** | `/conversations/{id}/chat[/stream]` | `SystemMessage` + 历史 messages + `HumanMessage(工具检索结果)` | 有路由、有工具、多轮 |

两者的共同约束写在 prompt 里：**只依据给定资料、必须注明来源、没有就说「知识库中未找到相关信息」、不许编造**。这是「不胡编」的第一道防线（第二道是评测兜底）。

`answer_node` 有个易错点已修（注释里写了）：评测链路 `run_agent([], question)` 的 `messages` 为空，会退化成「您没有提出具体问题」，所以现在显式判断末条 human 是不是当前问题，不是就补一条。

### 3.3 mock 的设计：确定性优先

`MockChatModel` 继承 `BaseChatModel`，实现 `_generate` / `_stream` / `with_structured_output`，**输出由 prompt 形态决定，不含随机数**：

| prompt 形态 | 输出 |
|---|---|
| 含 `【资料】`+`【问题】` | 回显前 3 条资料；无资料则「资料中未找到相关信息。」 |
| 含 `【工具检索/查询结果】` | 基于工具结果给摘要 |
| 含 `query_a`（对比拆词） | 规则切出两个检索词，返回 JSON |
| 结构化 schema 含 `route` | 关键词规则判五路 |
| 其他 | 「已收到问题」固定提示 |

三个细节值得说：
- **必须用「用户问题：」锚点截取提问**，否则会把 prompt 里自带的「报表：需要汇总统计」当成用户问题，导致所有问题都被判成 `report`。
- `_stream` 是**按 24 字符切片真实吐流**，不是一次性返回再切——所以 SSE 前端在 mock 下也是逐字效果。
- `human` 消息优先于整条 prompt 文本，避免把 system prompt 复述给用户。

**代价**：mock 的路由是关键词规则（对比 > 报表 > 设备/工单 > 知识库 > 兜底），与真模型的口径不同。所以「路由准不准」在 mock 下只能验证链路通不通，不能验证准确率。

## 四、评测层

### 4.1 四指标与 judge 的来源

`RagasEvaluator.__init__` 里只构建一次，四条指标共用同一个 judge LLM：

```python
llm = LangchainLLMWrapper(get_chat_model(purpose="eval", temperature=0.0))
embeddings = LangchainEmbeddingsWrapper(_AppEmbeddings())   # 复用 app/rag 的 embed_texts
metrics = [Faithfulness(llm), AnswerRelevancy(llm, embeddings), ContextPrecision(llm), ContextRecall(llm)]
```

| 指标 | 衡量什么 | 依赖 |
|---|---|---|
| faithfulness | 答案是否都能被检索上下文支撑（防幻觉） | judge LLM |
| answer_relevancy | 答案与问题的相关度 | judge LLM + embedding |
| context_precision | 召回的块里相关的是否排在前面 | judge LLM |
| context_recall | 该召回的是否都召回了 | judge LLM |

**两个刻意的设计**：
1. **判分温度固定 0.0**，不读配置页的采样温度——判分要可复现，不能因为调了聊天温度导致历史分数不可比。
2. **Embedding 直接复用 `app_embeddings.embed_texts`**，不另建一套——否则「检索用的向量」与「评测用的向量」不是同一个空间，`context_recall` 没有意义。

### 4.2 单样本流程（`eval_service.py:609-663`）

```
run_agent([], question)                 ← 跑完整 Agent 图，拿到真实答案和路由
  → route 白名单：只有 rag / db_query 参与评测
     report / direct → 记 warning 后跳过（可审计，不再静默消失）
  → rag 路由重新 hybrid_retrieve 拿 contexts
     （用 rag_config 快照的 top_k / search_mode，保证与问答口径一致）
  → evaluator.evaluate_one(question, answer, contexts, reference)
  → 返回四指标 + latency_ms
```

**关键设计：评测不复用问答时的上下文，而是按同一参数重新检索一遍。** 原因是问答链路只在 tool_output 里拼了文本，没有保留结构化 contexts；重新检索能保证「评分用的上下文」和「参数」严格对齐，代价是多一次检索开销。

### 4.3 并发、重试、落库

| 机制 | 参数 | 设计理由 |
|---|---|---|
| 并发 | `EVAL_MAX_CONCURRENCY=4`，`ThreadPoolExecutor` | 上限 1~10，防上游 429；`EVAL_CONCURRENT_ENABLE=false` 可回退串行（结果口径完全一致） |
| 重试 | `EVAL_RETRY_ATTEMPTS=2`，线性退避 `min(2, 0.5×n)` | 单样本失败不打断整体，失败明细写进 run 的错误摘要 |
| 批量落库 | `EVAL_SCORE_BATCH_SIZE=10` | 减少 commit 次数；主线程批量写，工作线程不碰 DB |
| RAGAS 超时 | `EVAL_RAGAS_TIMEOUT=600` | 库默认 180s，长样本超时后指标**静默变 None**，这是踩过的坑 |
| 僵死清理 | `EVAL_STALE_RUN_SECONDS=600` | 启动时把超时仍 running 的 run 判为中断 |

另外 Chroma 的 `PersistentClient` 非线程安全（并发会触发 RustBindings 竞态），所以 `vector_store.py` 用 `RLock` 把所有客户端/集合操作串行化——**这是并发评测能跑的前提**。

### 4.4 mock 下的评测是「链路验证」不是「质量验证」

`provider=mock` 时 judge 也是 `MockChatModel`，它只会按模板输出「资料中未找到相关信息」之类文本，RAGAS 的 LLM 判分拿到的全是废话，**四指标没有实际语义**。所以历史 23 个 run / 333 条得分只能说明「评测流水线跑通了」，不能当质量结论讲。真实评测必须把 provider 切到 `openai`/`anthropic`。

## 五、三层怎么咬合在一起（这才是架构重点）

```
                     ┌── 系统配置页 / .env ──┐
                     │  runtime_config 覆盖  │
                     └──────────┬───────────┘
              ┌─────────────────┼──────────────────┐
     embedding_provider    llm_provider      eval_* 超时重试
              │                 │                  │
        ┌─────▼─────┐    ┌──────▼──────┐    ┌──────▼──────┐
        │ 向量化层  │    │ 对话生成层  │    │  评测层      │
        │ embed_texts│    │get_chat_model│    │ judge LLM   │
        └─────┬─────┘    └──────┬──────┘    └──────┬──────┘
              │                 │                  │
        ┌─────▼─────────────────▼──┐        ┌──────▼──────┐
        │ 检索层（向量+BM25+RRF）  │───────▶│ RAGAS 四指标 │
        └──────────────────────────┘  上下文 └─────────────┘
```

三个一致性约束，缺一个评测就不可比：

1. **provider 一致性**：问答与判分共用 `get_chat_model`，UI 切供应商两边同时生效。这是批次 2 的核心改造。
2. **embedding 一致性**：评测的 embedding 与检索的 embedding 是同一个函数、同一个模型。
3. **参数一致性**：`rag_config` 快照把 `top_k` / `search_mode` 固化进 run，保证「重跑同一 run」时检索口径不变。

## 六、已知风险与边界（实测/读码得出）

| # | 风险 | 说明 | 影响 |
|---|---|---|---|
| 1 | **切 embedding provider 会导致维度不匹配** | `EMBEDDING_DIM` 只约束 hash；`bge-m3`=1024、`text-embedding-3-small`=1536。换模型后旧 collection 维度不同，Chroma 会直接报维度错 | 换模型必须重建 collection（reprocess 全部文档） |
| 2 | **rerank_threshold 语义是余弦，不是 0~1 相关度** | bge-m3 下 0.6 会让召回全空，0.3 等于不过滤 | 只能凭实测分布调，不能凭直觉 |
| 3 | **负例无法靠分数区分** | 负例余弦 0.515 vs 正例 0.565，区间重叠 | 拒答必须放生成层，不能只用阈值 |
| 4 | **配置页覆盖值会永久遮蔽 .env** | 当前 `overridden_keys = [llm_api_base, llm_api_key, llm_model]`，改 .env 不生效 | 排障要同时看两处，或用 DELETE 接口恢复默认 |
| 5 | **mock 的路由是关键词规则** | 与真模型口径不同，且 `report`/`direct` 路由不参与评测 | mock 下只能验证链路，不能验证路由准确率 |
| 6 | **BM25 索引是进程内缓存** | 多 worker 部署时各进程独立、内存翻倍 | 单机演示没问题，横向扩容要换成外部索引 |

## 七、一句话总结（面试口径）

> 我的三层是**分层解耦、配置统一、口径一致**：向量化层有 hash 和 bge-m3 两条实现，靠 RRF 把向量召回和 BM25 融合，rerank 是用同一套 embedding 重算余弦来纠正排名偏差；对话生成层收口到一个工厂，provider 白名单 + 签名缓存做到热更新和非法配置降级；评测层用 RAGAS 四指标，judge LLM 和 embedding 都复用前面两层，保证「评测的是同一件事」。
>
> 而且这些参数不是我拍脑袋定的——`rerank_threshold=0.6` 会让召回直接空掉、负例余弦 0.515 和正例 0.565 区间重叠、切 embedding 模型必须重建 collection，这三条都是我在自己库上实测出来的。
