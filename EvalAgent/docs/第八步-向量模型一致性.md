# 第八步：向量模型与项目一对齐（bge-m3）

> 起因：用户发现项目一检索用的是 `BAAI/bge-m3`（硅基流动），而项目二裁判的 `answer_relevancy` 用的是
> `text-embedding-v3`（百炼），怀疑"不一致会不会算错"。
>
> 结论先行：
> 1. **不会算错** —— RAGAS 的 embedding 只用于 `answer_relevancy` 内部，从不与知识库向量比较，不存在跨空间问题；
> 2. **但确实该改** —— 同一个指标名在两套 embedding 下算出来的分**跨平台不可比**，而项目二是中央评测中台；
> 3. **不能只改字符串** —— 项目二原本 embedding 与裁判 LLM 共用 `api_base/api_key`，
>    直接填 `BAAI/bge-m3` 会把向量请求打到百炼 → 404 → `answer_relevancy` 全 NaN（现在会被熔断判死）。
>    所以先补了「向量模型独立 provider」，再切。

## 一、事实核实

### 项目一（检索侧）

```ini
# 企业垂直知识库 Agent 后台/.env
EMBEDDING_PROVIDER=openai
EMBEDDING_API_BASE=https://api.siliconflow.cn/v1
EMBEDDING_MODEL=BAAI/bge-m3
EMBEDDING_DIM=1024
```

且项目一的 RAGAS 评测**用的是同一套 embedding**（`app/eval/metrics.py`）：

```python
from ..rag import embeddings as app_embeddings

class _AppEmbeddings(Embeddings):
    def embed_documents(self, texts):  return app_embeddings.embed_texts(list(texts))
    def embed_query(self, text):       return app_embeddings.embed_texts([text])[0]

embeddings = LangchainEmbeddingsWrapper(_AppEmbeddings())
metrics = [AnswerRelevancy(llm=llm, embeddings=embeddings), ...]
```

**这一点很关键**：项目一的 `answer_relevancy` 是拿 **bge-m3** 算的。项目二用 `text-embedding-v3`，
两边的 AR 虽然同名，但底下的向量模型不同 → 分数不可比。

### 项目二（评测侧）

`app/services/judge.py` 里 embedding 只出现在 `_make_clients`，用途单一：

```python
embed = OpenAIEmbeddings(model=cfg.embedding_model, api_key=cfg.api_key, base_url=cfg.api_base or None, ...)
```

四个指标里**只有 `answer_relevancy` 会碰它**。

## 二、为什么"向量空间不同"不会算错（RAGAS 源码证据）

`ragas/metrics/_answer_relevance.py`：

```python
def calculate_similarity(self, question: str, generated_questions: list[str]):
    question_vec = np.asarray(self.embeddings.embed_query(question)).reshape(1, -1)
    gen_question_vec = np.asarray(self.embeddings.embed_documents(generated_questions))
    ...  # 余弦相似度
```

- 参与比较的是「原始问题」和「由答案反推出来的问题」，**两侧都用同一个 `self.embeddings` 编码**；
- 全程**没有**把 `retrieved_contexts` 拿去和知识库向量比 —— 那是检索侧的事，评测侧拿不到项目一的向量库；
- 整个 ragas 包里，用 `self.embeddings` 的指标只有 `answer_relevancy` / `answer_similarity` / `answer_correctness`，
  我们只用第一个；`faithfulness` / `context_precision` / `context_recall` 全靠 LLM。

所以「项目一 bge-m3、项目二 text-embedding-v3」不会产生数学上的错，**只会产生口径上的不可比**。

## 三、真正该改的理由（可复现 / 可比性）

1. **跨平台不可比**：项目二的核心价值是"统一口径评测"。项目一历史上用 bge-m3 算的 AR，与项目二用 v3 算的 AR
   放在同一张 A/B 表里比较，是两把尺子量同一件东西。
2. **跨时间不可比**：同一个项目二，换 embedding 前后的历史 run 也不能直接比 —— 所以换模型要"划断"，
   老数据要标注用的是哪个 embedding。
3. **未来加指标会踩坑**：一旦引入需要"上下文 ↔ 参考上下文"语义相似度的指标（例如 context 相似度类），
   就必须与检索侧同空间，那时没有独立 provider 就只能改代码。

### 硬约束：原来的实现换不了

`_make_clients` 里 embedding 用的是 `cfg.api_key` + `cfg.api_base` —— 和裁判 LLM 同一套。
直接把模型名改成 `BAAI/bge-m3`，请求会打到 `dashscope.aliyuncs.com`，模型不存在 → 404；
RAGAS 把异常吞成 NaN → `answer_relevancy` 全空 → 现在会被「空指标熔断」判死整轮。
**所以"改成一样"的前提是先拆开配置。**

### 关键代码

```python
@dataclass
class JudgeConfig:
    ...
    embedding_model: str = ""
    embedding_api_base: str = ""
    embedding_api_key: str = ""

    @property
    def emb_api_base(self) -> str:
        return self.embedding_api_base or self.api_base      # 留空 = 沿用裁判的

    @property
    def emb_api_key(self) -> str:
        return self.embedding_api_key or self.api_key

    def signature(self) -> tuple:
        # embedding 的 base/key 必须进签名：只改向量服务商却复用旧客户端，
        # 表现是「界面改了没生效」，比报错难查得多
        return (self.model, self.api_base, self.api_key, self.embedding_model,
                self.emb_api_base, self.emb_api_key, self.temperature)
```

### 向量探活（新增，原来只探 LLM）

```python
@staticmethod
def _probe_embeddings(embeddings, cfg) -> int:
    vecs = embeddings.embed_documents(["销售额统计", "上下文召回测试"])
    # 1) 能出向量；2) 同一批维度一致；3) 不是全零
    ...
    if all(abs(float(x)) < 1e-12 for x in vecs[0]):
        raise JudgeUnavailable("向量模型探活失败：返回全零向量（疑似网关占位，会让 answer_relevancy 恒为 0）")
```

为什么要检「全零向量」：个别网关对不认识的 embedding 模型会回 `[[0.0]*dim]` 这种"成功但无意义"的响应，
`answer_relevancy` 会稳定算成 0 —— 长得像"模型相关性很差"，比报错更难查。

探活结果现在会直接报维度和模型：

```
结构化输出正常（qwen3.8-flash，1520ms）；向量 BAAI/bge-m3 1024 维正常
```


返回：

```json
{"changed": true,
 "applied_keys": ["JUDGE_EMBEDDING_API_BASE","JUDGE_EMBEDDING_API_KEY","JUDGE_EMBEDDING_MODEL"],
 "preflight": {"ok": true, "latency_ms": 2189}}
```

**裁判 LLM（qwen3.8-flash @ 百炼）未动**，只把向量换成 bge-m3 @ 硅基流动 —— 这正是「独立 provider」要支持的能力。
`1024 维`与项目一 `EMBEDDING_DIM=1024` 对齐。

### 2. 真实评测（同数据集 19，7 条样本，同一裁判模型，温度 0）

| 任务 | embedding | 状态 | run 级 AR |
|---|---|---|---|
| #167 | text-embedding-v3 | `done` 7/7 | **0.6677** |
| #222 | BAAI/bge-m3 | `done` 5/7（2 条失败） | **0.6986** |

> 直接比 run 级均值会被分母坑到（222 只算了 5 条）。所以逐条对齐：

| seq | text-embedding-v3 | BAAI/bge-m3 | Δ |
|---|---|---|---|
| 1 | 0.000 | 0.000 | 0 |
| 4 | 0.993 | 0.995 | +0.002 |
| 5 | 0.966 | 0.960 | −0.006 |
| 6 | 0.907 | 0.692 | **−0.215** |
| **4 条重叠样本均值** | **0.7165** | **0.6618** | **−0.055** |

**怎么读这张表**：3 条样本的差异 ≤0.006（可视为噪声），1 条掉了 0.215（模型对"同义改写"的判定分歧）。
均值差 −0.055 恰好落在既有记录的裁判方差 ±0.05 量级内 —— 也就是说，
**单次运行既证明不了 bge-m3 更好，也证明不了更差**。

> 所以本次切换的正当性**不是"分数更好"**，而是「与项目一同一把尺子」。这点必须讲清楚，
> 否则下一次有人看到分数变了会以为 embedding 换错了。

### 3. 顺带发现：这次有 2 条样本失败（与 embedding 无关）

| seq | error_msg |
|---|---|
| 2 | `打分失败：RAGAS 打分异常：InvalidStateError: invalid state` |
| 3 | `打分超时（>300s）` |

- `InvalidStateError: invalid state` 是 **RAGAS 在 `asyncio.to_thread` 里并发打分时的线程/事件循环竞态**
  （httpx AsyncClient 跨 loop 复用），与向量模型无关 —— run #167（v3）没出错、#148 出过 1 条超时，属间歇性；
- 这是**独立于本次改动的稳定性问题**，建议单独一轮排查方向：
  ① `JUDGE_MAX_CONCURRENCY` / `RUN_ITEM_CONCURRENCY` 降到 2 观察复现率；
  ② 打分不再用 `to_thread`，改成"每样本一个独立线程 + 独立 ragas 调用上下文"；
  ③ 记录失败时的 loop/线程标识，确认是否同一 executor 线程复用。
- 不影响本次结论：失败行不参与均值，且熔断逻辑（连续 3 条全空）未触发。

## 八、运维口径（换 embedding 时必须做的三件事）

1. **换完立刻跑一次基线**：同一数据集、同一 `top_k`、同一裁判 LLM，跑 7 条以上，把 AR 记下来；
   之后所有对比都以这次为基线，**不要跨配置比**。
2. **A/B 两侧必须同 embedding**：`variant` 不同但裁判配置必须一致，否则 Δ 里混进了向量模型的差异（而且量级还不小，见上面 seq6）。
3. **历史 run 要能追溯**：`evaluator_config` 现在同时快照 `judge_model` 与 **`judge_embedding_model`**
   （`create_run` 与 `_finalize` 都写，取的是生效配置），`GET /eval/runs/{id}` 返回 `judge_embedding_model`，
   详情页「向量模型」一栏直接显示。否则半年前的 run 无法回答"当时用的哪个向量模型"。

## 九、这次踩到的一个"看起来是对的"陷阱

「`text-embedding-v3` 和 `bge-m3` 都是 1024 维，所以可以混用」——**错**。
维度相同只代表「能算余弦距离」，不代表语义空间一致。两个模型对"同义改写"的判定差异很大：
本次实测里 seq6 的 AR 从 0.907 掉到 0.692，就是同一个答案在两个空间里"相关性"判定不同。

所以判断标准不是维度，而是：**同一张对比表里的所有分数，必须由同一个 embedding 模型产生**。
