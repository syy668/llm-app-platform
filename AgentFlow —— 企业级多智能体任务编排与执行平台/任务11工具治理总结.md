```python

def _map_kb_search_v2(args):               # payload 兼容映射注册表
    return {("search_query" if k == "query" else k): v for k, v in args.items()}

PAYLOAD_ADAPTERS = {("kb-search", "v2"): _map_kb_search_v2}

class ToolVersionRouter:
    def resolve(self, tool, arguments) -> ToolResolution:
        # 无路由 → 原样直通；有路由 → 工具名改写为 {tool}-{version}，参数按适配器映射
```

**2. 幂等结果缓存 `IdempotencyStore`**

```python
key = agentflow:tool:idem:{task_id}:{tool}:{sha256(canonical_args)[:32]}   # TTL 600s
load(key)   # 命中 → 直接返回上次成功结果；Redis 故障 → 视为未命中（fail-open）
save(key, payload)  # 只在调用成功后写；失败/超时不落缓存（重试仍会真实发起）
```

## 四、面试话术

> **"多 Agent 并发下，你怎么防止重复副作用和兼容底层接口升级？"**
>
> "我在 MCP 工具调用的唯一咽喉——客户端连接池的 `call` 入口——加了两层轻量治理中间件，工具实现和协议层一行没动。
>
> **防重复副作用**：Agent 的重试矩阵是双刃剑——查询类工具重试是韧性，但推送通知、扣库存这类副作用工具重试就是事故。我给每次调用生成 `task_id + 工具名 + 参数哈希` 的幂等键写 Redis：调用前先查，命中说明这是超时重试，直接返回上次成功的结果，真实调用一次都不会多发；只有成功结果才落缓存（TTL 10 分钟），失败重试仍然真实发起，不会把暂时性故障冻结成假成功。task_id 是我之前用 ContextVar 做日志追踪时注入的，这里零成本复用，调用方完全无感知。
>
> **兼容接口升级**：底层接口 v1 升 v2 时，最怕 Agent 硬编码全盘失效。我做了一个配置驱动的版本路由适配器：运维只在配置表里把 `kb-search` 指到 v2，适配器自动改写实际下发的工具名、并按注册表里的 payload 映射函数把 v1 参数（`query`）转成 v2 契约（`search_query`）——上层 Planner 和 Executor 完全无感知。还有一个兼容层韧性细节：如果配置先行、v2 工具还没部署，路由器在服务发现里找不到目标版本，会自动回退 v1 原契约并打 WARNING，灰度期系统照常跑。
>
> 两条防线都有同一个设计原则：**治理逻辑必须放在所有调用的必经之路，而不是散在各工具里**——这也让 13 个单测可以用可编程的传输层桩做端到端验证，比如模拟重试 3 次断言底层只执行 1 次。"
