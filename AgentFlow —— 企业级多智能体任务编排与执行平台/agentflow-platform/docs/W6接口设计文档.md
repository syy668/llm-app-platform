## 1. `GET /tasks` —— 任务分页列表（缺口 G1）

### 1.1 PRD 依据与角色

- PRD §7.1 任务类接口清单；角色规则：**A/R 可查全部（可按创建人过滤），V 仅本人创建**。
- 服务端强制：`role == viewer` 时忽略请求中的 `creator_id`，强制 `creator_id = current_user.id`（**脱敏第 1 条**）。

### 1.2 请求

```
GET /api/v1/tasks?page=1&size=20&status=COMPLETED&creator_id=1001&keyword=退货&start=2026-10-01T00:00:00&end=2026-10-21T23:59:59&order=created_desc
```

| 参数              | 类型       | 必填 | 校验                                                                                        | 说明                                        |
| --------------- | -------- | -- | ----------------------------------------------------------------------------------------- | ----------------------------------------- |
| `page`          | int      | 否  | ≥1，默认 1                                                                                   |                                           |
| `size`          | int      | 否  | 1~100，默认 20                                                                               | 上限与 `PageMeta.size` 一致                    |
| `status`        | string   | 否  | 枚举 `TaskStatus`（PLANNING/RUNNING/AWAITING_APPROVAL/COMPLETED/FAILED/CANCELLED），可多值 `,` 分隔 |                                           |
| `creator_id`    | int      | 否  | 存在于 users                                                                                 | viewer 下被忽略并强制覆盖                          |
| `keyword`       | string   | 否  | ≤64                                                                                       | 对 `goal` 做 LIKE `%kw%`（SQLite/MySQL 兼容写法） |
| `start` / `end` | datetime | 否  | ISO8601                                                                                   | 过滤 `tasks.created_at`                     |
| `order`         | string   | 否  | `created_desc`（默认）/ `created_asc`                                                         | 排序                                        |

### 1.3 响应 `ApiResponse[PageData[TaskListItem]]`

`TaskListItem` **复用 `task_service.get_detail` 顶层字段名**（前端 `types/task.ts` 已按此建模），去掉重负载（不含 `subtasks` 数组）：

```json
{
  "code": "OK", "message": "ok", "trace_id": "…",
  "data": {
    "items": [
      {
        "task_id": 1024,
        "task_no": "AF20261021-0007",
        "goal": "分析 10 月华南大促退货率异常原因",
        "time_range": {"start": "2026-10-01", "end": "2026-10-21"},
        "status": "COMPLETED",
        "replan_count": 0,
        "token_usage": 183420,
        "trace_id": "tr_9f2c…",
        "creator_id": 1001,
        "creator_name": "ops_zhangsan",
        "error": null,
        "created_at": "2026-10-21T10:02:11",
        "finished_at": "2026-10-21T10:06:47",
        "duration_s": 276
      }
    ],
    "meta": {"page": 1, "size": 20, "total": 57}
  }
}
```

| 字段             | 来源                         | 说明                                                    |
| -------------- | -------------------------- | ----------------------------------------------------- |
| `creator_name` | JOIN `users.username`      | 列表展示创建人；**viewer 角色时恒为 `null`**（脱敏第 2 条，PRD：V 无创建人字段） |
| `error`        | `tasks.error` JSON         | 仅取 `{code, message}`，`span_id` 不下发（列表不需要）             |
| `duration_s`   | `finished_at - created_at` | 服务端算好，前端不再重复计算；未终态为 `null`                            |

### 1.4 性能

- 现有索引 `ix_tasks_status_created_at(status, created_at)` 覆盖状态过滤；纯时间范围扫描建议补 `ix_tasks_created_at`（单列，迁移一份）。
- `keyword` LIKE 在 MySQL 走前缀索引有限，内部数据量级（千级）可不加全文索引。

### 1.5 错误

| 场景                       | 返回                                             |
| ------------------------ | ---------------------------------------------- |
| `status`/`order` 非法值     | 422 `VALIDATION_ERROR`                         |
| `creator_id` 不存在         | 422 `VALIDATION_ERROR`（不做 404，避免枚举用户）          |
| viewer 传入他人 `creator_id` | 200 正常返回，但数据被强制限定为本人（**不报错，静默覆盖**，避免泄露他人任务存在性） |

## 2. `GET /dashboards/summary` 与 `GET /dashboards/tools` —— 大盘聚合（缺口 G2）

### 2.1 PRD 依据与角色

- PRD §7.1：`GET /dashboards/summary`，角色 **A/R/V（V 脱敏）**。
- 脱敏定义（V）：`token_usage_total`、`avg_token_per_task` 返回 `null`；其余指标正常返回（前端 viewer 态卡片显示「—」并提示脱敏）。

### 2.2 `GET /api/v1/dashboards/summary?start=&end=`

| 参数      | 必填 | 默认       | 说明                |
| ------- | -- | -------- | ----------------- |
| `start` | 否  | 今日 00:00 | ISO8601 datetime  |
| `end`   | 否  | 今日 24:00 | 必须晚于 start，否则 422 |

**响应 `data`**（字段与前端 P02 五张指标卡一一对应）：

```json
{
  "window": {"start": "2026-10-21T00:00:00", "end": "2026-10-21T23:59:59"},
  "task_total": 12,
  "completion_rate": 0.75,
  "pending_approvals": 3,
  "avg_duration_s": 241,
  "token_usage_total": 1520330,
  "avg_token_per_task": 126694,
  "status_breakdown": {
    "PLANNING": 0, "RUNNING": 2, "AWAITING_APPROVAL": 3,
    "COMPLETED": 6, "FAILED": 1, "CANCELLED": 0
  }
}
```

| 字段                                         | 计算口径                                                                | 前端消费卡                                |
| ------------------------------------------ | ------------------------------------------------------------------- | ------------------------------------ |
| `task_total`                               | `COUNT(tasks)` in window（按 `created_at`）                            | 「今日任务总量」                             |
| `completion_rate`                          | `COMPLETED / 终态总数`（终态=COMPLETED+FAILED+CANCELLED）；窗口内无终态任务时返回 `0.0` | 「任务完成率」                              |
| `pending_approvals`                        | `COUNT(tasks WHERE status=AWAITING_APPROVAL)`（不限定 window，反映当前积压）    | 「待审批数量」（**替换现在从审批列表 total 间接取值的逻辑**） |
| `avg_duration_s`                           | 窗口内终态任务 `AVG(duration_s)`；无样本返回 `null`                              | 「平均端到端耗时」                            |
| `token_usage_total` / `avg_token_per_task` | `SUM/AVG(tasks.token_usage)` in window                              | 「总 Token 消耗」                         |
| `status_breakdown`                         | 窗口内 `GROUP BY status`，六键恒齐（缺的补 0）                                   | 预留：状态分布图，前端本期可不用                     |

> 一致性说明：`pending_approvals` 与 `GET /approvals` 的 `total` 同源（都是 AWAITING_APPROVAL 计数），切换后前端两处数字不会出现矛盾。

### 2.3 `GET /api/v1/dashboards/tools?start=&end=`

参数与 2.2 相同。数据源：**`task_executions` 按 `tool_name` 聚合**（真实执行记录；不要用 `subtasks.tool_hint`，那是规划意图不是实际调用）。

```json
{
  "window": {"start": "…", "end": "…"},
  "items": [
    {"tool_name": "sql-query",      "call_count": 84, "success_rate": 0.96, "avg_latency_ms": 412},
    {"tool_name": "chart-render",   "call_count": 37, "success_rate": 1.0,  "avg_latency_ms": 158},
    {"tool_name": "kb-search",      "call_count": 22, "success_rate": 0.91, "avg_latency_ms": 630},
    {"tool_name": "notify",         "call_count": 6,  "success_rate": 1.0,  "avg_latency_ms": 95}
  ]
}
```

- `call_count`：`COUNT(*) GROUP BY tool_name`；`success_rate`：成功次数/总数（成功判定沿用 `task_executions` 既有状态字段口径）；`avg_latency_ms`：执行耗时均值，无耗时记录时 `null`。
- 按 `call_count` 降序返回，前端饼图/条形图直接用。
- 无记录时 `items: []`（不报错）。

## 3. 评测接口组 —— `/eval/runs`（缺口 G3，FR-016 P1）

### 3.1 关键事实（实现前必读）

1. **`eval_runs` 表已存在**（`orm_models.py` L280）：`run_no` / `source`(reviewer_gate|regression|ab_test) / `dataset_id` / `variant`(compress_on|compress_off) / `ext_run_id` / `metrics` JSON / `status`(PENDING|RUNNING|DONE|FAILED) / `detail` JSON。本组接口 = 对这张表的读 + 触发 + 回写。
2. **PRD 内部矛盾裁决**：A-02 写「AgentFlow 内嵌轻量评测 runner，项目二仅作展示端」，而评测看板流程（PRD L704-706）写「触发项目二 → 回调 → 每 10s 轮询回写」。**以 L704-706 主流程为准**（它是 FR-016 的实现细节章）；`MOCK_EXTERNAL_EVAL=true` 时（当前 dev_serve 默认态）由内嵌 mock runner 生成 metrics 落库，即「内嵌 runner」语义，两种模式共用同一张表与同一组接口，联调期不依赖项目二。

### 3.2 `GET /api/v1/eval/runs?page=&size=&source=&variant=&status=`

- **角色：A/R**。viewer 调用返回 403 `FORBIDDEN`（PRD L562：V 仅汇总）。
- 分页信封同 §1；过滤参数 `source` / `variant` / `status` 均可多值 `,` 分隔；按 `created_at` 降序。
- **响应 item**（直接映射表列，不造新字段）：

```json
{
  "run_id": 31,
  "run_no": "ER20261021-0004",
  "source": "regression",
  "variant": "compress_on",
  "dataset_id": "agentflow-30",
  "ext_run_id": "evr_8a2c",
  "status": "DONE",
  "metrics": {
    "task_completion": 0.93,
    "plan_f1": 0.87,
    "tool_acc": 0.91,
    "token_cost": 1420000,
    "latency_p50_s": 188,
    "latency_p95_s": 402
  },
  "sample_count": 30,
  "error_message": null,
  "created_at": "2026-10-21T14:00:00",
  "finished_at": "2026-10-21T14:21:36"
}
```

| 字段              | 来源                       | 说明                                                                                                               |
| --------------- | ------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| `metrics`       | `eval_runs.metrics` JSON | 键名**沿用表注释里的既有键**：`task_completion / plan_f1 / tool_acc / token_cost / latency_p50 / latency_p95`；DONE 前可为 `null` |
| `sample_count`  | `detail` JSON 的样本数       | `detail` 逐样本明细不整体下发（体积大），仅出计数；需要明细时后续加 `GET /eval/runs/{id}/samples`，本期不做                                        |
| `error_message` | `detail.error` 或状态回写记录   | FAILED 时给一句话原因                                                                                                   |

### 3.3 `GET /api/v1/eval/runs/summary?variant=compress_on&variant=compress_off`

- **角色：A/R/V**（viewer 的「汇总」入口，本接口对 V 开放；V 请求时 `token_cost` 类字段返回 `null`，脱敏）。
- `variant` 可传多个；不传 = 全部 variant 各聚合一行。
- 用途：P06「上下文压缩 A/B 对比」卡（前端 `expected-api` 与此一致）。

```json
{
  "window": null,
  "groups": [
    {
      "variant": "compress_on",
      "run_count": 6,
      "avg_task_completion": 0.93,
      "avg_plan_f1": 0.87,
      "avg_tool_acc": 0.91,
      "avg_token_cost": 1420000,
      "token_saving_rate": 0.38,
      "avg_latency_p95_s": 402
    },
    {
      "variant": "compress_off",
      "run_count": 5,
      "avg_task_completion": 0.92,
      "avg_plan_f1": 0.86,
      "avg_tool_acc": 0.90,
      "avg_token_cost": 2290000,
      "token_saving_rate": null,
      "avg_latency_p95_s": 371
    }
  ]
}
```

- **`token_saving_rate` 计算口径（写死，避免歧义）**：以 `compress_off` 组 `avg_token_cost` 为基线，`1 - 该组 avg_token_cost / 基线`；基线组（`compress_off` 自身）为 `null`；无基线组时两组均为 `null`。仅统计 `status=DONE` 的 run。
- A/B 差值由前端两行相减得出，后端不算 `delta` 字段（避免重复口径）。

### 3.4 `GET /api/v1/eval/metrics?start=&end=`

- **角色：A/R/V（V 同样脱敏 token 字段）**。用途：P06「指标趋势」按天折线（前端 `expected-api` 与此一致）。
- 窗口内按**自然日**对 DONE 状态 run 聚合：

```json
{
  "points": [
    {"date": "2026-10-19", "run_count": 2, "avg_task_completion": 0.91, "avg_plan_f1": 0.85,
     "avg_tool_acc": 0.90, "avg_token_cost": 2050000, "avg_latency_p95_s": 415},
    {"date": "2026-10-20", "run_count": 3, "avg_task_completion": 0.94, "avg_plan_f1": 0.88,
     "avg_tool_acc": 0.92, "avg_token_cost": 1710000, "avg_latency_p95_s": 390}
  ]
}
```

- 无数据的日期不出点（前端折线断点处理）；`points` 按日期升序。

### 3.5 `POST /api/v1/eval/runs` —— 触发回归评测（FR-016 验收标准 2）

- **角色：A/R**（viewer 403）。
- 请求体（`extra="forbid"`，与 W3 契约风格一致）：

```json
{"dataset_id": "agentflow-30", "variant": "compress_on", "note": "10月第三轮回归"}
```

| 字段           | 类型     | 必填 | 校验                                   |
| ------------ | ------ | -- | ------------------------------------ |
| `dataset_id` | string | 否  | ≤64，默认 `"agentflow-30"`（PRD 写死的数据集）  |
| `variant`    | string | 否  | 枚举 `EvalVariant`；回归评测可比对两种时由调用方分两次提交 |
| `note`       | string | 否  | ≤200，写入 `detail.note` 供列表备注          |

- **处理流程**（对应 PRD L704-706）：
  1. 本地插入 `eval_runs`：`source=regression`、`status=PENDING`、`run_no` 按既有编号规则生成 → **立即返回 200**，不阻塞等待评测完成；
  2. 转发项目二 `POST {EVALAGENT_BASE_URL}/api/v1/eval/runs`（body 带 `dataset_id, target=agentflow, variant, callback_run_no`），成功则把返回的 run id 写入 `ext_run_id` 并置 `status=RUNNING`；


1. 后台任务每 10s 轮询 `GET {EVALAGENT_BASE_URL}/api/v1/eval/runs/{ext_run_id}`，DONE 后把 metrics 写入 `eval_runs.metrics`、置 `status=DONE`（PRD L706 原文口径）；连续失败超阈值（建议 30 次 ≈5 分钟）置 `FAILED`；
2. **mock 模式**（`settings.MOCK_EXTERNAL_EVAL=true`）：跳过 2/3，由内嵌 runner 直接生成 metrics 落库置 DONE——与现有 health 摘要里 `mock.external_eval` 语义一致。

- **响应 `data`**：`{"run_id": 31, "run_no": "ER20261021-0004", "status": "PENDING"}`，前端拿 run_id 轮询 `GET /eval/runs` 刷新（PRD 验收标准 2 的「指标自动回写并在看板刷新（轮询间隔 10s）」由**后端轮询回写 + 前端页面 10s 轮询列表**两端共同完成）。
- **错误**：项目二不可达且非 mock → 502 `EVAL_UPSTREAM_UNAVAILABLE`，本地记录置 `FAILED`（`error_message=upstream unreachable`），响应体正常信封携带错误码；`variant` 非法 → 422。
- **新增配置**（`app/core/config.py`）：`EVALAGENT_BASE_URL: str = ""`（空 + 非 mock 时触发返回 502）、`EVAL_POLL_INTERVAL_S: int = 10`、`EVAL_POLL_MAX_RETRY: int = 30`。
- **并发约束**：同一 `dataset_id+variant` 存在 PENDING/RUNNING 记录时返回 409（错误码复用 `TASK_INVALID` 语义不当，新增 `EVAL_RUN_DUPLICATE`，HTTP 409；或直接 422 `VALIDATION_ERROR`，实现时二选一并记录到 CHANGELOG）。
