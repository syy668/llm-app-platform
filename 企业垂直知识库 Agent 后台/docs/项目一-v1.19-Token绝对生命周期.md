# v1.19 Token 绝对生命周期（A3 安全边界补齐）

日期：2026-10-25
背景：文档《产品与技术总结》第 96 行遗留边界 3「Token 绝对过期上限缺失」。
目标：一次登录（含任意次滑动续期与 refresh 轮换）最长存活 30 天，到期必须重新登录。

## 一、动手前纠正的三个事实

| 任务描述 | 实际情况 | 影响 |
|---|---|---|
| 「在 JWT payload 加 iat」 | **本项目不用 JWT**。access/refresh 都是「随机串 + HMAC-SHA256」，`requirements.txt` 无 `pyjwt`/`python-jose` | 加 JWT 需引新依赖（违反约束 3）且要重写整条 token 链 |
| 「refresh 只有滑动续期」 | **access session 也滑动续期**（`security.py` 的 `get_session` 每次 `expire` 重置 30min） | 只改 refresh = A3 完全失效：持续访问永不触发 refresh |
| — | 现有用例 `test_refresh_token_storage_rule` 断言 `redis.get(key) == str(user_id)` | 任何「value 改 JSON」的方案都会打红既有用例（违反 524 全绿） |

## 二、设计：iat 编进 token

```
现在：{random}.{hmac}
改后：{random}~{iat}.{hmac}      iat = 首签时间戳（续期不变）
```

**为什么不用 JWT**：引依赖 + 重写整链，属重构而非局部增强。
**为什么不用 Redis value 存 JSON**：直接打红 `test_refresh_token_storage_rule`，且存量 token 需迁移。
**为什么不用独立 key `kb:iat:{token}`**：两个 key 有同步/残留问题，多一次往返；Redis 内存淘汰丢掉 iat 会**静默放宽**成新的 30 天。

**方案优势**：
1. iat 参与 HMAC → **改 iat 必然验签失败**，安全性不依赖 Redis 完整性；
2. 续期只改 Redis TTL、不动 token 内容 → iat 天然不变；
3. 轮换从旧 token 解析后写入新 token → 绝对起点跨刷新传递；
4. `redis.get(key)` 仍是 `str(user_id)` → **零既有用例改动**；
5. `~` 不在 `token_urlsafe` 字符集内，且不干扰 `rsplit(".", 1)` 取签名段；老 token 无 `~` 照样验签通过。

## 四、两处刻意的取舍

**1. 旧格式 access session 直接判无效**
升级前签发的 session 没有 iat，且无法补进去（改内容即毁签名）。处理：判无效并删除，前端收 401 后自动用 refresh 换新 token —— 用户**无感**，但从此进入受上限约束的新格式。这是唯一能真正闭环的做法。

**2. 旧格式 refresh token 放行一次，按 now 起算**
存量 refresh（Redis 里 7 天内签发的）解析不到 iat，若直接拒会导致所有在线用户强制重登。处理：放行，轮换时以当前时间为新起点（**一次性宽限**，此后不再放宽）。最坏情况是这批老 token 多拿一次 30 天，但不会无限。

## 五、fail-safe

| 场景 | 行为 |
|---|---|
| `parse_token_iat` 畸形输入 / 非数字 / None | 返回 `None`（当 legacy），绝不抛 |
| `is_absolutely_expired` 计算异常 | 返回 `False`（不判超期），打 WARNING |
| 配置非法（0 / 负数 / 非数字） | 回退 30 天，且最小 clamp 到 1 小时 |
| 新增校验本身出问题 | 只影响「是否超期」这一个判断，签名 / 黑名单 / 存在性三道旧防线照常生效 |

只有「我们主动算出超期」这一种情况才会拒绝，其余路径全部维持 v1.18 行为。

## 六、实测（真实 MySQL 用户 + 真实 security 代码）

```
user_id = 1
refresh token 形态      : AS6bensMgfsL7hI1rG...c7e1e71981

```

## 八、运维须知

1. **升级影响**：部署后所有在线 access session 会失效一次，前端自动 refresh 无感恢复；若某用户 refresh token 已超 7 天未用，则需重新登录（属预期）。
2. 调整上限改 `.env` 的 `TOKEN_MAX_LIFETIME_SECONDS` 后**需重启**（`settings` 是启动时读取）。
3. 刻意**不加**系统配置页控件：绝对生命周期是安全基线，不应给运营一个「改成 100 年」的下拉框。
