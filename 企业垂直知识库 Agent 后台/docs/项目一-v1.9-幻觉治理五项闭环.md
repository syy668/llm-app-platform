### 1.3 三个设计取舍（都能被追问）

1. **不新增数据库列**。点踩原因复用 `message_feedbacks.comment`；样本只落在
   `eval_dataset_items` 现有字段上。理由：`create_all` 不给存量表补列，加列就要
   在生产 MySQL 上跑 ALTER，且 `schema_check` strict 模式会直接阻断启动。
2. **`reference_answer` 刻意留空**，而不是填 AI 的错误答案。填错的参考答案会让
   RAGAS 把幻觉当基准反过来打分；留空时 faithfulness / answer_relevancy /
   context_precision 仍可计算，只有 context_recall 缺参照 → 响应里用
   `needs_reference=true` 提示前端。AI 原答案并未丢失，`messages` 表按
   `message_id` 可回溯。
3. **集合名固定 + 按 KB 聚合 + 只能上报自己的消息**。不接受任意 `dataset_id`，
   避免普通用户借上报接口往别人的评测集塞样本（越权写）。

### 1.4 前端

- `src/api/features.ts`：`BadcaseResult` 类型 + `addBadcaseToEval(messageId, reason?)`。
- `src/views/Chat.vue`：AI 气泡工具栏新增 ☆ 按钮（`Star` 图标），点击弹原因输入
  （可留空）→ 提交 → 按钮置为已加入态；`duplicated=true` 时提示「已在集合中，已更新反馈原因」。

### 1.5 测试（`tests/test_badcase_flywheel.py`，12 例）

## 任务 3：轻量级后置引用校验

新增 `app/rag/citation_guard.py`：

```python
def validate_citations(answer: str, context: str) -> dict:
    """返回 {"suspect": bool, "checked": int, "misses": list[str]}；不抛错、不拦截。"""
```

算法：`_DATE_RE` 抽日期 + `_NUMBER_RE` 抽数字（去千分位后 ≥3 位）→ 归一化 →
在归一化后的上下文里做子串比对 → 未命中打 `WARNING: hallucination_suspect` 并置
`suspect=true`。

四个防误杀设计：

| 设计 | 原因 |
|---|---|
| **只标记不拦截** | 误判代价是多一个提示，拦截代价是答对也不给答案 |
| **无上下文不校验** | direct 路由合法地会提数字，拿空上下文比对必然全量误报 |
| **拒答文案放行** | 「未找到相关信息」本身没有事实主张，里面的年份会被误判 |
| **1~2 位数字忽略** | `[来源1]`、序号、`8.4%` 都不该参与校验 |

归一化细节（踩过的坑）：`2024-01-05` 与 `2024年1月5日` 必须能对上，所以
`年/月/日`、`/`、`.` 统一成 `-`，并且**去掉各数字段的前导零**——否则一个归一化成
`2024-01-05`、另一个成 `2024-1-5`，会把正常日期判成幻觉（有专门用例守着）。

接入点：`agent_service.chat` 在写回复前校验（`result["context"]`），响应新增
`suspect` / `citation_misses`；`stream_service` 在 `done` 事件里同样下发。前端在
气泡头部显示橙色「待核验」标签（hover 提示「数字/日期未能在检索资料中找到」）。

测试：`tests/test_hallucination_guard.py` 14 例（含千分位、日期格式、拒答、空上下文、
脏数据不抛错）。

**已知局限**：子串比对只能证明「这个数在上下文里出现过」，不能证明「用在正确的位置」。
上下文同时有 500 和 800 时，答案把标准说成 500 仍会通过——这一步是降低幻觉留存率，
不是证明答案正确。

## 任务 4：引用卡片（溯源 UI）

### 4.1 后端：把结构化来源一路带出来

```
retriever.hybrid_retrieve()            # 已有：返回带 chunk_id/document_title/content/score 的命中
   ↓
rag_tool.rag_retrieve_with_sources()   # 新增：返回 (带 [来源i] 标号的文本, to_sources(hits))
   ↓
graph.rag_node / parallel_compare_node # AgentState 新增 sources 字段
   ↓
run_agent() → {answer, route, context, sources}
   ↓
agent_service.chat → sources              （POST /conversations/{id}/chat 响应）
stream_service → done 事件 {..., sources, suspect, citation_misses}   （前端实际走这条）
```

`rag_tool` 改造后有三个函数，职责清晰且**不嵌套重试**：

```python
@with_retry
def _retrieve(...) -> tuple[str, list[dict]]:   # 唯一带重试的实现
def rag_retrieve_with_sources(...)               # 新入口：文本 + sources
def rag_retrieve(...)                            # 旧签名：只返回文本，历史调用方零改动
```

> 踩坑记录：最初把 `@with_retry` 同时套在两个公开函数上，`rag_retrieve` 内部又调
> `rag_retrieve_with_sources`，失败时会变成 3×3=9 次尝试。改为「一个带装饰器的实现 +
> 两个薄封装」后，每个入口恰好一层重试。

**并行对比路由的重编号**：两路检索各自从 `[来源1]` 编号，合并后必须顺延，
否则前端点击 B 路的「来源1」会串到 A 路的片段：

```python
def _shift_source_labels(text: str, offset: int) -> str:
    return re.sub(r"\[来源(\d+)\]", lambda m: f"[来源{int(m.group(1)) + offset}]", text)
```
合并后 `sources` 的 `index` 连续（A 在前、B 顺延），并带 `group: "A"/"B"` 供 UI 标注。

### 4.2 前端

- `renderAnswer(m)`：`renderMarkdown` 之后把 `[来源N]` 正则替换为
  `<span class="cite-chip" data-cite="N">来源N</span>`（仅当本条消息有 `sources`）。
- 事件委托 `onBubbleClick`：v-html 内容无法直接绑事件，因此监听 `.chat-body` 的
  click，`closest('.cite-chip')` 取 `data-cite`，再用 `closest('.msg')` 的
  `data-msg-index` 定位是哪条消息的 sources。
- 右侧抽屉展示：《文档名》 + 第 N 块 + 相似度 + 片段原文（`white-space: pre-wrap`）。

### 4.3 已知限制

`messages` 表没有地方存 sources（加列同样牵动 ALTER），所以**只对本次回答提供溯源**；
刷新页面后历史消息只剩纯文本 `[来源N]`，点击会提示「历史消息不回传来源」。

测试：`tests/test_citation_sources.py` 9 例（标号连续性、字段完整性、空召回、异常降级、

## 任务 5：PDF 跨页表格表头回填（尽力局）

### 5.1 判定条件（四个同时成立才回填）

`app/rag/loader.py` 在页循环里维护 `prev_header` / `prev_ended_at_bottom`：

1. 上一页最后一张表的底边 ≥ 页面高度 × **0.78**（视为被页尾截断）；
2. 本页第一张表的顶边 ≤ **100pt**（视为从页首继续）；
3. 本页首行与上一页表头**不等价**（等价说明续页自己重复了表头，不必再插）；
4. 列数一致 **且** 首行含数字（数据行特征；表头通常是纯文字）。

满足则 `rows = [prev_header] + rows`，再走原有 `_table_to_markdown` 生成
「表头 + 分隔线 + 数据」。

### 5.2 为什么用「页面高度比例」而不是固定留白

实测（`samples/demo_docs/generated/跨页销售明细表.pdf`，A4 842pt）：

| 页 | 表格 bbox | 距页底 | 首行 |
|---|---|---|---|
| 第 1 页 | top=51.0, bottom=**725.7** | 116.2pt | `Channel / Q1 / Q2`（表头） |
| 第 2 页 | top=**28.4**, bottom=87.9 | 753.5pt | `CH-033 / 1033 / 2033`（**纯数据**） |

第一版阈值是「距页底 < 80pt」，按这份真实 PDF **会漏判**（116 > 80）——表格因为
「下一行放不下」而换页，留白取决于行高与页脚，不是固定值。改成比例阈值 0.78
（842×0.78 = 657）后稳定命中。这就是本任务「尽力局」的核心结论：
**判据不能写死绝对留白，要相对于页面尺寸。**

### 5.3 局限性（如实说明）

1. **没有表头的原始表格会被把首行当表头**（存量问题，本批未动）：若第一页表格本身
   就没有表头，`prev_header` 记的是首行数据，续页会把它当表头插回去。
2. **跨页续页自带不同措辞的表头**会被插成双表头（`_same_row` 只认完全一致）。
3. **pdfplumber 未把跨页表格识别成两张表**（例如无 ruling lines 的纯文本表格）时，
   本逻辑无从介入——那类 PDF 连 Markdown 表格都抽不出来。
4. 阈值是通过实测标定的启发式，遇到特殊版式（表格止于页面下部 + 下一页顶部恰有
   另一张同列数无表头表）会误判。设计上宁可多一行表头，也不要出现无列名的裸数据。

### 5.4 测试

`tests/test_pdf_cross_page_table.py` 9 例：用假 pdfplumber 模块精确控制 5 种判定分支
（回填 / 自带表头 / 未被截断 / 不贴页首 / 列数不符 / 首行无数字 / 单页不变 / 中间夹正文后
状态复位）+ 1 例真实 PDF 端到端。样本可用 `scripts/gen_cross_page_pdf.py` 重建。

## 顺带修复：测试隔离 `data/system_config.json`（封版隐患）

**现象**：本批第一次跑全量时 2 个用例变红，而这 2 个用例与本批改动毫无关系：

```
tests/test_llm_factory.py::...::test_default_is_mock_in_test_env   FAILED
tests/test_retry.py::test_retry_exhausted                          assert 3 == 2
```

**根因**：22:28 有人在配置页点了一次保存，`data/system_config.json` 变成 11 项覆盖
（含 `llm_provider=openai`、`tool_max_attempts=3`）。而 `runtime_config._overrides` 是
进程级缓存、默认直接读项目根目录这个文件 —— 于是**线上配置漏进了测试**，两个用例
分别被 `llm_provider` 和 `tool_max_attempts` 污染。代码没动、测试却红，是最难排查的一类。

**修法**（`tests/conftest.py`，autouse）：

```python
@pytest.fixture(autouse=True)
def _isolate_runtime_config(tmp_path, monkeypatch):
    monkeypatch.setenv("SYSTEM_CONFIG_FILE", str(tmp_path / "system_config.json"))
    runtime_config.reset_cache()
    yield
    runtime_config.reset_cache()
```

顺带收益：以后任何用例即使忘记设 `SYSTEM_CONFIG_FILE`，`update_config` 也只会写到
tmp 目录，不会再把测试数据写进生产配置文件。
