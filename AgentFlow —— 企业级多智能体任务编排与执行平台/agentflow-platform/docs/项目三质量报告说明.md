## 四、面试绝杀话术

> **问：多智能体项目为什么不能只靠"人工点几下"？你怎么保证复杂状态机不崩溃？**

"人工测试有两个致命盲区：**触发不了故障，也复现不了时序**。我这套系统里最危险的路径——锁竞争、快照覆盖、管道超限——没有一条是'点几下'能碰到的，它们只在并发窗口、大响应、三方库边界条件下出现。所以我的答案是：**把故障变成测试夹具，让每个 bug 都能被一条命令重新拉出来。**

具体三层打法：

第一层，**并发和时序用假环境精确制导**。整套 715 个用例跑在内存 SQLite + fakeredis 上，8 秒跑完还全绿——不是为了让测试快，而是为了让'锁竞争'这种概率性故障可以被确定性复现：两个请求同时 resume 同一个任务，在真实环境里可能一千次才撞上一次，在夹具里我安排它们必然撞上，然后验证分布式锁让后到者拿到 TASK_LOCKED 而不是把状态机写花。

第二层，**大模型的不确定性用'坏输入'枚举**。LLM 输出截断、带 markdown 围栏、括号残缺——我把这些坏样本全部固化成用例，验证结构化修复器能补全括号、剥围栏、多级重试后降级，而不是抛异常炸掉执行图。最狠的是三方库 checkpoint key 错位那个 bug：每次保存覆盖上次快照、interrupt 信息全丢、任务被误判 FAILED，而且 InMemory 测试环境完全复现不了——它教会我**测试基建必须和生产同构**，所以现在连 64KB 管道超限这种传输层问题，我都是 spawn 真实子进程灌 200KB 数据去验证的，全 suite 最慢的三个用例就是它们——**用真实开销换真实信心**。

第三层，**每个历史事故都是一条回归用例**。kb-search 超时全灭、MCP 数值变字符串、SQL 修复循环丢列名——每次排完障我都会把故障场景写成测试钉死。715 个用例里相当一部分不是'测功能'，是'测事故不会复发'。所以这套系统敢说自己不崩溃，不是因为代码写得漂亮，而是因为它已知会怎么崩——**并且每次崩法都有测试在岗盯着**。"
