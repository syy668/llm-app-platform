# 任务 9：极限成本防御总结（v2.2）

> 一句话版本（可直接用于简历/述职）：
> **为多智能体平台补上最后两道成本与稳定性防线——基于 Redis 的单任务 Token 硬熔断（防重试风暴烧穿预算，超限立即中断执行图并落库错误码）与 LLM 调用级双重防御（生成上限 2048 Token 防输出爆炸 + asyncio 硬超时防 API 挂起卡死），全部拦截点设在客户端门面层，11 项新测试、全量 588 项测试零失败，核心链路零重构。**

## 背景

系统已有工具重试（3 次）、解析修复重试（2 次）、主备模型降级等多层容错。但复盘发现两个极端场景隐患：

1. **重试风暴**：模型陷入"报错→反思→重报错"死循环时，单任务可消耗数十万 Token，瞬间烧穿用户日配额；
2. **输出爆炸 / API 挂起**：长文本失控生成引发 OOM 风险，或 API 挂起导致节点卡死。

## 改进 1：单任务 Token 消耗硬熔断

- **记账**：`LLMClient`（主备门面，所有 LLM 调用的唯一咽喉）每次响应返回后，立即对 Redis 键 `task:token_usage:{task_id}` `INCRBY` 本次消耗（prompt+completion），TTL 24 小时。
- **拦截**：每次请求**前**预检累计值，达到 `MAX_TOKENS_PER_TASK=50000`（可配置）即抛 `TokenBudgetExceededError`（`AppException` 家族，429），强制中断执行图。
- **闭环**：任务以 `FAILED(TOKEN_BUDGET_EXCEEDED)` 落库，错误信息完整保留。
- **安全性设计**：
  - task_id 来自任务 7 的 ContextVar 注入，**调用方零改动**；未绑定场景（离线/评测）自动跳过；
  - 熔断异常继承 `AppException` 而非 `LLMError`——刻意绕过主备降级逻辑，**不会**触发备用模型重试；
  - executor 节点的宽泛异常兜底为它加了放行分支，熔断可穿透到图级处理，不会被吞掉后继续跑后续子任务；
  - Redis 故障 fail-open：只留 warning 日志，绝不因计数器故障阻断业务。

## 改进 2：Output 爆炸与硬超时防御

- **生成上限**：`LLM_MAX_TOKENS` 默认值收紧为 2048（.env 可覆盖），每次请求 payload 强制携带，杜绝无限生成。
- **硬性总超时**：`LLMClient.complete` 外层包 `asyncio.wait_for`（默认 30s，可配置），主/备两条路径各自生效；超时转 `LLMError(LLM_TIMEOUT)`。实现沿用加固任务 2 踩坑后的安全模式（先捕获再在 try 外处理，规避 Python 3.13 `wait_for` 与取消簿记的冲突）。

## 测试证据

- 新增 11 项：累计记账+TTL、**第 N 次调用精确拦截且不再发真实请求**、预检先于请求（Redis 已超限时桩客户端 0 次调用）、无绑定跳过、Redis 故障 fail-open、备用路径同样记账、熔断不触发降级、主/备硬超时、max_tokens 强制携带（payload 捕获验证）；
- 全量回归 **588 passed / 0 failed**（577 基线 + 11），ruff 通过。

## 运维提醒

- **生产环境部署时，请务必确认 `.env` 中的 `LLM_MAX_TOKENS` 未被错误放大，系统启动时会自动进行安全阈值校验**（`LLM_MAX_TOKENS > 4096` 或 `MAX_TOKENS_PER_TASK > 100000` 会在启动日志打出一行 `[安全警告]`，配置正常则打印 `[启动自检] Token 成本控制配置正常。`）。
- 本机 `.env` 与 `.env.example` 已同步修正为 `LLM_MAX_TOKENS=2048`（此前为 8192，曾导致防御机制在真实运行时失效）。
- 单任务阈值 `MAX_TOKENS_PER_TASK` 可在 `.env` 中按业务调低/调高；设为 0 可整体关闭该熔断。
- 与既有日配额（用户维度/天级）形成双层防护：**日配额防合法频率下的累计烧钱，本补丁防单任务内的失控循环**。
