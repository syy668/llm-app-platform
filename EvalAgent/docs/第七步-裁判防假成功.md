# 第七步：裁判「防假成功」两道防线

> 2026-10-26 交付。起因：kimi-k3 完美穿过旧探活（只发「回复两个字：就绪」），
> 真实评测却每条样本都解析不出 RAGAS 要的 JSON，四项指标全空 —— 一整轮跑完才判失败，钱白烧、人也白等。
>
> 现在两道防线：**保存前拦（结构探活）** + **执行中拦（空指标熔断）**，文案统一，不给人留猜的空间。
>
> 验证：换成 `qwen3.8-flash` 后真跑 7 条样本 → `7/7 ok`，四项指标全部非空（见第五节）。

---

## 一、问题本质：能聊天 ≠ 能吐结构化 JSON

RAGAS 的四项指标不是问模型「打几分」，而是每个指标各发一套**带特定输出契约**的 prompt，
再由 ragas 侧解析 JSON / 列表结构。所以：

| 模型能力 | 旧探活（"回复两个字：就绪"） | 真实评测 |
|---|---|---|
| 能聊天，不会按契约输出 JSON | ✅ 通过（假成功） | ❌ 每条样本解析失败 → 四项全空 |
| 能聊天，输出被 max_tokens 截断 | ✅ 通过 | ❌ 解析失败 |
| 正常 | ✅ 通过 | ✅ 有分 |

kimi-k3 落在第一行。**探活必须探"结构"，不能只探"连通"** —— 这是本次补强的全部理由。

## 二、防线一：结构探活（`judge.preflight`）

### 探活的提示词

```python
_STRUCTURED_PROBE = (
    "你是 RAG 评测裁判。请判断【回答】是否完全由【上下文】支持。\n"
    "严格只输出一个 JSON 对象，不要 markdown 代码块、不要任何解释文字：\n"
    '{"faithfulness": 0 到 1 之间的小数, "reason": "一句话理由"}\n\n'
    "【上下文】2026 年第三季度华东区销售额为 1200 万元。\n"
    "【回答】2026 年第三季度华东区销售额为 1200 万元。"
)
```

为什么是「带上下文的判断题 + 强制 JSON」而不是随便问一句：

1. 复刻 RAGAS 的真实工作形态（给上下文、要求打分），不是闲聊；
2. 强制 JSON **且**要求 0~1 数值位 —— 只回"忠实"不够，rags 侧要的是数字；
3. 上下文与回答完全一致（答案应该是接近 1.0），**内容足够简单**，失败只能是「格式不行」，
   不会因为"题太难答错"而误判。

### 三档判定（分开才能排障）

```python
content = str(getattr(out, "content", "") or "")
if not content.strip():
    raise JudgeUnavailable("裁判模型返回空 content（大概率是思考模式未关闭，或 max_tokens 被 reasoning 吃光）")

parsed = _extract_json_object(content)
if parsed is None:
    raise JudgeUnavailable(f"{STRUCTURED_OUTPUT_UNSUPPORTED}（模型有返回内容，但解析不出 JSON；"
                           f"返回片段：{content.strip()[:120]}）")
if not _has_probability(parsed):
    raise JudgeUnavailable(f"{STRUCTURED_OUTPUT_UNSUPPORTED}（JSON 里没有 0~1 的数值字段；"
                           f"返回：{str(parsed)[:120]}）")
```

其中 `STRUCTURED_OUTPUT_UNSUPPORTED = "该模型不支持 RAGAS 结构化输出，请更换模型"`。

| 档 | 触发 | 文案指向 |
|---|---|---|
| 1 | 调用异常 / content 为空 | 思考模式 / 额度 / key —— **不要**误导用户换模型 |
| 2 | 有内容但解析不出 JSON | **换模型**（本次 kimi 的场景） |
| 3 | JSON 可解析但没有 0~1 数值 | **换模型**（"形似"型选手） |

### 解析容错：模型爱干的三件事

`_extract_json_object()` 三级兜底，实测覆盖真实输出：

1. 整串就是 JSON（理想情况）；
2. 包了 ` ```json ` 围栏 → 剥掉再解；
3. 前面加了"好的，结果如下："、后面补了一段解释 → `json.JSONDecoder().raw_decode()`
   从第一个 `{` 起增量解析（自动忽略尾部多余内容，`{"a":1}{"b":2}` 也能拿到第一个）。

配套 `_has_probability()` 有个细节：**bool 必须排除** —— `True` 能被 `float()` 转成 `1.0`，
不排的话 `{"ok": true}` 会被判成"有分数"，又是一次静默假成功。

### 保存即探活，不通过不落库

`PUT /system/judge-config` 的流程没变，只是 `preflight(candidate)` 变严了：
候选配置 → 结构探活 → 失败返回 **422**（`探活失败，配置未保存：该模型不支持 RAGAS 结构化输出，请更换模型`）→ 不写库。
单测 `test_preflight*` 锁的就是这条：**探活失败绝不允许配置生效**。

`POST /system/judge-config/preflight`（只读探活）也同步升级，返回 `message="结构探活通过（JSON 可解析）"`。

## 三、防线二：空指标熔断（执行器）

结构探活只能拦"保存前已知不兼容"。还有两种漏网：
模型更新后行为变了、RAGAS 内部 prompt 与探活 prompt 不完全一致。
所以执行侧要有兜底。

### 连续 N 条全空 → 判定不兼容，立刻收尾

```python
if row.status == SCORE_FAILED and (row.error_msg or "").startswith("指标全空"):
    empty_streak += 1
    if empty_streak >= settings.RUN_EMPTY_METRIC_STREAK_LIMIT and pending:
        await _cancel_tasks(tasks)            # 剩下还在跑的打分任务全部取消
        for rest in items:                    # 没跑的样本留痕，别让审计以为"样本丢了"
            if rest.id in pending:
                db.add(_build_score_row(run_id, rest, ..., None, "裁判模型未返回有效解析结果，任务提前终止"))
                run.skipped_items += 1
                run.processed_items += 1
        _mark_failed(db, run, EMPTY_METRIC_ABORT_MSG)
        return
else:
    empty_streak = 0                          # 中间有一条成功就清零（偶发失败不判死）
```

`RUN_EMPTY_METRIC_STREAK_LIMIT = 3`：单条偶然解析失败（输出被截断）不该判死整轮，
但连续三条空必然不是偶然。

### 三条文案统一（同一个病，一种说法）

```python
# runner.py
EMPTY_METRIC_ABORT_MSG = "裁判模型未返回有效解析结果，请检查模型兼容性"
```

三处共用：

| 触发点 | 场景 |
|---|---|
| `judge.preflight` | 保存配置时（`STRUCTURED_OUTPUT_UNSUPPORTED`） |
| 执行中熔断 | 连续 3 条全空 |
| `_finalize` 零成功 | 样本数 < 阈值，整轮跑完才归零 |

`_finalize` 里还做了一次归因区分：

```python
judge_incompatible = any(r.status == SCORE_FAILED and (r.error_msg or "").startswith("指标全空") for r in rows)
run.error_msg = EMPTY_METRIC_ABORT_MSG if judge_incompatible else "全部样本未产出有效指标（请查裁判配置与上游可用性）"
```

裁判吐不出 JSON 和上游没取到答案都是「零成功」，但**责任方不同**，文案不能一样 —— 否则运维第一反应会去查知识库。

### 一个诚实的边界：熔断做不到"一条都不多跑"

并发闸是信号量，一条样本结束的瞬间，在途的下一条立刻拿到许可并启动（线程已在跑，`cancel()` 取消不掉）。
实测 6 条样本、阈值 3 的情况下，裁判被调用了 **3~4 次**（多跑 1 条在途）。

价值不在"零浪费"，而在"不再把剩下全部跑完"：7 条样本 × 每条约 5 次 LLM 调用，原来要烧 35 次，
现在 3~4 条打住。测试 `test_empty_metric_streak_aborts_early_and_stops_burning_tokens` 锁的就是这个上界。

## 四、顺带修掉的口径 bug：详情页显示的裁判模型是错的

截图时发现：实际用 `qwen3.8-flash` 打的分，详情页却显示「评测模型：deepseek-v4.1-flash」。

根因：两处取的是 `.env` 默认值，而不是**生效配置**：

```python
# runs.py::create_run —— 修复前
evaluator_config=payload.evaluator_config or {"judge_model": settings.JUDGE_MODEL},
# 修复后
evaluator_config=payload.evaluator_config or {"judge_model": build_judge_config().model},
```

```python
# runner.py::_finalize —— 修复前
"judge_model": settings.JUDGE_MODEL,
# 修复后
"judge_model": build_judge_config().model,
```

优先级是 `runtime_configs` > `.env` > 默认值。管理员在界面改过模型后 `.env` 就是旧值，
快照写错 = **详情页撒谎**（"用 A 模型打的分，实际是 B"）。这类口径错误比字段缺失更糟：
审计的人会据此得出完全相反的结论。

## 九、运维口径：看到"空分"该怎么查（3 步）

1. **先点「探活」**：`ok=false` 且提示"不支持 RAGAS 结构化输出" → 直接换模型，别再往下查。
2. **看任务前 3 条明细的 `error_msg`**：
   - `指标全空：裁判未返回可解析结果` → 兼容性（探活漏网 / 模型行为变了）；
   - `上游未召回任何上下文` / `上游调用失败` → 项目一 8010 的问题，别甩锅裁判；
   - `打分超时（>300s）` → 单条太慢（`JUDGE_ITEM_TIMEOUT`），先看裁判 qps/网络。
3. **看 `run.error_msg` 是否为统一文案** `裁判模型未返回有效解析结果，请检查模型兼容性`
   —— 是则整轮都被判定为裁判不兼容（要么熔断、要么零成功）。

## 十、仍然存在的边界

1. **探活 ≠ 全量兼容性证明**。探活用的是简化 prompt，RAGAS 内部 4 个指标的 prompt 更复杂；
   模型可能"探活过、某些指标仍解析失败"。所以熔断必须存在（这就是两道防线而不是一道的原因）。
2. **熔断阈值是全局配置**，不按模型区分。若某个模型天然有约 30% 单条解析失败率，
   连续三条全空的概率仍不低，会被判死 —— 需要时把 `RUN_EMPTY_METRIC_STREAK_LIMIT` 调到 5。
3. `POST /eval/runs` / `DELETE /eval/runs/{id}` 的鉴权缺口仍在（见 `第六步` 第八节，高危）。
