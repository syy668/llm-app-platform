## 五、核心链路

### 1. Agent 六节点图
```
START → classify ─┬─ rag ──────────────┐
                  ├─ db_query ─────────┤
                  ├─ parallel_compare ─┼→ answer → END
                  ├─ (direct) ─────────┘
                  └─ report ─────────────────────→ END（不走 LLM）
```
- 路由由 LLM function_calling 判定（`RouteDecision` 5 路），失败回退 `direct`
- `parallel_compare`：先 LLM 拆两个检索词 → `ThreadPoolExecutor(max_workers=2)` 并行两路 rag_retrieve → 合并「资料A/B」→ answer 出对比结论；单路失败不阻断
- `report`：`report_tool` 生成 Markdown 报表落 messages，报表中心可预览/下载
- 全链路写 `trace_logs` + `trace_tool_calls`（`core/tracing.py` 挂 on_chain_start/end）

### 2. RAG 检索
上传 → loader 解析 → splitter 分块 → embeddings → Chroma + MySQL 双写
提问 → 向量 top_k 召回 + BM25 召回 → RRF(k=60) 融合 → （`rerank_threshold>0` 时）余弦重排 + 阈值过滤 → 上下文拼 prompt → LLM 生成 + sources 引用

### 3. 评测
dataset → `POST /eval/runs` 异步线程跑 → 逐样本 answer + 召回 → ragas 4 指标 → 批量落库；支持并发（默认上限 4）、样本级重试、`rag_config` 请求级实验参数、分层指标、badcases、CSV 导出、批次对比。

## 八、已知问题与风险（本次核查新发现，按严重度排序）

### A【中危·安全】禁用用户不会掉线，角色变更不生效 —— ✅ 已修复（2026-10-23 批次1）
- **现象**：`DELETE /users/{id}` 是软删除（`status=disabled`），登录时确实拦（`auth_service.py:27`），但**已登录会话不受影响**。
- **根因**：`api/deps.py:41-57` 的 `get_current_user` 只读 Redis 里缓存的 user 快照（含 role/status），从不回查数据库，且**完全没有校验 status**；`core/security.py:88` 每次访问都 `expire` 滑动续期 → 只要持续使用，token 永不过期。
- **后果**：管理员禁用某员工后，对方仍可无限期使用全部接口；降级 admin 为 user 同样要到会话自然过期（实则可能永不）才生效。
- **修复**（`app/api/deps.py`）：新增 `_load_user_state`，每请求按主键单行投影回查 `id/username/display_name/role/status`；账号不存在或 `status != active` → `delete_session` 清会话 + 401；角色以 DB 为准，降级/升权立即生效。实测单次 0.32ms，未加 TTL 缓存（与「下一次请求立刻失效」口径冲突）。
- **验证**：`tests/test_auth_revocation.py` 11 例，其中 6 例在旧逻辑下必然失败；全量 pytest 161 passed。

### B【中危·一致性】`LLM_PROVIDER` 双轨：配置页切了，会话链路不认 —— ✅ 已修复（2026-10-23 批次2）
- **现象**：系统配置页/`.env` 可切 `mock|openai|anthropic`，但只有 `POST /kbs/{id}/query`（`rag/llm.py:27`）读它；**Agent 会话链路 `agent/llm.py` 恒构造 `ChatOpenAI`**，完全不读 provider。
- **后果**：当时配置文件是 `llm_model=deepseek-ai/DeepSeek-V3 @ 硅基流动` + `LLM_PROVIDER=mock`，于是会话问答打真实 API、知识库问答回显假答案，同一系统两套口径。
- **修复**：新建 `app/llm/`（`factory.py` + `mock.py`），三条 LLM 调用路径（Agent 图 / 知识库问答 / RAGAS judge）全部收敛到 `get_chat_model()` / `generate_text()`；删除 `app/agent/llm.py`。mock 模式下返回 `MockChatModel`（LangChain BaseChatModel 实现，支持 invoke / stream / with_structured_output），离线与 CI 均可跑通。
- **验证**：`tests/test_llm_factory.py` 42 例（含「禁止绕过工厂」架构守卫）；全量 pytest 203 passed。
- **注意**：`.env` 当前 `LLM_PROVIDER=mock`，修复后**会话也走 mock**（这是配置生效的正确结果）。要看真实大模型回答，在「系统配置」页把 provider 切到 openai（现有配置指向硅基流动 DeepSeek-V3，实测可用）。

### C【中危·部署】`FAKE_REDIS=true` 但本机真实 Redis 就在跑 —— ✅ 已修复（2026-10-23 批次3）
- 影响面：① 登录态全在进程内存 → **后端一重启所有人被踢下线**；② refresh 黑名单不跨进程，logout 无法真正吊销；③ `rate_limit.py:56-61` 在 fake 模式下**直接跳过限流**（AI 问答无限流保护）；④ 多 worker/多实例部署下会话完全失效。
- **修复**：`.env` 改 `FAKE_REDIS=false` 并显式加 `AI_RATE_LIMIT_PER_MINUTE=30`；`core/redis.py` 补 `socket_connect_timeout=2s / socket_timeout=5s / health_check_interval=30s`，Redis 挂掉时快速失败而不是把请求挂死；`get_redis()` 增加「运行期 FAKE_REDIS 变更 → 自动重建句柄」的一致性校验（否则可能"配置写 real、句柄还是 fake"导致限流静默失效）；启动日志明确播报后端类型。
- **顺带补的真缺口**：`POST /kbs/{id}/query` 此前**完全没有限流**——只有会话问答受限，而这个接口才是显式消耗「向量检索 + LLM 生成」的高成本入口，现已挂 `rate_limit_ai`。
- **验证**：`tests/test_rate_limit_enforcement.py` 10 例（真实 Redis db=15 隔离，无 Redis 环境自动 skip）；在线脚本 `scripts/probe_rate_limit.py` 实测：`/kbs/6/query` 上限 3/分钟时第 4 次返回 `HTTP 429 code=429 请求过于频繁，请稍后重试`。全量 pytest 213 passed。

### D【低危·可观测】健康检查的 redis 字段在 fake 模式下恒 ok —— ✅ 已修复（2026-10-23 批次3）
`GET /health` 原取 `ping_redis()`，fake 模式 ping 的永远是内存实例 → 真实 Redis 挂了也报 ok。现已新增 `redis_backend`（`real`/`fake`）与 `rate_limit`（`enabled`/`disabled`/`degraded`）两个字段，保留原有 `status/db/redis` 以兼容既有脚本与文档；fake 模式下 `redis_backend=fake, rate_limit=disabled` 一眼可辨。

### E【待确认·业务】RAGAS 基准达标结论缺位
