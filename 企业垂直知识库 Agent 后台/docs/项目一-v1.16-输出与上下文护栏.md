# 项目一 v1.16：输出端硬限制 + 历史窗口（两项静默故障的工程级护栏）

> 触发：Token 限额梳理时定位到两个「不会报错、但会在生产上出事」的缺口。
> 本文只记录这两件事：**输出被截断却当成成功**、**上下文无界膨胀且被失败消息污染**。

## 一、问题定性：两个「静默故障」

| # | 现象 | 为什么危险 |
|---|---|---|
| 1 | 输出不设 `max_tokens`，且从不看 `finish_reason` | 命中上限时上游返回 **HTTP 200 + `finish_reason=length`**，正文在半句处断掉。系统把它当「完整回答」落库、渲染、进报表。事后排查：trace 里只有一次成功的 LLM 调用，没有任何异常记录。 |
| 2 | 历史 `.all()` 全量拼接，且不看 `status` | ① 长会话 prompt 随轮数线性增长，成本与首字延迟双失控，最终撞上下文窗口直接 500；② `failed` 消息的正文是「余额不足/未返回内容」这类错误文案，被当成 AI 上一轮回复喂回模型 —— 等于教模型顺着错误话术继续编。 |

关键判断：**两个都是配置/逻辑缺失，不是模型能力问题**。加参数、加检查即可，无需换模型。

## 二、改造 1：输出端硬限制与截断感知

### 2.1 限制下发（`app/llm/factory.py`）

```python
# config.py
self.llm_max_tokens: int = max(64, min(32768, _int("LLM_MAX_TOKENS", 2048)))

# factory.py::_create_model
ChatOpenAI(..., max_tokens=max_tokens, extra_body=_dashscope_extra_body(api_base))
ChatAnthropic(..., max_tokens=max_tokens)
```

三处细节：

1. **必须显式传**。不传时上限由上游默认值决定，各家差异极大 —— `ChatAnthropic` 默认只有 **1024**，比本系统常见回答还短，等于「默认就在截断」。
2. **`max_tokens` 进了缓存签名**。配置指纹变化即重建客户端，改 `.env` 重启后立刻生效，不会被旧缓存实例带走。
3. **`mock` 不传**（规则模型无 token 概念），但签名一致，不破坏既有离线测试。

### 2.2 截断识别（新增 `app/llm/truncation.py`）

单一判定源，避免三处各写一遍字符串：

| 来源 | 字段 | 截断值 |
|---|---|---|
| ChatOpenAI 兼容（DeepSeek/硅基流动/百炼/魔搭） | `response_metadata.finish_reason` | `length` |
| ChatAnthropic | `response_metadata.stop_reason` | `max_tokens` |
| 部分自建网关 | `generation_info.finish_reason` | `length` |

- `is_truncated_message(msg)`：业务侧拿到的 `AIMessage`
- `is_truncated_result(llm_result)`：Trace 回调拿到的 `LLMResult`（batch 下任一条截断即 True）
- `TRUNCATION_NOTICE`：提示文案**只此一份**，后端追加、SSE 下发都用它，前端不硬编码

### 2.3 三处接入

| 位置 | 行为 |
|---|---|
| `agent/graph.py::answer_node` | 判定后 `final_answer = append_notice(...)` 并回写 `state["truncated"]`；提示进**最终文本**，刷新后仍可见 |
| `services/stream_service.py` | SSE `delta` 已逐字推给前端，提示不能混进 delta（会重复），改由 `done` 事件下发 `truncated` + `truncation_notice`；落库正文仍带提示 |
| `llm/factory.py::generate_text` | `/kbs/{id}/query` 链路同口径追加（返回类型仍是 `str`，不动任何调用点） |
| `core/tracing.py::on_llm_end` | 观测层独立采集，`flush` 写 `trace_logs.is_truncated` |
| `models/trace_log.py` | 新增列 `is_truncated BOOLEAN NOT NULL DEFAULT 0` |

### 2.4 实测（2026-10-24，百炼 qwen3.7-plus，OpenAI 兼容端点）

| 场景 | completion_tokens | finish_reason | 正文字符 | is_truncated | 提示 |
|---|---|---|---|---|---|
| `max_tokens=64` | 64 | `length` | 139 | True | 已追加（`...以下是对 RAG 全流程` 后直接接提示） |
| `max_tokens=2048`（默认） | 2048 | `length` | 4033 | True | 已追加 |
| 端到端 `agent_service.chat` | 2048（+classify 19 = 聚合 2067） | `length` | 3859 | True（DB 布尔列） | 落库正文末尾一致 |

**结论**：默认 2048 对「详细讲解/长报表」类问题**会撞顶**。这不是 bug，是刻意的成本上限 —— 现在它会显式告诉用户「没说完」，而不是假装说完了。需要长文时调 `LLM_MAX_TOKENS`。

## 三、改造 2：历史滑动窗口 + 状态过滤

### 3.1 从 `.all()` 到「SQL 过滤 + 双预算」（`app/services/agent_service.py`）

```python
rows = (
    db.query(Message)
    .filter(Message.conversation_id == conversation_id)
    .filter(Message.role.in_(("user", "assistant")))
    .filter(or_(Message.role == "user", Message.status == MSG_DONE))  # 状态过滤
    .order_by(Message.id.desc())
    .limit(max_turns * 2 + 1)                                         # SQL 层先裁
    .all()
)
rows.reverse()
rows = _trim_to_turns(rows, max_turns)   # 轮数窗口
rows = _trim_to_chars(rows, max_chars)   # 字符预算
```

四个设计决定：

1. **状态过滤放在 SQL 里**。`user` 提问一律保留（提问总是有效的），`assistant` 只认 `done`；`failed`/`running` 的正文都不是「已完成的回答」。
   > 注：需求文档写的是 `status='success'`，本项目消息表的真实枚举是 **`done`/`failed`/`running`**（`app/models/message.py`），实现按真实值取 `MSG_DONE`。
2. **`limit(max_turns*2+1)` 而不是全量拉回再筛**。`+1` 是容错：末轮可能只有提问、回答还没落库。
3. **轮数以 `user` 消息为边界**从后往前数。不按「条数 / 2」硬算，避免「末轮只有提问」时算错一轮。
4. **字符预算与轮数预算并存**。5 轮不代表可控 —— 用户粘一份 8000 字文档进来，5 轮就是 4 万字符。两个维度必须同时封顶，缺一个就漏。

### 3.2 丢弃顺序：从最早开始，且不留悬空 assistant

- 超预算时从**最早**的消息开始丢，保留最近的上下文；
- 丢完后若开头剩一条 `assistant`（它的提问已被丢掉），一并移除 —— 一条没有对应提问的 AI 发言会让模型误以为「这是我说过的话」，反而更容易被带偏。

### 3.3 意图继承不受窗口影响

`last_assistant_route(history)` 换成独立单行查询 `latest_assistant_route(db, conversation_id)`：

窗口会过滤 `failed`、也会被预算截断，而「上一轮真实路由」必须与窗口无关。否则同一个追问在长会话里会突然不继承了 —— 这类「行为随会话长度变化」的 bug 最难查。旧函数保留（有单测直接调用），仅标注非主链路。

### 3.4 流式链路同步

`stream_service.stream_chat` 原本同样 `.all()` 全量，已改为调用同一个 `load_history_window`。两条链路口径一致，不存在「流式会话更贵」的偏差。

## 四、升级步骤（存量库）

`create_all` 只补缺失表、**不补列**；`trace_logs` 由 `ensure_trace_tables()` 建，存量库需要手工执行：

```sql
ALTER TABLE trace_logs
  ADD COLUMN is_truncated TINYINT(1) NOT NULL DEFAULT 0
  COMMENT '回答是否被 max_tokens 截断' AFTER total_tokens;
```

未执行时 `SCHEMA_CHECK_MODE=strict` 会在启动期直接抛 `SchemaDriftError` 并打印该语句（fail fast，避免半路 500）。
新建库无需处理：ORM 建表已含该列。

## 五、配置项

| 变量 | 默认 | 说明 |
|---|---|---|
| `LLM_MAX_TOKENS` | 2048 | 单次回答输出上限（64~32768）。同时也是成本封顶 |
| `CHAT_HISTORY_MAX_TURNS` | 5 | 送入上下文的历史轮数（1~50） |
| `CHAT_HISTORY_MAX_CHARS` | 2000 | 历史字符总预算（200~50000），超预算丢最早 |

三者都在 `.env`，改完重启生效（属于进程级配置，不进配置面板 —— 与分块/检索参数同级）。

## 七、遗留

1. **截断率大盘未做前端展示**。`is_truncated` 已在表里，`/traces` 接口尚未暴露该字段；建议后续在 Trace 列表加「截断」筛选，用真实截断率反推 `LLM_MAX_TOKENS` 该设多大，而不是拍脑袋。
2. **历史窗口是「按条丢弃」，不是「按语义摘要」**。更优解是超长历史做滚动摘要（用小模型压成一段），但会引入额外调用与延迟，当前阶段收益不划算。
3. **`/kbs/{id}/query` 无 Trace**。该链路不走 `TraceCallbackHandler`，截断只在日志里可见，没进 `trace_logs`。要么补 trace，要么该链路后续下线。

## 附录：面试话术 —— 把这两处讲成「高可用与成本控制」的架构亮点

### 一句话版本（20 秒）

> 我给大模型调用加了两道监控发现不了的护栏：一道让「截断」从成功里分出来，一道让上下文从「有多少传多少」变成有界状态。

### 结构版本（90 秒，推荐）

**背景**：做 token 成本核算时，我把一次问答的输入输出逐层拆开看，发现两个缺口。它们的共同点是——**HTTP 200，监控全绿，结果是错的**。

**冲突（关键在这里）**：
- 输出侧：`max_tokens` 没设、`finish_reason` 没人看。上游把回答截断了照样返回 200，正文在半句处断掉，我们把它当完整回答落库、渲染、甚至进报表。事后查 trace，只有一次"成功"的 LLM 调用，没有任何异常。**这是最难查的一类故障：它不是失败，是残缺的成功。**
- 输入侧：历史是 `SELECT *` 全量拼进 prompt，也不看消息状态。前者让成本随会话长度线性涨，后者把"账户余额不足"这种错误文案当成 AI 上一轮说过的话喂回去 —— 等于给模型做了一次错误的 few-shot。

**动作（三条设计原则，比功能本身重要）**：
1. **上限必须配感知**。设 `max_tokens` 只是造了一条边界，边界被撞到必须能识别。所以我把各厂商的截断信号归一（OpenAI 的 `finish_reason=length`、Anthropic 的 `stop_reason=max_tokens`、部分网关放在 `generation_info`），然后在三个层面落地：用户看到提示、前端收到事件、trace 落一个布尔位。
2. **观测层不信任业务层**。截断判定我写了两遍——answer 节点决定"要不要告诉用户"，trace 回调决定"事实是什么"。故意冗余：观测不能依赖"这次业务代码没写错"，否则观测和真相一起失效。
3. **上下文是成本函数，不是数据结构**。所以做**双预算**：轮数防线性增长，字符防单点爆炸（用户粘一份 8000 字文档进来，5 轮就是 4 万字）。丢弃时从最早丢，并且清掉"提问已被丢掉"的孤立 AI 回复——否则模型会把那条发言当成自己说过的，反而更容易被带偏。

**量化**：全量 511 个测试通过，新增 28 个专测这两条护栏；实测 2048 tokens 时模型输出 4033 字符撞顶，`finish_reason=length` 被正确捕获，端到端 `trace.is_truncated=true`；输入侧从此有硬上限（≤5 轮且 ≤2000 字），不再随会话长度增长。

**反思（收尾金句）**：
> 这两个问题的共同点是「默认值不可见」。`max_tokens` 各家默认不同（Anthropic 默认只有 1024），历史长度根本没有默认上限，错误状态没人过滤。我的结论是：**凡是把不确定性交给上游默认值的地方，都要显式化，并且给这个显式值配一个可观测信号**——否则你只是把风险挪了个位置。

### 追问预判（面试官大概率会问）

| 追问 | 答法 |
|---|---|
| 2048 这个数怎么定的？ | 不是拍脑袋，是"典型回答 P95 × 1.5"起步。更重要的是：现在有 `is_truncated` 字段了，下一步用真实截断率反推这个值，而不是继续猜。**配置项要有数据回流，否则调参就是玄学。** |
| 为什么不直接拒绝超长请求？ | 拒绝会让用户丢掉已经生成的部分，体验更差。截断 + 明示 > 报错。**可用性优先于整齐。** |
| 为什么不用滚动摘要代替窗口？ | 摘要要额外一次 LLM 调用：延迟、成本、以及一个新的幻觉入口。当前阶段窗口化的收益/风险比更好。摘要留到"历史本身就是答案来源"的场景再上。**工程上先解最痛的那个，不做通用方案。** |
| 提示追加在正文里，会不会污染后续轮次？ | 会进历史，但它是明确的系统提示语，且窗口只保留最近 5 轮，不会长期累积。要彻底隔离应该存结构化字段而不是拼文本——这是我知道的下一层优化，不是没想到。**主动交出边界，比被问出来强。** |
| 你怎么确定没有别的静默故障？ | 我没法确定。但这两个的共同模式是"状态二元化"——把成功/失败当全部。我的做法是每引入一个上游，就把它的结束原因、错误码、默认值列成一张表，缺项就是风险点。**这类排查应该变成清单，不是靠灵感。** |
