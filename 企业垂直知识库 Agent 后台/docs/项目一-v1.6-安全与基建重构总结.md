## 一、一句话结论

v1.6 没有新增业务功能，做的是**把"看起来能跑"的系统改成"经得起追问"的系统**：三个中危安全/一致性缺陷 + 一个可观测缺陷全部闭环，并把重构过程中沉淀的三种工程手法（反向验证、架构守卫、量化决策）固化进了测试与代码注释里。

| 维度 | 重构前 | v1.6 |
|---|---|---|
| 用户被禁用 / 降级后旧 token | **永久有效**，可无限期使用全部接口 | 下一次请求即 401 / 403 |
| LLM 调用出口 | 3 套互不相通的客户端（Agent 恒 ChatOpenAI、RAG 自己维护原生 SDK、评测又 new 一个） | 1 个工厂 `app/llm/`，provider 一处生效 |

## 三、批次 1：鉴权失效（A）

### 现象
管理员在后台软删除（`status=disabled`）某个账号后，**对方仍然可以正常使用全部接口**，直到"token 自然过期"——而实际上永远不会过期。

### 根因（两处叠加才致命）
1. `app/api/deps.py::get_current_user` 只读 Redis 里的用户快照（含 role/status），**从不回查数据库，也完全不校验 `status`**；
2. `app/core/security.py` 每次访问都 `expire` 做滑动续期 → 只要用户持续使用，token 就永续。

顺带暴露第二个问题：管理员被**降级**为普通用户时，`CurrentUser.role` 仍取自旧快照，降级同样不生效。

### 方案
```python
def _load_user_state(db, user_id):
    """按主键读取用户权威状态（单行投影，不加载 ORM 实体）"""
    return (db.query(User.id, User.username, User.display_name, User.role, User.status)
              .filter(User.id == user_id).first())
```

`get_current_user` 的语义变为：

| 数据库状态 | 行为 |
|---|---|
| 行不存在（物理删除） | 删除该会话 + 401「账号不存在或已被删除」 |
| `status != active` | 删除该会话 + 401「账号已被禁用」 |
| 正常 | 返回身份，**role 取 DB 值**（降级/升权立即生效） |

### 关键决策：为什么**不**加 60 秒 TTL 缓存
需求里给了"回查 DB"和"加 60s 缓存"两个选项，但二者在物理上互斥——缓存必然把"下一次请求立刻失效"退化成"最长 60 秒内仍可用"。用数据决策：

| 方式 | 单次耗时（MySQL 3306，300 次均值） |
|---|---|
| SQLAlchemy 单行主键投影查询 | **0.320 ms** |
| 裸 pymysql | 0.203 ms |

`WHERE id=?` 走主键索引、只投影 5 列、不加载 ORM 实体、不读 `password_hash`，且**复用每请求本已持有的 db 会话**（不额外开连接）。0.32ms 相对列表类接口（5~20ms）可忽略，而本地 Redis 一次 RTT 也在 0.2ms 量级——加缓存近乎零收益却牺牲即时性。决策已写入代码注释，后续要开缓存是改一处的事。

### 验证
11 条用例（真实 `/auth/login` → 真实 Bearer → 真实 `get_current_user`，不覆盖任何依赖）。**并做了反向验证**：把 `deps.py` 临时改回旧逻辑，6 条核心用例全红；还原后全绿——证明用例抓得住缺陷，不是摆设。

## 四、批次 2：LLM 统一工厂（B）

### 现象
配置页可切 `mock|openai|anthropic`，但**只有** `POST /kbs/{id}/query` 认这个开关；Agent 会话链路恒定 `ChatOpenAI`。于是同一个系统里出现两套回答口径：知识库问答返回"回显检索内容"的假答案，会话却在调真实模型 —— 使用者会直接判定"知识库问答坏了"。

### 方案：新增 `app/llm/` 作为唯一出口
```
app/llm/
├── __init__.py   只暴露 get_chat_model / generate_text / get_provider / reset_cache
├── factory.py    provider 分发 + 签名缓存 + 热更新
└── mock.py       MockChatModel（LangChain BaseChatModel 真子类）
```
三条链路全部收编：Agent 图（3 处调用）、RAG 问答（删掉自己维护的原生 `openai`/`anthropic` SDK 分支）、RAGAS judge。**删除 `app/agent/llm.py`**。

设计要点：
- **provider 白名单收敛**：非法值（配置文件手写错）降级为 mock 而非抛错炸服务；
- **签名缓存**：`(provider, model, temperature, api_base, Key指纹, timeout, max_retries)` 任一变化即重建 → 配置页改完**无需重启**；密钥只以 sha256 前 12 位进缓存键；
- **purpose 预设**：`chat` 60s/2 次（沿用旧值），`eval` 走 `EVAL_LLM_*`；
- **缺 Key 抛可执行错误**：明确告知去配置页填还是改 `.env`。

### Mock 不是假对象，是真模型
`MockChatModel` 实现 `_generate` / `_stream` / `with_structured_output`，所以**路由分类**和 **SSE 逐字输出**在 mock 下照常工作。输出由 prompt 形态决定（非随机）：

| prompt 形态 | 输出 |
|---|---|
| 含 `【资料】`+`【回答】`（知识库问答） | 回显前 3 条资料；无资料则「资料中未找到相关信息。」 |
| 含 `【工具检索/查询结果】`（Agent 回答） | 基于工具结果的摘要式回答 |
| 含 `query_a`（对比拆词） | 规则切出两个检索词，返回 JSON |
| schema 含 `route` 字段 | 关键词判五路：对比 > 报表 > 业务库 > 知识库 > direct |
| 其他 | 固定格式回应 |

`/kbs/{id}/query` 的 mock 输出与改造前**逐字节一致**（有专门断言），历史演示脚本与文档口径不会漂移。

### 踩坑（真实发生，值得记）
1. **路由 prompt 自带说明文字**（"report：需要汇总、统计或生成报表"），全文匹配会让每题都判成 `report` → 必须用「用户问题：」锚点截取；
2. **direct 路由下把整段 system prompt 当成了用户提问**复述 → 改为「human 消息优先，跳过末条工具结果块」。两条都已补用例锁死。

### 架构守卫（本批次最有价值的产出）
```python
# 除 factory.py 外，整个 app/ 不允许再出现 ChatOpenAI( / ChatAnthropic(
# agent/graph.py、rag/llm.py 必须从 app.llm 导入；app/agent/llm.py 必须不存在
```
这条测试让"双轨"不可能在未来的迭代里悄悄长回来——比任何文档约束都可靠。

### 验证
42 条用例 + 两项真实运行验证：mock 下 `run_agent([], "你好，你是谁")` 完整跑完 LangGraph（route=direct）；临时切 openai 分支打硅基流动 `deepseek-ai/DeepSeek-V3`，真实返回规范的卡纸处理步骤。

### 一个必须知道的行为变化
`.env` 是 `LLM_PROVIDER=mock`。改造前：会话走真实 API、知识库问答走 mock（就是 bug 本身）。改造后：**配置说了算** → 会话也走 mock，页面会显示「【模拟回答】…」。要看真实回答，在系统配置页把 provider 切 `openai`（即时生效），或改 `.env` 后重启。**这不是退化，是配置第一次真正生效**；同时也换来断网可演示、CI 可离线跑。

## 五、批次 3：真实 Redis + 真实限流（C / D）

### 现象与根因
`.env` 里 `FAKE_REDIS=true`，但本机真实 Redis 就在跑。三重后果：
1. 登录态全在进程内存 → **后端一重启，所有人被踢下线**；
2. refresh 黑名单不跨进程 → logout 无法真正吊销；
3. `rate_limit.py` 在 fake 模式下**直接跳过限流** → AI 问答无限流保护。

### 改造
| 文件 | 改动 |
|---|---|
| `app/core/redis.py` | 重写：`is_fake_redis` / `redis_backend` / `probe` / `reset_client` 收敛为公共能力；真实连接加 `socket_connect_timeout=2s / socket_timeout=5s / health_check_interval=30s` |
| `app/api/rate_limit.py` | 复用公共判定（原来两处各写一份口径，易漂移）；新增 `rate_limit_status()`；fake 跳过时打 WARNING |
| `app/api/v1/kbs.py` | **`POST /kbs/{id}/query` 挂上限流**（此前完全裸奔） |
| `app/api/v1/system.py` | `/health` 新增 `redis_backend`(real/fake) + `rate_limit`(enabled/disabled/degraded) |
| `app/main.py` | 启动期 Redis 后端自检三态播报 |
| `frontend_vue/src/views/Chat.vue` | SSE 401 刷新失败 → 清凭据跳登录；429 → 友好提示 |

### 抓到的"假生效"陷阱（本批次最有价值的发现）
`get_redis()` 原来把客户端缓存成全局变量、只读一次 `FAKE_REDIS`。若运行期把 fake 切成 real（测试 monkeypatch、配置热切换），句柄仍是 fakeredis —— 而 **fakeredis 不支持 Lua EVAL**，令牌桶 `eval` 抛异常 → 被 fail-open 吞掉 → **限流看起来开着，实际一条都没限**。

修复：`get_redis()` 每次比对期望后端，不一致就重建句柄。这类"故障静默降级为不设防"的问题，只有真正压测才会暴露。

### 顺带补的真缺口
限流原先只挂 `chat` 与 `chat/stream`，而 `POST /kbs/{id}/query` 完全没限流 —— 这个接口显式消耗"向量检索 + LLM 生成"，是最贵、最容易被脚本刷的入口。现已与另外两个入口共用同一令牌桶（`rate_limit:ai:{user_id}`）。

### 验证（用真实的 HTTP 429 说话）
在线脚本打运行中的 8000 端口（不是测试假客户端）：
```
[health] status=ok db=ok redis=ok backend=real rate_limit=enabled
[config] ai_rate_limit_per_minute: 30 -> 3（结束自动还原）
[stress] 对 /kbs/6/query 连续请求 5 次（上限 3/分钟）
  #1   HTTP 200  #2 HTTP 200  #3 HTTP 200
  #4   HTTP 429  code=429 请求过于频繁，请稍后重试
```
10 条测试（真实 Redis 用 **db=15 隔离**，无 Redis 环境自动 skip）覆盖：容量耗尽→拒绝、匀速补充、按用户隔离、依赖层 `BizError(429)`、HTTP 端到端 429、会话跨重启存活、会话被删→401 且在**查库之前**就拒绝。同样做了反向验证：临时删掉 kbs 的限流依赖，第 4 次请求返回 200 → 用例立刻变红。

### "重启掉线"的结论：真实 Redis 下**不再掉线**，且失效路径受控
| 场景 | 结果 |
|---|---|
| 重启后端，同一 token 请求 `/auth/me` | **200**（会话在 Redis，不在进程里） |
| 手动删 session key（模拟 Redis 丢数据） | 401，refresh 也 401 |
| 前端 axios 路径 | 401 → 尝试 refresh → 失败 → 清凭据 + 跳 `/login`（原有逻辑） |
| 前端 SSE 路径 | **原来只往消息列表塞一条"失败"气泡，人卡在对话页反复 401** → 已改成与 axios 一致 |

### D：健康检查不再"永远 ok"
`/health` 的 `redis` 字段原先在 fake 模式下恒为 `ok`（ping 的是内存实例），真实 Redis 挂了也看不出来。现在额外暴露 `redis_backend` 与 `rate_limit`，这是判断"限流到底开没开"的唯一可信来源。

## 六、批次 4：库隔离 + 配置恢复默认

### 1) Redis 逻辑库隔离（db0 → db1）
本机 6379 的 db0 里有 1895 个键，其中 **1869 个是另一个项目的 LangGraph checkpoint**（`checkpoint*` / `agentflow:*`）。共用库的现实风险：任一方 `FLUSHDB` 或键前缀撞车，就会互相伤害。

- `REDIS_URL=redis://127.0.0.1:6379/1`（项目一独占）；
- 代价：已登录会话失效一次（开发阶段可接受，本来就是本次要验的行为）；
- 实测：用 db0 里的旧 token 打新服务 → `401 未登录或登录已过期`，证明隔离真的生效；重新登录后键落在 db1，db0 的 1895 个键一个没动；
- `.env.example` / 部署运维手册 / `config.py` 注释均已注明"库号按项目独占"。

### 2) `DELETE /system/config/{key}`：给覆盖值一个出口
**问题**：`runtime_config` 的覆盖值（`data/system_config.json`）优先级高于 `.env`，管理员在配置页保存过一次 `ai_rate_limit_per_minute` 之后，改 `.env` 就**永久失效**，且没有任何恢复入口。这个缺陷是在批次 3 用压测脚本时被自己的测试撞出来的（改阈值后 `AI_RATE_LIMIT_PER_MINUTE` 不再生效）。

**接口语义**：
- 删除该键覆盖值 → 立即回退 `.env` / 代码默认值，无需重启；
- **幂等**：键本来没有覆盖值时同样 200（结果一致）；
- **未知键 404**：避免拼写错误被当成"恢复成功"静默吞掉；
- 返回值与 GET / PUT **同形状**，前端可直接刷新表单；
- 仅管理员（403 边界），未登录 401。

**配套**：`GET /system/config` 新增 `overridden_keys` 字段，前端据此显示"当前有 N 项使用服务端覆盖值"并控制「恢复默认」按钮的可用性。前端点击后确认弹窗 → 逐键删除 → 重新拉取表单。

**实测（运行中的服务）**：
```
overridden_keys = ['llm_api_base','llm_api_key','llm_model']
PUT  tool_max_attempts=7  → 7        | overridden_keys 追加该项
DEL  tool_max_attempts    → 3（回退 .env）| overridden_keys 复原
DEL  再删一次             → HTTP 200（幂等）
DEL  bogus_key            → HTTP 404 未知的系统配置项: bogus_key
DEL  无 token             → HTTP 401
```
并且验证了"重启后不复活"：清空内存缓存从磁盘重载，被删键确实不再出现。

### 3) 联动验证（两个批次一起用）
把限流阈值临时降到 2 → 连打 `/kbs/6/query` 4 次（**200, 200, 429, 429**，db1 真实 Redis）→ 用新的 DELETE 接口恢复默认 30。这条链路同时证明了"限流在 db1 生效"与"恢复默认接口可用"。

## 七、收益汇总

### 安全性
- 权限回收从"永不生效"变为"下一次请求生效"，且**同时吊销会话**（不是单纯拒绝）；
- 降级/升权即时生效，`/auth/me` 与权限判定同源，不会出现"显示 admin 却无权限"；
- AI 入口 3/3 限流覆盖，杜绝单账号刷爆向量检索 + LLM 的成本风险；
- 项目一与其它项目 Redis 物理隔离，消灭"误伤"这类不可控事故。

### 稳定性与可运维性
- 后端重启不再踢人（会话在 Redis），rolling restart 变得安全；
- 真实 Redis 连接带超时，Redis 宕机时快速失败而不是把请求挂到 TCP 超时；
- `/health` 能真实回答"限流开没开、Redis 是真是假"；
- 前端两条 401 路径（axios / SSE）行为一致，不会再卡死在对话页。

### 一致性与可维护性
- LLM 出口唯一，provider 一处生效；换模型/换厂商/切 mock 不需改代码；
- 架构守卫测试让"绕过工厂"在 CI 阶段就红，双轨不可能复发；
- 配置有"写 / 读 / 删"完整生命周期，覆盖值与 `.env` 的关系变得可解释。

### 成本与体验
- 离线可演示：`provider=mock` 下整条 Agent 图可跑通，断网也能做 demo 与 CI；
- 限流把"被刷爆"从不可控成本变成可配置阈值（配置页热更新，无需重启）。

## 八、面试话术（可直接口述）

**Q：讲一个你排查过的线上隐患。**
> 后台有"禁用用户"功能，界面显示已禁用，但我核对中间件时发现被禁用的账号还能正常调接口。根因是鉴权中间件只读 Redis 里的用户快照、从不回查数据库，而会话又做了滑动续期——两个设计单独看都合理，叠加起来就让"禁用"永久失效。修复是在依赖里加一次主键单行投影查询，按数据库状态判定，并且顺手把会话删掉。团队担心性能，我先量了一下：单行主键投影 0.32 毫秒，而且复用每请求已有的连接，比本地 Redis 一次往返还便宜，所以没有加缓存——加了反而会让"立刻失效"退化成"最长 60 秒仍可用"。最后我把新逻辑改回旧版跑了一遍，6 条核心用例全红，证明测试真的抓得住问题。

**Q：怎么做架构治理？**
> 我们系统原先有三套 LLM 客户端，配置开关只对其中一条链路生效，导致同一个系统两套回答口径。我做了统一工厂，把 provider 分发、密钥热更新、超时重试策略收在一处；mock 不是一个假对象，而是实现了完整 LangChain 接口的真模型，所以路由分类和流式输出在离线下照样能跑通。更有意思的是我加了一条"架构守卫"测试：除工厂文件外，全仓库不允许再出现 `ChatOpenAI(`，改回双轨 CI 直接红。用测试守住架构，比写文档靠谱。

**Q：讲一个只有压测才能发现的问题。**
> 我们把 Redis 从内存模拟切到真实实例后压测限流，结果发现"看起来开着、实际一条都没限"。原因是客户端句柄被缓存成全局变量、只读一次配置，运行期切换后端后句柄还是模拟实现，而模拟实现不支持 Lua 脚本，令牌桶的原子脚本抛异常后被 fail-open 吞掉——故障被静默降级成了"完全不设防"。修复是每次比对期望后端、不一致就重建句柄。这件事让我后面所有"降级"逻辑都加了显式告警，不允许静默。

**Q：怎么处理配置与默认值的关系？**
> 我们的配置有两层：管理员保存的覆盖值优先级高于环境变量。压测时把阈值临时调低，结果发现环境变量再也不生效了——覆盖值永久遮蔽了 env，而且没有恢复入口。我加了 `DELETE /system/config/{key}`：删除覆盖值即回退 env，幂等、未知键返回 404 而不是静默成功，返回体和查询接口同形状，前端可以直接刷新表单；同时给查询接口加了 `overridden_keys`，界面能显示"哪几项是覆盖值"并支持一键恢复。配置从此有了完整的读写删生命周期。

## 九、沉淀的三条工程手法

1. **反向验证**：新增用例必须先在**旧代码**上跑红，再在新代码上跑绿。否则你无法区分"用例有效"和"用例恒真"。本次 4 个批次中，鉴权与限流两次关键验证都用了这个手法。
2. **架构守卫**：把"不许绕过 X"写成测试（扫描 import 与构造调用），而不是写在文档里。人会在 deadline 前妥协，CI 不会。
3. **量化决策**：性能类争议（要不要加缓存、要不要加索引）先测 300 次取均值，再决定。0.32ms 这个数字直接终结了 60 秒缓存的讨论。
