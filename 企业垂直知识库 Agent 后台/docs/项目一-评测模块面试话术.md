# 项目一｜评测模块完整面试话术

> 用途：在面试里讲清「从建集到 A/B 测试」这条闭环。所有数字与行为都对应真实代码，被追问能落到文件名。

---

## 0. 30 秒电梯版（先背这段）

> 「我做的不是『接了个 RAGAS 跑分脚本』，而是一条**可运营的评测链路**：评测集能新建、能批量导入、能补标准答案、能删脏样本；跑任务能带检索参数；跑完能看四项指标、能下钻到单条样本；坏例子还能从用户点踩回流成新样本。
>
> 核心价值是一句话：**把『效果好不好』从主观感受，变成一条可复现的数字，并且这条数字能被业务方自己跑出来。**」

如果对方只有 1 分钟，就停在这，等他挑一个点往下问。

## 1. 先给结构：五步闭环（配手势/画图）

```
① 建集          ② 导入              ③ 补答案            ④ 带参跑            ⑤ 看数+回流
指定 KB      →  JSON/CSV 粘贴   →   黄金集人工确认   →  top_k/search_mode →  四项指标/单样本
+ 名称          逐行校验+500上限      空答案拒绝          请求级生效           ↓ 点踩回流到 ①
```

一句话解释每步的**存在理由**（不要只报功能名，面试官听功能会走神，听理由才会追问）：

| 步骤 | 我会怎么说 |
|---|---|
| ① 建集 | 「评测集必须绑定一个知识库，因为『好答案』是相对于某个 KB 的语料说的，脱离 KB 的评测集没有基准。」 |
| ② 导入 | 「支持 JSON 和 CSV 粘贴，解析和逐行校验都放前端。原因是批量导入真正的失败原因不是接口挂了，而是从 Excel 复制出来带了表头、空行、整列空答案——这些必须在提交前逐行报出来。」 |
| ③ 补答案 | 「参考答案是评分的锚点。用户点踩沉淀的样本我**故意留空**，因为把 AI 的错误答案直接填成标准答案，等于教评测器把幻觉当正确答案。留空之后必须有人补，所以我做了补答案入口。」 |
| ④ 带参跑 | 「`top_k` 和 `search_mode` 是**请求级**参数，随任务持久化，跑的时候覆盖知识库默认检索。这样才能做控制变量。」 |
| ⑤ 看数+回流 | 「列表里参数和指标同屏，展开能看四项均值再下钻单样本；发现坏例可以一键回流成新样本。」 |

## 2. 四个高频问法，四套答法

### Q1「你们 RAG 的效果是怎么评的？」

不要直接说「用 RAGAS」。分三层答，显得有判断：

> **指标层**：四项 —— faithfulness（答案是否有资料支撑）、answer_relevancy（是否答到点上）、context_precision（召回里有多少是有用的）、context_recall（该召回的是否都召回了）。前两个看生成，后两个看检索，**能区分『是检索错了还是模型编了』**。
>
> **数据层**：指标靠评测集，评测集是「问题 + 人工确认的标准答案 + 可选的分层标签」。没答案的样本我不让它进评测，因为 context_recall 会算不出来。
>
> **口径层**：这是我踩过坑的地方 —— 均值统计里 NULL 不算 0，也不参与计算；样本删了但历史运行记录保留，所以会出现「数据集 0 条但历史指标还在」的情况，这是刻意设计（历史结论不该被后来的数据改动抹掉）。

### Q2「怎么保证回答不幻觉？」

> 「我不敢说保证了，我是做了四层收口 + 一层度量。
>
> 第一层是**入库清洗**：PDF 表格按 bbox 纵向切条带，表格单独转 Markdown 并回填表头，避免表格被抽成一行行空格拼接的乱码——脏数据进去，后面全是幻觉。
>
> 第二层是**混合检索**：向量 + BM25 + RRF 融合。纯向量对数字、专有名词不敏感，制度类问答里「500 元」和「800 元」向量距离极近，必须靠字面召回兜住。
>
> 第三层是**生成约束**：只依据给定资料、找不到就说找不到、多份资料冲突时必须列出冲突而不是自己融合出一个中间值。
>
> 第四层是**后置校验**：把答案里的 ≥3 位数字和日期抽出来，归一化后在检索上下文里做子串比对，没命中就打 `suspect` 标记。注意是**只标不拦** —— 拦了会误杀（模型可能在做合理的单位换算），但标记让我能监控幻觉率。
>
> 最后用 RAGAS 把这四层的效果量化出来。」

### Q3「你的优化真的有效吗？」（最重要的一问）

这题答不好，前面全白搭。要给「控制变量」的方法论：

> 「我的做法是**同一个数据集、只改一个变量、跑两次**。
>
> 接口上 `rag_config` 是请求级的，随任务落库，所以每个 run 都能回答『你当时用的什么参数』——列表里我把参数和指标放在同一屏，就是为了让这件事不需要口算。
>
> 举个真实的例子：我怀疑纯向量对数字类问题召回不够，就把 `search_mode` 从混合改成 `vector_only`、`top_k` 保持 5，跑同一批样本，对比 context_recall。如果掉得明显，说明混合检索对这类语料是必要的；如果基本不变，那说明我的向量模型对这些数字已经够敏感，混合检索的成本可以省。
>
> 这里有个**必须自己先说的前提**：单次跑的差异可能是噪声，样本量小的时候尤其如此。所以我的判断标准不是『高 0.02 就算赢』，而是『这个方向上的差异是否在多批样本上稳定复现』。」

### Q4「评测集从哪来？会不会自己给自己出题，自己给自己打分？」

这是**陷阱题**，考的是你有没有意识到「评测集污染」。

> 「两个来源，且都不是模型生成的：
> 一是人工构造的黄金集（按业务场景分层，比如简单事实、跨表汇总、制度冲突）；
> 二是**线上真实坏例回流** —— 用户在对话页点踩，一键沉淀成 badcase 样本。
>
> 第二个来源是关键，因为它来自真实分布，不是我想象出来的分布。
>
> 关于『自己给自己打分』：RAGAS 的 faithfulness 和 relevancy 确实是用 LLM 当裁判，这是公认的弱点。我的应对是：
> ① 裁判模型可以独立配置（`eval_llm_model`），能跟对话模型分开，避免『同一个模型既当运动员又当裁判』；
> ② 我只把它的分数当**趋势指标**，不当绝对值 —— 0.62 和 0.68 之间我不做精细解读，但 0.62 掉到 0.35 一定是出事了；
> ③ 真正的兜底是**确定性校验**（数字/日期子串比对），那个不依赖模型，可复现。」

## 3. 现场演示脚本（120 秒，按这个顺序点，别跳）

> 前提：RAGAS 评测页 → 点「数据集管理」

| # | 动作 | 配的一句话（边点边说） |
|---|---|---|
| 1 | 点「新建数据集」，填名称、选 KB | 「建集必须绑 KB，因为好坏是相对语料说的。」 |
| 2 | 粘贴 CSV，**故意留一条参考答案为空** | 「我故意留一条空的，你看它会……」 |
| 3 | 看到红色逐行报错「第 2 行：reference_answer 为空」 | 「……它不会闷头提交然后后端返 422，而是告诉我第几行、为什么。空答案的样本 context_recall 永远算不出来，我不允许它进来。」 |
| 4 | 补上答案，点「导入 3 条」 | 「前端解析 + 校验，后端只做兜底，单次上限 500 条。」 |
| 5 | 列表里看「参考答案」列变成「已齐全」 | 「这列是我特意加的：一个数据集有多少条缺答案，一眼能看到，不然你永远不知道自己的 recall 为什么缺一半。」 |
| 6 | 「新建评测任务」，选数据集，`top_k=5` + 混合检索 | 「参数是请求级的，会随任务落库。」 |
| 7 | 再跑一次，`top_k=3` + 纯向量 | 「同一个数据集、只改参数，这就是控制变量。」 |
| 8 | 列表里两行并排，参数列不同、指标列同屏 | 「参数和指标放一起，是为了不用翻详情页做对比。」 |
| 9 | **勾选这两行 → 点「对比 A/B」** | 「勾两个已完成的任务，对比按钮才亮；跨数据集的会被挡掉，因为样本对不齐就没法比。」 |
| 10 | 报告弹窗：顶部两侧参数 → 一句话结论 → 四项 Δ → 逐样本 | 「先看结论这一行：3 项提升、1 项下降、12 条样本超过阈值。**先给结论再给表** —— 只甩一张表让对方自己算是偷懒。」 |
| 11 | 打开「只看差异样本」开关 | 「12 条里挑最差的看原文，这才是能落地的地方：均值告诉你有没有变好，样本告诉你为什么。」 |
| 12 | 展开某一行，看四项均值 → 下钻单样本 | 「均值只能看趋势，问题都藏在单样本里。这条 faithfulness 0.3，说明答案里出现了资料不支持的内容。」 |
| 13 | （可选）回对话页点踩 → 提示「已加入评测集」 | 「坏例回流。这条回答的错误会变成下一轮评测集里的一个待补样本，闭环回到第 1 步。」 |

**演示纪律**：
- 不要念指标定义，直接说「这条低，我去看原文」。
- 不要让页面空着等加载，提前跑好一批数据。
- 演示「失败」比演示「成功」更有说服力（第 2 步的故意留空就是干这个的）。

## 4. 抗追问 10 问（提前想好，别现场编）

**1. RAGAS 用的是 LLM 当裁判，它本身会幻觉，你怎么信它？**
> 「不全信。我把它当温度计，不当尺子。温度计有系统误差，但能看出病人发烧了。真正的硬指标是确定性校验（数字/日期子串比对）和人工抽检。」

**2. LLM 打分不稳定，同一批数据跑两次分数不一样怎么办？**
> 「会不一样，尤其样本量小的时候。所以我把裁判温度设为 0，并且判断标准是趋势和跨批次稳定性，不做小数点后两位的比较。这也是我不把 RAGAS 分数接进告警阈值的原因。」

**3. context_recall 算不出来怎么办？**
> 「它的前提是有标准答案。空答案的样本我直接拦在导入环节，已经进来的（早期数据）会在数据集列表里标『N 条待补』，补完才算完整样本。剩下三项在缺答案时仍可计算，所以缺答案不至于让整批数据报废。」

**4. 为什么单次导入上限是 500 条？**
> 「两个考虑：一是单次请求的耗时要可控（每条要跑问答链路 + 四项指标）；二是我希望导入是『人看过的一批』，而不是无脑灌十万条。前端在解析阶段就把超限挡掉，并提示分批。」

**5. 为什么不让业务方随便在页面上建评测集？**（这题最容易答成「我们没做」）
> 「现在是**开放建集、限制编答案**：建集、导入、补答案、删脏样本都能做，但参考答案必须是人工确认过的非空文本，空答案直接拒绝。
>
> 这条线是我刻意划的：**读取和修正应该开放，从零编造黄金集应该受限。** 让业务随手编 30 条标准答案，评出来的分数会虚高，反过来把幻觉测成合格 —— 那比不评测更糟。」

**6. 评测集会不会过拟合？毕竟你就用这批题调参。**
> 「会，所以评测集要分两层：**调参用集**和**验收集**必须分开，验收集不参与任何调参决策。我现在有分层标签（stratum），可以按层看指标，避免一个整体均值掩盖某一层的退化。短板是还没有做数据集版本快照，这点我认。」

**7. top_k 是不是越大越好？**
> 「不是。top_k 变大，context_recall 通常升，但 context_precision 会降 —— 塞进去的无关片段会干扰生成，faithfulness 也可能掉。这正好是 A/B 要回答的问题：找一个 recall 够了、precision 还没崩的点。所以我把它做成请求级参数，而不是写死在配置里。」

**8. 你怎么知道 A/B 的差异不是噪声？**
> 「三个做法：一是同数据集、只改一个变量；二是看方向是否在多批样本上复现；三是看分层结果 —— 如果整体升了但难例层大幅下降，那不是优化，是换了个捷径。我没有做显著性检验，样本量不够支撑，这点我不装。」

**9. 为什么 chunk_size 只记录、不生效？**
> 「chunk_size 是**入库切片**参数，文档在入库时就已经切好并向量化了，查询期改它对已有数据没有任何作用。真实的切片实验必须重建索引、重跑一遍文档处理。所以我不把它做成能点的开关 —— 做成能点但不生效的开关，比没有更害人，用户会以为实验做了。」

**10. 这套东西最大的短板是什么？**（一定要主动说）
> 「三个：
> ① **评测集没有版本快照** —— 数据集被改过之后，历史 run 的分数和当前数据集对不上，复现性打折。
> ② **样本量级不够** —— 百量级能看趋势，不足以支撑小数点后两位的结论。
> ③ **没有自动回归** —— 现在是人工触发评测，理想状态是每次改动知识库或检索参数自动跑一批基线，掉了就拦发布。这个属于工程化，还没做。」

## 6. 别说这三句话

1. ❌「我们用了 RAGAS，所以评测结果比较权威。」
   → 这句话会让面试官立刻追问 judge 的可靠性，而你没有准备就只有挨打。要说「RAGAS 给我趋势，确定性校验给我底线」。

2. ❌「优化之后指标提升了 0.05。」
   → 不说样本量、不说方差、不说是不是同一批题的提升，等于自己挖坑。

3. ❌「这套系统已经比较完善了。」
   → 主动交短板反而加分。**能说清自己系统边界的工程师，比说『都做完了』的可信。**

> 「这套东西的代码量不算大，但我花最多时间的地方不是写功能，是**划边界** —— 哪些该开放、哪些该限制、哪些指标只做趋势不做结论。评测系统最大的风险不是跑不起来，是跑出来一个你错误相信的数字。」
