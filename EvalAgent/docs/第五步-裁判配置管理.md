# 第五步：裁判配置管理（考生 / 考官双面板）

> 2026-10-26 实现。解决「考官的模型和 Key 藏在服务器 .env 里，管理员在界面上动不了」的黑洞。

## 一、为什么分两块

| 面板 | 谁 | 归属 | 接口 | 改完影响 |
|---|---|---|---|---|
| 问答模型配置（考生） | 被评测的 RAG 问答模型 | **项目一** 8010 | `PUT /system/config`（上游已有，热更新） | 下一轮评测的「答案」会变 |
| 裁判模型配置（考官） | RAGAS 打分的裁判 | **项目二** 8200 | `GET/PUT /system/judge-config`（本次新增） | 下一轮评测的「分数」会变 |

两者必须分开：改考生是改「被测对象」，改考官是改「尺子」。混在一个配置里，A/B 对比就失去了可比性
（尺子变了却以为是模型变了）。

## 二、数据结构

`runtime_configs`（`app/models/runtime_config.py`）：

| 字段 | 用途 |
|---|---|
| `config_key` | 主键，如 `JUDGE_MODEL` / `JUDGE_API_KEY` |
| `config_value` | 值；secret 键明文（同项目一 `data/system_config.json` 敏感级） |
| `is_secret` | 是否敏感：是则不落日志、读接口脱敏 |
| `description` | 配置说明，前端直接展示 |
| `updated_by` / `updated_at` | 审计：谁在什么时候改的 |

**优先级：`runtime_configs` > `.env` > 代码默认值。**
库里没有的键 = 沿用 `.env` → 现有部署零迁移升级（实测空表时读出来全是 `source=env`）。

## 三、四个关键设计

### 1. 保存即探活（最关键）
```
PUT /system/judge-config
  ① 合并候选配置（未提交字段沿用现值；key 空/掩码 = 不改）
  ② judge.preflight(candidate) ← 用候选配置真的发一次请求
  ③ 失败 → 422，一个键都不写；成功 → 写库 + invalidate 缓存 + judge.reload()
```
理由：裁判配置写错的代价是**整场评测静默空分**（RAGAS 把异常吞成 NaN），
错误必须拦在保存那一刻，而不是跑到一半才发现。

### 2. 热更新（不重启 8200）
`RagasJudge._build()` 每次比对配置签名 `(model, api_base, api_key, embedding, temperature)`，
签名变了就重建 LangChain 客户端。写入后 `reload()` 置空，下一次打分/探活自动按新配置重建。
实测服务日志：
```
裁判就绪：model=qwen-plus ... temperature=0(locked)
裁判就绪：model=deepseek-v4.1-flash-1017 ... temperature=0(locked)
```

### 3. 温度锁死 0
- 请求 schema 里**没有** `temperature` 字段（传了也被 pydantic ignore）
- `JudgeConfig.temperature` 恒为 `0.0`，`ChatOpenAI(temperature=0)` 写死
- 读接口返回 `temperature=0.0, temperature_locked=true`，前端渲染成 disabled 输入框

原因写进代码注释：**为保证评测结果的可复现性，裁判温度强制锁定为 0**。
温度 >0 会让同一份样本两次跑分不同，A/B 的 Δ 直接被噪声吃掉（项目四已实测 ±0.05 级波动）。

### 4. 权限与脱敏
- 身份不复制：拿 `Authorization: Bearer <token>` 调**上游** `GET /auth/me` 取 role，判 `admin`
- 失败口径区分：无 token→401、上游不可达→503、非 admin→403（403 不跳登录，只提示权限不足）
- `GET` 任何登录用户可读（便于排查「这次评测用哪个模型打的分」），但 key 恒返 `******`
- 提交 `******` 或空串 = 不修改（前端占位符回传的就是掩码）

## 四、接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/v1/system/judge-config` | 读配置（key 掩码、含 source/overridden/readonly/审计信息） |
| PUT | `/api/v1/system/judge-config` | 改配置（**仅 admin**，探活通过才落库） |
| POST | `/api/v1/system/judge-config/preflight` | 单独探活当前配置 |

裸路径 `/system/judge-config` 同步挂载（不含 `/api/v1`），与其它接口口径一致。

响应体（节选）：
```json
{"model":"deepseek-v4.1-flash-1017","api_base":"https://dashscope.aliyuncs.com/compatible-mode/v1",
 "api_key":"******","api_key_configured":true,"embedding_model":"text-embedding-v3",
 "temperature":0.0,"temperature_locked":true,
 "source":{"JUDGE_MODEL":"env","JUDGE_API_KEY":"env"},
 "readonly":{"JUDGE_MAX_RETRIES":3,"JUDGE_METRIC_TIMEOUT":90,"JUDGE_DISABLE_THINKING":true},
 "updated_at":null,"updated_by":null}
```

## 六、已知边界

1. **懒重建**：PUT 只清客户端，真正重建发生在下次打分/探活。想在保存时就看到「已切换」，点一下「探活」即可。
2. **缓存 TTL 30s**：多进程部署时，别的 worker 最迟 30s 后跟上；本机单 worker 立即生效。
3. **密钥明文落库**：与项目一 `data/system_config.json` 同级。要更强，下一步接 KMS/加密列，接口层不用改。
4. **审计只到「最后修改人」**：没有变更历史表。要做合规追溯再加 `runtime_config_logs`（追加写）。

## 七、回归中连带发现并修掉的三个真问题

第五步交付后跑第四步全链路回归（项目三 → 8200 → 项目一），暴露了三个**原本就存在、只是没被触发**的问题。
都不是「跑不通」，而是「跑得又慢又静默」——这类最伤人。

### 1. 判分模型免费额度耗尽（环境性，但暴露了设计缺陷）
`deepseek-v4.1-flash-1017` 是**带日期后缀的免费额度模型**，今天反复探活/评测把它打爆：
```
403 AllocationQuota.FreeTierOnly: Free quota exhausted...
```
后果不是直接报错，而是 RAGAS 每条样本各重试到 90s×3 次，一轮 7 条拖到 **5 分钟**，
项目三 300s 轮询窗口直接判超时。
- **处置**：用新做的配置接口切到短名 `deepseek-v4.1-flash`（同日验证 200 OK，延迟 1.4s）。
  这恰好是「管理员可在界面切裁判模型、无需重启」的第一个真实用例。
- **记忆**：带日期后缀的模型只有免费额度 → 判分模型必须用短名。

### 2. 致命错误不熔断（已修）
上面那种「配置坏了」的错误，逐条重试毫无意义。新增 `_is_fatal_judge_error()`：
额度耗尽 / key 失效 / 模型不存在（`AllocationQuota`、`FreeTierOnly`、`insufficient_quota`、
`PermissionDenied`、`invalid_api_key`、`does not exist`）命中即**提前终止整轮**，
未跑样本标 `skipped`，任务置 `failed` 并写明根因。单条难/超时不算致命，继续跑其余样本。

### 3. 裁判客户端 reload 与在飞打分的竞态（已修）
`reload()` 把 `self._llm` 置 None，若恰好跨在某个 `score()` 读取之间，会拿 None 传给 RAGAS，
表现为 `AssertionError(set LLM before use)` / `AttributeError: 'NoneType' object has no attribute 'generate'`
——**指标静默变 NaN**。
- `score()` 改为先取本地引用 `llm, embeddings = self._llm, self._embeddings` 再使用；
- ragas 的指标是**模块级单例**，多线程并发 evaluate 会互相覆盖 llm 属性，
  因此在锁内显式回填一次（`_metric_lock`）。

### 4. 项目三「转发分支」轮询窗口过紧（配置修正）
`EVAL_POLL_MAX_RETRY` 默认 30 次 × 10s = **300s**，而「直连项目一」分支配的是 400 次 —— 明显不一致。
RAGAS 单条样本 40~280s，7 条一轮实测 **328s**（run EV20261026-0022，7/7 完成）。
已改 `.env`：`EVAL_POLL_INTERVAL_S=10` / `EVAL_POLL_MAX_RETRY=180`（30 分钟），E2E 脚本窗口同步放到 900s。

### 补的测试
`test_execute_run_processes_every_item`：用 3 条样本真实跑 `execute_run`，断言
`processed_items == total_items` 且 `success_items == 3`。
这条测试的价值在这次体现得很直接——修缩进时又踩了一次「循环体错位导致只处理一条」，
有它兜底立刻红灯。全量 **36 passed**。
