# AgentFlow v1.2 操作演示流程文档

> **用途**：面向**零基础演示者**的“照着做就能跑通”手册。任何人拿到本文件，按步骤原子化操作，即可完整演示 AgentFlow v1.2 的核心能力，不跳过任何关键动作。
> **版本**：v1.2.0（v1.0 全量交付 → v1.1 真实知识库/可信度/导出 → v1.2 工具注册表/限流/评审干预/演示脚本/compose）
> **适用场景**：离线答辩（mock 模式）、完整联调（real 模式）。
> 文档中所有接口路径均以 `/api/v1` 为前缀；前端采用 hash 路由，页面 URL 形如 `http://127.0.0.1:5173/#/dashboard`。

---

## 1. 文档说明

### 1.1 本文档覆盖什么

- 一键拉起演示环境（推荐 `scripts/demo_up.py`，不依赖 docker 自动拉起整套服务）。
- 两种演示模式的区分与切换：`--mock` 离线 / `--real` 真实联调。
- 一条完整的端到端演示主线（登录 → 工具开关 → 建任务 → 知识库检索 → 评审干预 → 记忆 → 导出 → 限流）。
- 断点持久化专项演示（关后端、重启、恢复不丢）。
- 常见故障排查 + 演示前快速核对清单。

### 1.2 服务清单（演示必备，缺一个链路就不完整）

| 组件 | 端口 | 作用 | 谁来起 |
|---|---|---|---|
| **Redis Stack** | `6379` | 事件流 / 断点 / 限流 / 黑名单 / 短期记忆（必须带 RedisJSON + RediSearch） | 手动 `docker run` 或本机 redis-stack |
| **MySQL** | `3307` | 任务 / 子任务 / 审批 / 轨迹 / 记忆（8 张表） | 本机 `mysqld`（数据目录需提前初始化） |
| **AgentFlow 后端** | `8000` | 编排 + API + SSE | `demo_up.py` 或本地 `.venv` |
| **项目一「企业垂直知识库」** | `8010` | `kb-search` 的真实检索数据源（仅 real 模式需要） | 同级目录 `企业垂直知识库 Agent 后台/.venv` |
| **Vue 前端** | `5173` | 演示控制台 | `agentflow-web`（`npm run dev`） |

> 说明：Redis / MySQL 是“底座”，`demo_up.py` **只做连通性检查并给启动命令**，不会代管它们的数据；后端 / 项目一 / 前端由 `demo_up.py` 以**本地进程**方式拉起（这就是“不依赖 docker 自动拉起”的含义）。

### 1.3 前置依赖清单（首次演示前一次性准备）

| 依赖 | 说明 | 验证方式 |
|---|---|---|

| Node.js + npm | 前端运行环境 | `node -v`、`npm -v` |
| agentflow-web 依赖 | 前端 `node_modules` 已安装 | `agentflow-web\node_modules` 目录存在 |

| 项目一后端（仅 real） | 真实检索数据源 | `agentflow-platform\..\企业垂直知识库 Agent 后台\.venv` 存在 |
| 演示账号已播种 | `admin_user / Passw0rd!` 必须存在 | 见 §2.3 |

## 2. 前置准备清单

### 2.1 端口检查（逐项确认，避免启动后互相打架）

打开一个终端，逐条执行，确认**冲突端口未被占用**：

```bash
# 在 agentflow-platform 目录下执行（下文所有命令默认在此目录）
netstat -ano | findstr ":3307 :6379 :8000 :8010 :5173"
```

- **怎么判断成功**：上述命令**无输出** = 五个端口全部空闲，可直接启动。
- **若有输出**：记下对应 PID（`netstat` 最后一列），用 `tasklist /FI "PID eq <PID>"` 看是什么进程；若是旧 demo 残留，按 §8 清理后再继续。
- 特别注意：**系统自带 `MySQL80` 服务占用的是 3306，与本项目 3307 不冲突**，不要误关它。

### 2.2 环境文件说明

- 当前 `.env` 中几个与演示强相关的默认值（仅供参考，脚本会覆盖）：

### 2.4 两种模式区分（演示前先决定用哪种）

## 3. 一键启动流程（推荐：`scripts/demo_up.py`）

> 所有命令默认在 `agentflow-platform` 目录下执行。脚本的**三条安全约定**：只启动缺失端口、不代管 MySQL 数据目录、只停自己记录的 PID（不会误杀别人的进程）。

### 3.1 状态检查（启动前先做，心里有数）

```bash
cd agentflow-platform
.venv\Scripts\python.exe scripts/demo_up.py --status
```

- **预期输出**：打印“组件状态”表，五列分别是 Redis Stack / MySQL / AgentFlow 后端 / 项目一知识库 / Vue 前端，每行前缀 `[OK]` 或 `[DOWN]`。
- **怎么判断成功**：你能清楚看到哪些组件已经在线（OK）、哪些还没起（DOWN）。例如首次启动通常只有 Redis/MySQL 可能在线，后端/项目一/前端是 DOWN——这是正常的。

### 3.2 离线 mock 启动（推荐日常演示）

```bash
cd agentflow-platform
.venv\Scripts\python.exe scripts/demo_up.py
```

- **预期输出（顺序）**：
  1. 顶部打印“AgentFlow 演示环境”，`知识库模式 : MOCK（内置周报语料，离线可跑）`。
  2. 逐个检查组件：Redis 已在运行就跳过；MySQL 未起会打印启动命令但不代启；后端/项目一/前端被拉起并打印各自 `pid=...`。
  3. 末尾等待 8010、8000 就绪，再次打印组件状态表。
  4. 给出演示入口：`API 文档 http://127.0.0.1:8000/docs`、`前端 http://127.0.0.1:5173/`，以及 `MOCK_EXTERNAL_RAG=true（内置语料）`。
- **怎么判断成功（关键标志）**：
  - 组件状态表中 **后端 8000 = OK、前端 5173 = OK**（项目一 8010 在 mock 模式下允许 DOWN，不影响演示）。
  - 浏览器能打开 `http://127.0.0.1:5173/`（见到登录页）。
  - `curl -s http://127.0.0.1:8000/healthz` 返回 `{"status":"ok"}` 之类 200 内容。
- **注意**：如果 Redis 未运行且本机有 docker，脚本会**尝试** `docker run` 拉起 `agentflow-redis-stack`；若 docker 不可用或你不想让它自动拉，请先按 §2.1 手动起好 Redis，再用 `demo_up.py --no-start` 仅做体检、不代启任何进程。

### 3.3 真实联调启动（real 模式）

> **前置**：项目一后端目录 `企业垂直知识库 Agent 后台` 必须存在且已建 `.venv`；MySQL/Redis 已在线。

```bash
cd agentflow-platform
.venv\Scripts\python.exe scripts/demo_up.py --real
```

- **预期输出**：顶部 `知识库模式 : REAL（项目一 8010 真实检索）`；后端以 `MOCK_EXTERNAL_RAG=false` 注入；末尾组件状态表中 **项目一 8010 = OK**。
- **怎么判断成功**：
  - 组件状态表中 **后端 8000 = OK、项目一 8010 = OK、前端 5173 = OK**。
  - 执行知识库探针（见 §7.3 或 §5.3）返回真实命中条数 > 0。
- **失败标志**：若项目一目录不存在或被跳过，状态表 8010 为 DOWN，此时 `kb-search` 会走“熔断 → 兜底”，real 模式不成立。

### 3.4 停止环境（演示结束或切换模式前）

```bash
cd agentflow-platform
.venv\Scripts\python.exe scripts/demo_up.py --down
```

- **预期输出**：逐个打印“停止 backend / project_one / frontend（pid=...）”，或直接提示“已不在运行”。
- **怎么判断成功**：`netstat -ano | findstr ":8000 :8010 :5173"` 应**无输出**（这三个端口被脚本释放）。
- **重要**：`--down` **只停本脚本记录的进程**，不会动 Redis / MySQL（底座留给你手动管理，避免误清数据）。切换 mock/real 模式前请先 `--down` 再重新启动。

## 4. Docker Compose 启动方式（备用，非推荐）

> 本机日常演示**优先用 §3 的 `demo_up.py`**。Compose 仅作为“完整容器化部署”参考，且本机存在 docker 权限限制，不能 blindly 一键拉起整套。

### 4.1 文件仅做语法校验（不要指望它自动跑通整套）

仓库提供三份文件：`docker-compose.yml`（主）、`docker-compose.dev.yml`、`docker-compose.prod.yml`。先用命令确认语法合法：

```bash
cd agentflow-platform
docker compose -f docker-compose.yml config > nul && echo "语法 OK"
```

- **怎么判断成功**：输出 `语法 OK`，无 YAML 报错。

### 4.2 需要手动执行的命令（比脚本更“重”）

```bash
# 三必需服务（mysql 3307 / redis 6379 / backend 8000）
docker compose up -d --build

# 可选：前端（compose 里是 Nginx 8080，需先 npm run build，且不是演示用的 5173）
docker compose --profile frontend up -d
# 可选：项目一真实检索（8010）
docker compose --profile project1 up -d
```

- **怎么判断成功**：`docker compose ps` 显示 `mysql / redis / backend` 状态为 `running`（healthy）。

### 4.3 停止

```bash
docker compose down          # 停止，保留数据卷
docker compose down -v       # 连数据卷一起清（慎用）
```

### 4.4 本机 docker 权限限制（务必注意）

- **Docker Desktop 必须处于“已启动且当前用户有权限”状态**；否则 `docker` 命令会报 `permission denied / daemon not running`。
- Compose 里的 **backend 是容器**，它依赖同网络的 Redis/MySQL 容器；但本机演示惯例是用**本地 Redis/MySQL 进程**而非容器版——两套不要同时起，避免端口/数据打架。
- Compose 的 **前端端口是 8080（Nginx）**，不是演示主线要求的 **5173**；若要走 §5 的 UI 主线，仍建议用本地 `agentflow-web` 的 `npm run dev`（5173）。
- 结论：**日常演示不要走 Compose**，用 §3 脚本最省心；Compose 仅用于“我想在干净容器里验证部署”的场景。

## 5. 完整演示操作主线（按顺序，一步一步）

> 以下每一步都是“**一个动作 + 一个判断成功标志**”。前端默认地址 `http://127.0.0.1:5173/`，采用 hash 路由（地址栏会显示 `#/xxx`）。演示账号统一用 `admin_user / Passw0rd!`。

### 5.1 登录

1. **动作**：浏览器打开 `http://127.0.0.1:5173/`，自动跳到登录页（`/#/login`）。在用户名、密码框分别输入 `admin_user`、`Passw0rd!`，点击「登录」按钮。
2. **预期现象**：**登录成功，跳转到工作台 `/#/dashboard`**，左上角显示当前用户 `admin_user`、角色 `admin`。
3. **怎么判断成功**：URL 变为 `/#/dashboard`，页面出现侧边栏菜单（工作台 / 新建任务 / 审批收件箱 / 评测与实验 / 记忆管理 / 工具注册表 / 系统设置）。
4. 备选（无 UI 时验证）：
   ```bash
   curl -s -X POST http://127.0.0.1:8000/api/v1/auth/login \
     -H 'Content-Type: application/json' \
     -d '{"username":"admin_user","password":"Passw0rd!"}'
   ```
   - 返回体 `data.access_token` 有值即登录成功。

### 5.2 工具注册表面板：启用 / 禁用 `kb-search` 并验证生效

1. **动作**：侧边栏点「工具注册表」（`/#/tools`）。
2. **预期现象**：页面列出 4 个内置工具（`kb-search` / `sql-query` / `chart-render` / `notify`），每项显示当前启用状态、入参/出参说明、最近变更。
3. **动作（禁用）**：找到 `kb-search` 行，点击其启停开关将其**置为禁用**，在确认框填一句原因（如「演示禁用」），确认。
4. **预期现象**：该行状态变为「禁用」，页面出现成功提示“工具 kb-search 已禁用（下一次新建任务生效）”。
5. **怎么判断成功（验证生效）**：
   - 在「工具注册表」页确认 `kb-search` 状态为禁用；
   - 新建一个会触发知识库检索的任务（目标里带“分析/归因/周报”等，见 §5.3），进入任务详情 → 轨迹，确认**没有 `kb-search` 的 `tool.call` 事件**（说明开关已过滤该工具）；
   - 回到「工具注册表」，再次把 `kb-search` **重新启用**，确认状态回到「启用」，后续新建任务又能正常调用。
6. **权限提示**：启停开关是**仅 admin 可写**（你已经用 admin 登录，可直接操作；若用 approver 登录则只能看不能改）。

### 5.3 新建任务，触发知识库检索（kb-search）

1. **动作**：侧边栏点「新建任务」（`/#/tasks/new`）。
2. **动作**：在目标（goal）框输入一个会驱动检索的目标，例如：
   > 分析上周数码配件 GMV 下滑原因，并给出品类归因与图表
3. **动作**：点击「提交 / 开始执行」。
4. **预期现象**：页面跳到任务详情（`/#/tasks/<id>`），右侧/底部出现**实时进度流（SSE）**，依次看到：Planner 生成子任务 → 某个子任务调用 `kb-search` → 拿到知识库片段 → Reviewer 打分 → 任务完成（流以 `complete` 帧收尾）。
5. **怎么判断成功（知识库检索确实触发）**：
   - 进度流或轨迹里出现 `kb-search` 的 `tool.call` / `tool.result` 事件；
   - mock 模式：返回的是内置周报语料片段（标题含“周报”之类）；real 模式：返回项目一知识库文档切片（`chunk_id`/`document_title`）。
   - 可用知识库探针二次确认链路（需 admin/approver 令牌）：
     ```bash
     TOKEN=$(curl -s -X POST http://127.0.0.1:8000/api/v1/auth/login -H 'Content-Type: application/json' -d '{"username":"admin_user","password":"Passw0rd!"}' | python -c "import sys,json;print(json.load(sys.stdin)['data']['access_token'])")
     curl -s "http://127.0.0.1:8000/api/v1/kb/status?probe=true" -H "Authorization: Bearer $TOKEN"
     ```
     返回 `probe.ok=true` 且 `chunks>0` 即链路通。

### 5.4 观察 Planner 生成子任务、调用知识库、Reviewer 打分

1. **动作**：在任务详情页（`/#/tasks/<id>`），找到「子任务列表 / 计划」区域与「评审」区域。
2. **预期现象**：
   - **Planner**：把目标拆成若干带序号的子任务，每个子任务标注工具提示（tool_hint）与风险等级（risk_level，普通为 normal，高危为 high）。
   - **知识库调用**：其中一个或多个子任务类型即 `kb-search`，点开可见检索入参与返回片段。
   - **Reviewer 打分**：在「评审」区域看到 Reviewer 给出的评分与结论（评分字段 `eval_score` / `review`），体现“自动质量门”。
3. **怎么判断成功**：子任务列表非空、至少一个子任务含 `kb-search`、且「评审」区有分数与结论文字。

### 5.5 构造一个会被“评审拦截”的任务 → 人工批注中断 → 重规划（核心看点）

> 机制说明（演示者心里有数即可）：当 Planner 生成了**高危动作子任务**（典型是 `tool_hint=notify`，即“推送/通知”类动作）时，系统会在 `human_gate` 节点挂起，进入 **AWAITING_APPROVAL（人工审批中断）**——这就是用户说的“Reviewer 拦截 / 人工批注中断”。在审批收件箱**填写批注（comment）并选择“驳回”**，批注会作为**硬约束**注入 Planner 触发**重规划**，新子任务会跟随批注变更。

1. **动作（构造高危任务）**：侧边栏点「新建任务」（`/#/tasks/new`），目标里**包含“推送运营群通知”**这类高危动作，例如：
   > 分析上周数码配件 GMV 下滑原因，并推送运营群通知
   - （这是脚本里固定的高风险目标 `GOAL_HIGH_RISK`；含“推送”即触发 `notify` 高危 → 审批中断。）
2. **动作**：点击「提交」。
3. **预期现象**：任务进入执行，Planner 生成子任务后，遇到 `notify` 高危子任务 → **进度流以 `interrupt` 帧收尾**（前端据此关闭连接、提示“待审批”）；任务状态变为 `AWAITING_APPROVAL`。
4. **动作（人工批注中断）**：侧边栏点「审批收件箱」（`/#/approvals`），能看到该任务条目，状态 `AWAITING_APPROVAL`，附阻断原因与高危子任务预览。点开该条目，在批注/意见框填写你的修改要求，例如：
   > 取数窗口与财务口径不一致，请改为仅做归因分析、去掉推送动作
5. **动作**：选择决策为「**驳回（REJECTED）**」，确认提交。
6. **预期现象**：系统据此**重规划（replan）**——Planner 重新生成子任务计划，新计划**去掉了“推送运营群通知”子任务**，改为纯归因分析，并体现出你批注里的约束。
7. **怎么判断成功（子任务跟随批注变更）**：
   - 任务详情的「子任务列表」中**不再出现 notify/推送类子任务**，且出现 `replan` 相关节点（轨迹里能看到 `node=replan, event=enter`）；
   - 任务 `replan_count` ≥ 1（可在详情或导出 JSON 里看到）；
   - 进度流最终以 `complete` 帧收尾，任务进入完成态。
8. **对比演示（加分项）**：若想展示“通过”路径，可在收件箱对该任务选「通过（APPROVED）」，任务会直接续跑至完成（无 replan）。两种决策都讲一遍，评委印象更深。

### 5.6 查看分层记忆管理页面（短 / 中 / 长期）

1. **动作**：侧边栏点「记忆管理」（`/#/memories`，仅 admin 可见）。
2. **预期现象**：页面默认列出中期（mid）/ 长期（long）记忆条目；顶部有「分层配置自检」入口可看三层开关与 TTL。
3. **怎么判断成功（三层都现身）**：
   - **短期（short）**：运行期缓存层（Redis），不在此管理页列出，但可在「配置自检」里看到 `short.backend=redis`；
   - **中期（mid）**：页面列表里 `scope=mid` 的条目（任务会话摘要，MySQL 存储，TTL 若干天）；
   - **长期（long）**：页面列表里 `scope=long` 的条目（高价值结论，落库 + 向量，永久或长 TTL）。
   - 若列表为空，先回头跑一个 §5.3 的完成态任务，再刷新本页——记忆是任务跑完后才写入的。
4. 进阶（可选）：在「记忆管理」用「相似度召回」功能输入一个目标，能看到命中的历史记忆被注入提示词（`hits` 非空）。

### 5.7 打开任务详情，查看完整轨迹、节点日志

1. **动作**：侧边栏「工作台」或「新建任务」历史里点开任意一个已完成/执行中任务，进入任务详情（`/#/tasks/<id>`）。
2. **预期现象**：详情页包含：基本信息（目标/状态/耗时）、子任务列表、评审结论、**完整轨迹（steps）**、**节点日志**。
3. **动作**：切换到「轨迹 / 节点日志」标签页，浏览 `state_update / tool_call / interrupt / complete` 等事件，点开某个 `tool.call` 看入参与返回。
4. **怎么判断成功**：能看到从 Planner → kb-search → Reviewer →（若有）human_gate → 完成 的完整事件链；`complete` 帧存在表示执行正常收尾。

### 5.8 执行导出：任务归档 JSON、轨迹 JSON，并简单校验

1. **动作（任务归档）**：在任务详情页找「导出」按钮（任务归档 JSON），点击，浏览器下载 `task-<id>-export-<时间戳>.json`。
2. **动作（轨迹）**：同样点「导出轨迹 JSON」，下载 `task-<id>-trace-<时间戳>.json`。
3. **预期现象**：两个文件落到本机下载目录，文件名以 `task-<id>-export-` 和 `task-<id>-trace-` 开头。
4. **怎么判断成功（简单校验）**：
   - 用记事本/编辑器打开，确认是合法 JSON（首行含 `"schema": "agentflow.task_export.v1"` 或 `"agentflow.trace_export.v1"`）；
   - 任务归档含 `task / subtasks / review / approvals / trace` 等字段；轨迹文件含 `steps / checkpoints / interrupt`。
   - 命令行快速校验（Windows PowerShell）：
     ```powershell
     Get-Content task-<id>-export-*.json | ConvertFrom-Json | Select-Object schema, exported_at
     ```
     能解析出 `schema` 即文件有效。
   - 等价接口（无 UI 时）：`GET /api/v1/tasks/<id>/export` 与 `GET /api/v1/tasks/<id>/trace/export`，响应头带 `X-AgentFlow-Schema`。

### 5.9 限流演示：高频调用触发 429，查看 `Retry-After`

> 限流分层：普通接口 300/分钟；**LLM 类（建任务 / 续跑 / 批量审批）30/分钟**；知识库 60/分钟。超限返回 **HTTP 429 + `Retry-After` 头**。

- **推荐做法（改小阈值，演示最干净）**：临时把 `.env` 里 `RATE_LIMIT_LLM_PER_MINUTE` 改成 `5`，保存后 `--down` 再重启后端（§3.2）。之后第 6 次快速调用即触发 429，演示完改回原值即可。
- **不改配置的做法（循环压测）**：对任一 LLM 类接口（如 `POST /api/v1/tasks/<id>/resume` 或 `POST /api/v1/tasks/stream`）在 60 秒内连续打 31+ 次。

1. **动作（不改配置的循环示例）**：先拿令牌，再对 `resume` 高频调用（对已完成任务会返回 409，但仍消耗 LLM 配额，最终触发 429）：
   ```bash
   TOKEN=$(curl -s -X POST http://127.0.0.1:8000/api/v1/auth/login -H 'Content-Type: application/json' -d '{"username":"admin_user","password":"Passw0rd!"}' | python -c "import sys,json;print(json.load(sys.stdin)['data']['access_token'])")
   for i in $(seq 1 35); do
     code=$(curl -s -o /dev/null -w "%{http_code}" -X POST http://127.0.0.1:8000/api/v1/tasks/1/resume \
       -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
       -d '{"decision":"APPROVED"}')
     echo "第 $i 次 -> HTTP $code"
   done
   ```
2. **预期现象**：前若干次返回 `200` 或 `409`，**之后出现 `429`**。
3. **怎么判断成功（看响应头）**：对触发 429 的那次请求加 `-D -` 看响应头，确认存在：
   ```
   HTTP/1.1 429
   Retry-After: <剩余秒数>
   X-RateLimit-Limit: 30
   X-RateLimit-Remaining: 0
   X-RateLimit-Reset: <秒>
   ```
   且响应体 `code:"RATE_LIMITED"`。
4. **收尾**：演示完把 `RATE_LIMIT_LLM_PER_MINUTE` 改回 `30`（若改过），并 `--down` 重启后端恢复。

## 6. 断点持久化演示专项（关后端 → 重启 → 恢复不丢）

> 前提：Redis 必须**全程在线**（断点存在 Redis checkpointer，TTL 72h）；**只关后端，不要关 Redis/MySQL**。

1. **动作（跑到人工中断）**：按 §5.5 步骤 1–3，提交高危任务（含“推送运营群通知”），等进度流以 `interrupt` 帧收尾、任务状态变为 `AWAITING_APPROVAL`。**先不要审批。**
2. **动作（主动关闭后端）**：
   - 若后端是 `demo_up.py` 拉起的：查 `agentflow-platform\storage\_demo_pids.json` 里的 `backend` PID，用 `taskkill /PID <pid> /F` 结束；或直接关掉启动后端的那个终端/进程。
   - **怎么判断后端已关**：`curl -s http://127.0.0.1:8000/healthz` 连接失败 / 无响应。
3. **动作（重启后端）**：
   ```bash
   cd agentflow-platform
   .venv\Scripts\python.exe scripts/demo_up.py        # mock 模式
   # 或 .venv\Scripts\python.exe scripts/demo_up.py --real   # real 模式
   ```
   - 脚本检测到 8000 已空，会重新拉起后端；Redis/MySQL 保持原样。
4. **动作（进收件箱恢复）**：浏览器打开 `http://127.0.0.1:5173/#/approvals`，刷新页面。
5. **预期现象**：**刚才那个 AWAITING_APPROVAL 的任务仍然在收件箱里**（说明断点没丢）；点开它，选「通过（APPROVED）」提交。
6. **怎么判断成功（断点不丢失）**：
   - 重启后端后，收件箱仍能列出该待审批任务（若丢失会显示空）；
   - 点击「通过」后，任务从断点处**续跑至完成**（进度流第二段以 `complete` 收尾），而不是从头重跑或报错。
   - 关键验证点：**Redis 没被关**是前提；若你误关了 Redis，断点会丢，任务恢复会失败——这正是要演示的“底座重要性”。

## 7. 常见故障排查

### 7.1 端口占用（8000 / 8010 / 5173 / 3307 / 6379 起不来）
- **现象**：启动脚本报“端口已被占用”或组件状态 DOWN，且你确认没起对应服务。
- **定位**：`netstat -ano | findstr ":<端口>"` 拿到 PID，`tasklist /FI "PID eq <PID>"` 看进程名。
- **处理**：若是旧 demo 残留，按 §8 清理；若是别的程序占用，改端口或结束占用进程后再启动。**不要误杀系统 `MySQL80`（3306）**。

### 7.2 401 鉴权失败
- **现象**：调用接口返回 401，或前端一直弹回登录页。
- **原因**：令牌过期（access 默认 2h）/ 账号密码错 / 演示账号未播种。
- **处理**：
  1. 确认账号已播种（§2.3）；
  2. 重新登录拿新 token；
  3. 前端清掉 localStorage 里的旧 token（退出登录或浏览器清站点数据）再登录。

### 7.3 知识库探针不通（real 模式）
- **现象**：`GET /api/v1/kb/status?probe=true` 返回 `probe.ok=false` 或 `degraded=true`，或 `kb-search` 走“熔断→兜底”。
- **原因**：项目一 8010 没在线 / `EXTERNAL_RAG_BASE_URL` 不对 / 服务账号未配置。
- **处理**：
  1. `curl -s http://127.0.0.1:8010/openapi.json` 确认项目一在线；
  2. 确认后端是以 `--real` 启动（`MOCK_EXTERNAL_RAG=false`），且 `.env` 的 `EXTERNAL_RAG_BASE_URL=http://127.0.0.1:8010`、`EXTERNAL_RAG_KB_ID=6`；
  3. 若只是想离线演示，直接改用 mock 模式（不带 `--real`），无需项目一。

### 7.4 SSE 无 `complete` 帧（进度流不结束）
- **现象**：任务详情的实时流一直转圈，始终不出现 `complete`，任务卡在运行态。
- **原因**：任务其实是被 `interrupt` 挂起（正常！属人工审批中断，不是 bug）；或后端进程异常退出；或前端与后端连接被代理缓冲。
- **处理**：
  1. 先看任务状态是不是 `AWAITING_APPROVAL`——是的话去「审批收件箱」审批即可，流本就该以 `interrupt` 收尾；
  2. 确认后端进程还活着（`/healthz`）；
  3. 若用反向代理/Nginx，确认已关缓冲（`X-Accel-Buffering: no`，本后端已带此头）；
  4. 实在卡死：在任务详情用「取消」终止，重新建任务。

### 7.5 限流 429（非演示目的误触）
- **现象**：正常操作也偶发 429。
- **处理**：看 `Retry-After` 头，等待对应秒数再试；或确认没有脚本/循环在刷接口；必要时调大 `.env` 里对应配额（`RATE_LIMIT_LLM_PER_MINUTE` 等）并重启后端。

### 7.6 MOCK 开关切换不生效
- **现象**：明明用了 `--real`，知识库还是返回内置语料（或反之）。
- **原因**：混用了不同启动方式——`demo_up.py` 的开关只注入到**它自己拉起的后端子进程**，不会改 `.env`；如果你另开了一个手启的后端，它读的是 `.env` 里的静态值。
- **处理**：统一用一种方式。切换 mock/real 前先 `demo_up.py --down`，再带对应参数重启；确认启动日志里打印的 `MOCK_EXTERNAL_RAG=...` 与你的意图一致。

### 7.7 分层记忆不写入
- **现象**：「记忆管理」页中期/长期列表为空，连跑完的任务也不产生记忆。
- **原因**：`ENABLE_LAYERED_MEMORY=false`（功能未启用，查询会返回空且写操作返回 503）；或任务未跑到完成/未达写入阈值（长期记忆要求评审分达到一定阈值才归档）。
- **处理**：
  1. 确认 `.env` 的 `ENABLE_LAYERED_MEMORY=true` 且后端已重启；
  2. 先跑一个**完整完成**的任务（§5.3），再回记忆页刷新；
  3. 长期记忆有最低评审分门槛，低分词任务不会进长期层——属正常设计。

### 7.8 前端白屏 / 模块 0 字节（额外提示）
- **现象**：浏览器报 `does not provide an export named 'XXX'`，但源码导出正常、`vue-tsc` 全绿。
- **原因**：dev server 内存模块图缓存里该模块被写成 0 字节（编辑工具快速写多文件时的竞态）。
- **处理**：重启 dev server + 清 `node_modules/.vite`，浏览器 `Ctrl+Shift+R` 强刷；项目已提供 `npm run dev:clean` 与 `npm run doctor` 辅助。

## 8. 收尾：环境清理步骤

演示结束或要切换模式时，按以下顺序清理，避免残留进程占用端口：

1. **停脚本拉起的服务**（后端/项目一/前端）：
   ```bash
   cd agentflow-platform
   .venv\Scripts\python.exe scripts/demo_up.py --down
   ```
   - 判断成功：`netstat -ano | findstr ":8000 :8010 :5173"` 无输出。
2. **Redis / MySQL（底座，按需）**：若你是用 docker 起的 Redis，`docker stop agentflow-redis-stack`；MySQL 若是手动 `mysqld`，结束对应进程即可。**二者数据目录不要删**，下次演示直接复用。
3. **前端 dev server**：若你是手动 `npm run dev` 起的，在对应终端 `Ctrl+C` 结束。
4. **残留兜底**：若仍有端口占用，按 §7.1 定位 PID 并 `taskkill /PID <pid> /F`。
5. **切换模式**：要换 mock/real，先完成以上清理，再回到 §3.2 / §3.3 重新启动。
