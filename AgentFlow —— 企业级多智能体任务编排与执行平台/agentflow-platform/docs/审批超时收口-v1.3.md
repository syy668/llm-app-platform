# 审批超时收口 · v1.3

> 面向 PRD **L98 / L245 / L382** 三条验收标准的落地说明：`审批挂起超过 24h → approval 置 EXPIRED
> → task 转 FAILED（可一键重新发起）`。
> 这部分此前**完全未实现**：`expires_at` 从 `approval_service.py:56` 写入之后，全代码库无人读取它做判定；
> 唯一会置 EXPIRED 的 `expire_pending_approvals()` 只在**取消任务**时被调用一次（task 级，非时间驱动）。
>
> 本文示例均来自本机 uvicorn → MySQL 3307 的真实响应。

---

## 0. 缺陷实证：为什么这件事必须现在做

排查时库里存在 5 张 PENDING 审批单，全部超期 3 天。它们分成两类，危害不同：

| 类型 | 特征 | 实测样本 | 后果 |
|---|---|---|---|
| **死锁单** | 任务仍 `AWAITING_APPROVAL`，但 Redis 断点已被 72h TTL 清空 | `#4`（task#10） | `GET /tasks/10/interrupt` 返回 `paused=false, resumable=false`；批准必 409 `TASK_NOT_PAUSED`，又永不消失 → **侧边栏红点常亮** |
| **孤儿单** | 任务早已 FAILED/COMPLETED，审批单却还是 PENDING | `#5~#8`（task 11~14） | 「已处理」列表看不到、待办里也批不动，纯脏数据 |

关键时间窗（决定了**必须**用定时器，而不是"打开页面时惰性收口"）：

```
t+0h      审批单创建，expires_at = t+24h
t+0~24h   ✅ 正常可批
t+24h     ⚠️ 审批失效（但断点还在）
t+24~72h  🔶 唯一救援窗口：断点仍可恢复，任务可以"从最近 checkpoint 重发"
t+72h     ❌ Redis 断点被 TTL 清空 → 任务永久救不回来（task#10 就死在这里）
```

审批 TTL(24h) 比断点 TTL(72h) **短 48 小时**。惰性收口一旦拖过 72h，就不是"晚一点收口"，
而是"这个任务永久废掉"。所以定时器是唯一正确解。

## 1. L1 定时收口：`sweep_expired_approvals()`

实现：`app/services/interrupt_service.py`；调度：`app/main.py::lifespan` 拉起后台协程
（`start_approval_sweeper` / `stop_approval_sweeper`），**启动即扫一次**，之后每 `APPROVAL_SWEEP_INTERVAL_SECONDS`（默认 300s）。

### 1.1 收口动作矩阵

| 判定 | `approvals.status` | `tasks.status` | `tasks.error` | Redis 断点 |
|---|---|---|---|---|
| **超时** 且任务仍 `AWAITING_APPROVAL` | → `EXPIRED` | → `FAILED` | `{code: APPROVAL_EXPIRED, …}` | 删除（三族键） |
| **孤儿**（任务已在其他终态） | → `EXPIRED` | **不动** | **不动**（不许覆盖原 error） | 不动（任务自己负责） |
| 未超时 / `expires_at IS NULL` | 不动 | 不动 | 不动 | 不动 |

`approvals.decided_at` 在收口时写入当前时间。理由：EXPIRED 没有真实决策人，但「已处理」列表按
`decided_at DESC` 排序，NULL 在 MySQL 里会全部沉到末尾；同时前端「已过期」页签需要展示"失效时间"。

### 1.2 级联清理：为什么直接删 Redis 键

`clear_interrupts()` 才是"打死断点"的标准写法（写一个 `next` 为空、`interrupts` 清空的墓碑 checkpoint），
但它需要一个 graph 实例，而后台定时器里 `get_w3_runtime()` 会把 **4 个 MCP 子进程**拉起来——
每 5 分钟一次不可接受。

因此 L1 直接删键（`checkpoint` / `checkpoint_blob` / `checkpoint_write` 三族，
按 `:{task_id}:` 精确前缀，避免 `checkpoint:1:` 误伤 `checkpoint:10:`）。这样达成的两条不变量与墓碑方案等价：

1. 终态任务不可能再 resume——`ensure_resumable` 另有状态闸（`RESUMABLE_STATUSES = {AWAITING_APPROVAL}`），双保险；
2. `GET /tasks/{id}/interrupt` 不会再对已失败任务报 `paused=true`（真正的"僵尸视图"来源）。

代价：该任务无法"从最近 checkpoint 续跑"，退化为从头执行——PRD L317 明确允许"快照丢失则从头执行"。

### 1.3 启动日志（真实）

```json
{"msg": "approval_sweeper_scheduled", "interval_s": 300}
{"msg": "approval_sweeper_started", "interval_seconds": 300}
{"msg": "approval_sweep_done", "expired_approval_ids": [4, 5, 6, 7, 8], "failed_task_ids": [10],
 "orphan_approval_ids": [5, 6, 7, 8], "checkpoint_keys_deleted": 0}
```

> `checkpoint_keys_deleted: 0` 是**正确结果**，不是失败：task#10 的断点早已被 72h TTL 清空，
> 这正是它死锁的原因（删除幂等，删 0 个也说明"僵尸复活的路已经堵死"）。

## 2. L2 批准前二次校验：`409 APPROVAL_EXPIRED`

定时器最长有一个扫描周期的滞后（默认 5 分钟）。这段窗口里，过期单在库里仍是 `PENDING`，
如果不加闸，就会出现"倒计时显示已过期、却还能点通过"。

`approval_service.apply_decision` 入口处：

```
PENDING 且 expires_at < now  →  落 EXPIRED（decided_at=now）  →  raise 409 APPROVAL_EXPIRED
```

**顺手落 EXPIRED** 是刻意的：即使定时器挂了，第一个撞上来的审批动作也会把状态纠正过来（自愈）。

错误响应：

```json
{
  "code": "APPROVAL_EXPIRED",
  "message": "审批单已超过 24h 有效期，不能再批准；请让任务创建人重新发起",
  "detail": {"approval_id": 4, "expires_at": "2026-10-23T04:31:03"},
  "trace_id": "…"
}
```

> 与 `APPROVAL_STALE` 的区别：`STALE` 是"审批单与当前断点不一致（有人已经批过了）"，
> `EXPIRED` 是"审批单本身过期"。前端可据此给不同引导（STALE→刷新重试，EXPIRED→重新发起任务）。

## 3. L3 收件箱口径（红点能真正归零）

### 3.1 `GET /api/v1/approvals`（缺省 = 待处理收件箱）

**口径变更（v1.3）**：只返回 **未过期** 的 PENDING 单。

| 条件 | 是否计入待办 / 红点 |
|---|---|
| `PENDING` 且 `expires_at > now` | ✅ 计入 |
| `PENDING` 且 `expires_at IS NULL` | ✅ 计入（无期限，避免历史数据突然消失） |
| `PENDING` 且 `expires_at <= now` | ❌ 不计入（落「已过期」页签） |
| 无 PENDING 单的 `AWAITING_APPROVAL` 任务 | ❌ 不计入 |

侧边栏红点数据源是 `data.total`（`stores/approval.ts`），所以这条口径直接决定红点数。

实测（收口前后）：

```bash
# 收口前
GET /api/v1/approvals  →  {"total": 5, "items": [...5 张超期单...]}
# 收口后
GET /api/v1/approvals  →  {"total": 0, "items": []}
```

### 3.2 列表项新增字段 `resumable`

```json
{
  "task_id": 10,
  "task_no": "AF20261022-0010",
  "status": "AWAITING_APPROVAL",
  "approval_id": 4,
  "reason": "高危动作需审批",
  "expires_at": "2026-10-23T04:31:03",
  "resumable": false
}
```

- `false` = **死锁**：Redis 断点已丢，点「审批」必然 409。
- 探活实现见 `probe_resumable()`：一次 `SCAN checkpoint:*` 建立存活 task_id 集合（`checkpoint:{task_id}:{ns}:{id}` 的第 2 段）。
- **fail-open**：非 Redis checkpointer（`CHECKPOINTER_BACKEND=memory`）、无 Redis 客户端、扫描异常、
  键数超 `_KEY_SCAN_CAP(5000)`，一律返回 `true`。宁可让用户点进去看到抽屉里的真实报错，也不凭空禁用入口。
- 前端契约：`resumable=false` 的行内「审批」置灰 + tooltip「任务已死锁，请走一键重发或归档」；
  批量通过 / 全选自动跳过这些行（避免制造"成功 3 失败 2"的噪音）。

### 3.3 `GET /api/v1/approvals?status=EXPIRED`（「已过期」页签，只读）

复用既有 G4 已处理列表端点，**无需新增接口**：

```bash
curl -s -H "Authorization: Bearer $TOKEN" \
  "http://127.0.0.1:8000/api/v1/approvals?status=EXPIRED&page=1&size=20"
```

真实响应（收口后的 6 条）：

```
total = 6
 #8 AF20261022-0014 过期=2026-10-23T06:34:51 失效=2026-10-26T04:26:03 决策人=None
 #7 AF20261022-0013 过期=2026-10-23T06:34:33 失效=2026-10-26T04:26:03 决策人=None
 #6 AF20261022-0012 过期=2026-10-23T06:34:23 失效=2026-10-26T04:26:03 决策人=None
 #5 AF20261022-0011 过期=2026-10-23T06:27:46 失效=2026-10-26T04:26:03 决策人=None
 #4 AF20261022-0010 过期=2026-10-23T04:31:03 失效=2026-10-26T04:26:03 决策人=None   ← 原死锁单
 #3 AF20261022-0009 过期=2026-10-23T04:28:27 失效=None                        ← 旧取消路径留下的，无 decided_at
```

> 最后一行是历史数据：`#3` 是被**取消任务**路径置 EXPIRED 的，当时没有写 `decided_at`，
> 因此「失效时间」显示 `—`。新收口路径都会写，前端无需特判。

## 5. 配置项（`app/core/w3_config.py`）

| 键 | 默认 | 说明 |
|---|---|---|
| `APPROVAL_SWEEP_ENABLED` | `true` | 关掉则不起后台协程（仅用于排查） |
| `APPROVAL_SWEEP_INTERVAL_SECONDS` | `300` | 扫描周期；下限强制 5s（防止配置成 busy loop） |
| `APPROVAL_SWEEP_PURGE_CHECKPOINT` | `true` | 收口时是否删断点键。关掉只影响排查便利，不影响正确性（`ensure_resumable` 另有状态闸） |

## 6. 测试覆盖

`tests/test_v13_approval_sweeper.py`（10 例，此前该链路**零覆盖**）：

1. 超时单 → 审批 EXPIRED + 任务 FAILED + `error.code=APPROVAL_EXPIRED` + `finished_at` 落值；
2. 未超时单 / `expires_at IS NULL` → 一条都不动；
3. 孤儿单 → 只关审批，**不覆盖**任务状态与原 `error`（防"顺手改坏别人终态"）；
4. 幂等：连跑两次，第二次零改动（定时器每 5 分钟跑一次的前提）；
5. L2 二次校验：过期 PENDING 直接批准 → `409 APPROVAL_EXPIRED`，且顺手落 EXPIRED、`decided_by` 仍为 NULL；
6. 未过期单仍可正常批准；
7. 收件箱口径：过期单不进列表、不进 `total`；
8. 收件箱条目带 `resumable`，内存 checkpointer 下 fail-open 为 `true`；
9. `probe_resumable` fail-open（空入参、无客户端）；
10. 收口后该任务不再残留 PENDING 单（不会"复活"回待办）。
