# 项目一 v1.11：溯源体验修复（「第 0 块」与「点了没原文」）

> 触发：用户点开对话里的溯源标签，连续弹出两条灰条
> `暂无可展开的原文（历史消息不回传来源）：《公司差旅报销制度.md》第 1 块 / 第 0 块`

## 一、结论：是设计缺陷，不是渲染 bug

提示语本身是 v1.10 我加的**降级文案**，但它暴露了三个叠加的设计问题：

| # | 问题 | 本质 |
|---|---|---|
| 1 | 显示「第 **0** 块」 | `chunk_index` 在库里是 **0-based**（`range(len(chunks))`），被直接拼进了给模型的上下文 → 模型原样抄出来 → 用户看到「第 0 块」。属于**内部实现细节外泄** |
| 2 | 点了永远是空 | v1.9/v1.10 的 `sources` 只在 SSE `done` 事件里随回答一次性下发，**没有落库**；页面刷新 / 重开会话后 `GET /conversations/{id}/messages` 拿不到 → 必然为空 |
| 3 | 明知没数据还做成可点 | 渲染层不判断 `sources` 是否存在，一律渲染成蓝色可点 chip（`cursor: pointer` + hover 变色）→ 诱导用户白点一次，再用 toast 告知"没有" |

第 2 条尤其致命：**只要刷新页面，所有历史回答的溯源全部失效**。v1.9 当时把这条列进了遗留项，现在用户正好撞上。

## 二、修复

### 1. 块号统一 1-based（`app/agent/tools/rag_tool.py`）

```python
def display_chunk_no(hit: dict) -> int:
    """存储序号（0-based）-> 展示序号（1-based）。"""
    idx = hit.get("chunk_index")
    if idx is None:
        return 0
    return int(idx) + 1
```

- `format_context()` 拼上下文时用 `第{display_chunk_no(h)}块`
- `to_sources()` 新增 `chunk_no` 字段（`chunk_index` 原值保留，便于排查）

这样**模型抄的号 / 用户看到的号 / 前端匹配用的号**三者完全一致，不会再出现「模型写第1块、前端按 chunk_index=1 去找、结果找到第二块」的错位。

### 2. 来源快照落库（`messages` 表加 `sources` JSON 列）

| 文件 | 改动 |
|---|---|
| `app/models/message.py` | `sources: Mapped[list \| None] = mapped_column(JSON, nullable=True)` |
| `app/schemas/conversation.py` | `MessageOut` 加 `sources: list[dict] \| None = None` |
| `app/services/agent_service.py` | `_write_message(..., sources=...)`；非流式 chat 传 `result["sources"]` |
| `app/services/stream_service.py` | 流式 done 前把 `sources` 一起写库 |
| `scripts/init_db.sql` | 建表语句同步加列 |

**为什么用 JSON 列而不是关联表**：`sources` 是「回答当时检索结果的**快照**」。文档之后被重新分块、甚至删除，历史回答仍应指向当时的块内容，而不是随关联表一起变化。JSON 列天然是快照语义，且不给 `document_chunks` 加外键压力。

**空列表统一存 NULL**：前端只需要判 `!sources?.length` 一种情况，不用区分 `[]` 和 `null`。

**已执行 DDL**：
```sql
ALTER TABLE messages ADD COLUMN sources JSON NULL COMMENT '引用来源快照' AFTER error_msg;
```

### 3. 无快照时降级为静态样式（`frontend_vue/src/utils/citation.ts`）

`renderAnswerHtml(content, sources)` 现在会先算 `clickable = !!sources?.length`：

- **有快照** → 蓝色 chip + `data-doc` / `data-cite` + `cursor: pointer` + 「点击查看该片段原文」
- **无快照** → 灰色静态 chip（`.is-static`）+ 无 `data-*` + `cursor: default` + 「本条回答未保留来源快照」

点击处理里再加一层 `if (target.closest('.is-static')) return` 兜底，双保险。

toast 文案也改了：不再对用户说"历史消息不回传来源"这种实现细节，改为「该条回答未保留来源快照，无法展开《X》第 N 块」。

### 4. 前端读取历史消息的 sources

- `src/types/index.ts`：新增 `MessageSource` 接口（含 `chunk_no`），`Message.sources?: MessageSource[] | null`
- `Chat.vue::loadMessages`：`sources: Array.isArray(m.sources) && m.sources.length ? m.sources : undefined`
- 抽屉块号显示改用 `sourceChunkNo(activeSource)`（优先后端 `chunk_no`，兜底 `chunk_index + 1`）

## 四、需要你知道的两点

1. **v1.11 之前产生的历史消息仍然没有快照**（库里那列是 NULL）。它们会渲染成灰色静态样式，不会再有"点了弹提示"的骚扰。要补也不行——当时的检索结果没有留存，无法追溯重建。
2. **块号口径变了**：库里 `chunk_index` 仍是 0-based（不动存量数据），只有对外展示和匹配变成 1-based。回答正文里模型写的「第1块」现在指向文档的第一块（以前指向第二块）。

## 五、顺带观察到的一个真实幻觉

端到端测试时，问「部门经理出差住宿补贴标准」，模型答出「三线城市 350 元/天（500 × 70%）」，而 `citation_misses = ['350']` —— 350 是模型自己算的，检索上下文里没有这个数。

这说明 v1.9 的 `citation_guard` **确实在工作**，标 `suspect=true` 是正确判断，不是误报。深层原因是知识库里两份制度的金额口径冲突（部门制 500/800/400/600/450 vs 普惠制 400/300），模型自己"融合"出了一套。要根治得靠冲突检测从 prompt 约束升级为后置检查，属于另一个议题。

# 补充：第二次截图 —— 灰色 chip 背后的更严重问题

> 触发：用户追问「去成都呢？」时，回答底部出现两个**灰色**溯源标签。

## 一、灰色本身是设计

该条消息 `route=direct`、`sources=None`，所以前端按 v1.11 的降级规则渲染成静态 chip。**视觉上「灰色 = 无快照 = 不可点」这个语义是对的**。

但顺着查下去发现了真正的问题：

## 二、直接回答路由在凭空贴出处

实测数据（会话 13）：

```
id=207  route=rag     sources=5   「研发部住宿标准 … 400 元/天（500 × 80%）」
id=208  用户          「去成都呢？」
id=209  route=direct  sources=None 「研发部去成都的住宿标准 … 400 元/天」
                                   来源：《公司差旅报销制度.md》第1块 / 第2块   ← 编的
```

**为什么 direct 还能答出内容**：`answer_node` 会把完整历史消息一起喂给 LLM，模型看到上一轮 rag 答案里有这些数字，就"接着答"了。这本身合理（多轮对话就该有上下文），问题在于它**顺手补了一句「来源：《X》第N块」** —— 本轮没有任何检索，这个出处是凭记忆贴的。

**为什么系统没发现**：`citation_guard.validate_citations` 原设计是「没有上下文就不校验」（避免拿空上下文比对数字导致全量误报），于是 **direct 路由成了校验盲区**，编造的来源标注永远不会被标记。

## 三、两层修复

### 1. 生成层：无检索结果时禁止标注出处（`app/agent/graph.py::answer_node`）

`tool_output` 为空时追加一条硬约束：

> 【本轮未检索知识库】本次为直接回答模式，你手上没有任何资料或数据。
> 严禁输出「[来源N]」「来源：《文档名》第N块」这类溯源标注——本轮没有可引用的资料，标注出处即属编造，会误导用户。
> 若答案来自上文对话中出现过的内容，请在相应位置注明「（依据上文回答，本轮未重新检索）」，不要标注文档与块号。

**效果实测（同一串追问，新会话 14）**：

```
Q: 研发部住宿标准   → route=rag     suspect=False  sources=5
                     尾部：来源：《公司差旅报销制度.md》第1块、第2块、第5块。

Q: 去成都呢？       → route=direct  suspect=False  sources=0
                     答案：去成都的话，研发部的住宿标准为 400 元/天（依据上文回答，本轮未重新检索）。
```

从"假装有出处"变成"明确声明这是上文记忆、没重新检索"。这比编一个块号诚实得多。

### 2. 校验层：无上下文却声称有出处 = 高置信度幻觉（`app/rag/citation_guard.py`）

新增 `_SOURCE_CLAIM_RE`，匹配 `[来源N]` / `来源：《X》第N块` / `《X》第N页`。

```python
if not context_text.strip():
    claims = [m.group(0).strip() for m in _SOURCE_CLAIM_RE.finditer(answer_text)]
    if claims:
        logger.warning("hallucination_suspect reason=source_claim_without_context ...")
        return {"suspect": True, "checked": 0, "misses": claims[:5]}
    return {"suspect": False, "checked": 0, "misses": []}
```

**为什么这条规则不会误杀**：正常直答（闲聊、换算、总结）根本不会出现「《文档》第N块」这种格式；一旦出现，只可能是模型凭记忆或臆想补的。数字比对仍然跳过（保留原来的防误杀逻辑）。

### 3. 视觉：静态 chip 改虚线边框

实心灰块容易被读成"禁用按钮"，改成 `1px dashed` 更接近"这是一个不可用的占位标注"。

  - 无上下文 + `[来源1]` → `suspect=True`

## 五、仍存在的路由抖动（未修）

同一串追问里，「去成都呢？」被判成 `direct`，「谁审批？」却判成 `rag`。目前靠上文记忆兜住了，但如果**上文没提过**这个问题（比如首轮就问「去成都呢？」），direct 就会答"没有资料"。

根治方向：**短追问继承上一轮的检索意图** —— 若上一轮 route=rag 且本轮是 ≤12 字的指代型追问（含"呢/那/还有/这个"），强制走 rag。需要 `agent_service` 把上一轮 assistant 的 `agent_route` 透传到 `classify_node`，属于路由层改动，未在本批实施。
