## 零、系统全貌与业务流转链路

> 先建立一个直观认知：这个系统不是一个"搜一下、吐一段字"的问答盒子，而是一个**会"看菜下单"的小团队**——它先判断你问的是什么类型的问题，再决定派谁去办、去哪办，最后还让一个"质量督导"检查完才交给你。

### 1. 核心能力版图（把代码翻译成人话）

| 能力 | 大白话解释 | 对应文件 |
|---|---|---|
| **智能调度** | 一个"前台调度员"，听你一句话就判断该派谁：查资料（rag）、查业务库（db_query）、出报表（report）、比一比（parallel_compare）、还是纯聊天（direct） | `app/agent/router.py`（意图分类）+ `app/agent/graph.py`（六节点 LangGraph 图）+ `app/agent/intent_inherit.py`（追问继承） |
| **精准检索** | 一个"图书管理员"，同时用「语义理解」和「关键词匹配」两条腿找资料，再按重要度融合排序 | `app/rag/retriever.py`（向量+BM25+RRF 融合 + 可选 Rerank）+ `app/rag/bm25.py` + `app/rag/vector_store.py` |
| **质量督导** | 一个"质检员"，回答出炉后逐条核对：数字对不对、出处真不真、资料冲突有没有并列说清 | `app/rag/citation_guard.py`（后置引用校验）+ `app/eval/metrics.py`（RAGAS 四指标打分）+ `app/agent/graph.py::_ANSWER_SYSTEM_PROMPT`（冲突死命令） |
| **安全防线** | 一扇"门禁"：谁能进（鉴权）、能查多少（限流）、钥匙会不会泄露（密钥掩码）、库表对不对（启动防呆） | `app/api/deps.py`（双 Token + RBAC）+ `app/api/rate_limit.py`（令牌桶限流）+ `app/core/runtime_config.py`（密钥掩码）+ `app/core/schema_check.py`（Schema 自检） |

### 2. 一次典型问答的「生命旅程」（大白话版）

**先说一个重要的事实（避免面试被拆穿）**：这个系统是 **「单路由」**——一次提问，调度员只会派**一个**人去办，不会同时查资料又查库又汇总。所以像"查差旅标准 + 查我这个月报了多少工单 + 生成汇总"这种**一句话塞三件事**的提问，系统会诚实地把它当成**三个独立的问题**，你得分三次问、它分三次答、各走各的路由：

- "差旅报销标准是什么？" → 走 **rag**（查文档）
- "我这个月报了多少工单？" → 走 **db_query**（查业务库）
- "生成一份工单汇总报表" → 走 **report**（出报表）

下面用一个**真正能一次走完整个流转**的问题，展示数据是怎么在节点间跑的。

---

**场景**：用户问——"对比一下《差旅报销制度 v2》和《差旅报销制度 v3》有什么不同？"

**第 1 步 · classify（调度员接单）**
`classify_node` 先看这句话——它没有"如何/怎么"这种操作词，就交给 LLM 分类器判断。分类器一读"对比""有什么不同"，立刻判定：`parallel_compare`（比一比）。
> 小知识：如果用户上一轮刚问过"差旅标准"，这一轮只追问"那 v3 呢？"（≤12 字、带指代词），调度员会**跳过 LLM、直接继承上轮路由**，省一次调用（`intent_inherit.py`）。

**第 2 步 · parallel_compare（拆成两路人马分头找）**
`parallel_compare_node` 先把这句话拆成两个检索词——"差旅报销制度 v2"和"差旅报销制度 v3"（LLM 拆，拆失败就按"和/与/vs"规则兜底切）。然后**开两个线程同时检索**：
- A 路去知识库找 v2 的相关内容；
- B 路去知识库找 v3 的相关内容。
两路各走一遍「向量 + BM25 + RRF 融合」的精准检索，最后把结果拼成「===== 资料 A ===== / ===== 资料 B =====」的合并上下文，并把两路的 `[来源i]` 标号**顺延重排**，避免撞号。

**第 3 步 · answer（把原料炒成菜）**
`answer_node` 拿到这份"两份资料并排"的上下文，交给大模型生成对比总结，并按"相同点 / 差异点 / 结论"输出。同时——因为 `_ANSWER_SYSTEM_PROMPT` 里写死了**冲突死命令**——如果两份制度在金额、天数上打架，模型**严禁自己二选一**，必须并列列出各自说法 + 注明各自来源。

**第 4 步 · 质检 + 留痕（出锅前的最后把关）**
- **引用溯源**：`citation_guard.validate_citations` 把答案里的长数字、日期、块号抽出来，和上下文逐一比对，对不上的标 `suspect`（只提醒、不拦截）。
- **全链路 Trace**：`tracing.py` 的 `TraceCallbackHandler` 把这趟旅程的每一步（路由、检索、token 用量、耗时、是否截断）记进 `trace_logs`，出了岔子能顺着 `trace_id` 一路追回去。

> **一句话总结全貌**：一个"调度员"（classify）听你的话决定派谁，一个"检索员"（rag/db_query/report/parallel_compare）去对应的库/文档里取货，一个"写手"（answer）把原料炒成答案，最后"质检员"（citation_guard）+ "账房先生"（tracing）把关留痕。**单路由、多分支、每步可查**，这就是它跟"套壳 RAG"最直观的区别。

## 一、真实应用场景与解决的问题

**1. 解决的业务痛点（结合代码场景）**

系统内置一套模拟业务库（`app/agent/tools/db_query_tool.py`：`biz_devices` / `biz_tickets` / `biz_alerts` 三张表），demo 文档含差旅制度、故障应急手册等（`samples/demo_docs/`），对应三类真实场景：

| 痛点 | 落地机制 | 证据 |
|---|---|---|
| 新员工查制度，口径不一、找不到出处 | RAG 检索 + 答案强制带「《文档》第N块」来源，前端渲染可点击引用卡片 | `app/rag/retriever.py` → `hybrid_retrieve` 返回 `document_title`/`chunk_index`；`graph.py` `run_agent` 返回结构化 `sources` |
| 运维查历史故障，追问时丢失上下文 | 短追问意图继承，跳过 LLM 直接沿用上轮路由 | `app/agent/intent_inherit.py::decide_inherit` |
| 查业务数据（设备/工单/告警）不想写 SQL | 关键词意图识别 → 只读 SELECT 返回结构化文本 | `db_query_tool.py::query_business_db` |

**2. 相比"单体 RAG 套壳"的本质区别**

- **混合检索**：向量 + BM25 双路召回，RRF 融合（`k=60`），而非单路向量 top-k（`retriever.py`）。
- **六节点 LangGraph 路由**：classify / rag / db_query / report / parallel_compare / answer，能查库、出报表、做 A/B 对比，不是"检索→拼 prompt→吐文本"一条道（`app/agent/graph.py`）。
- **防幻觉是产品级能力**：后置引用校验（`citation_guard.py`）+ 冲突检测死命令（`graph.py::_ANSWER_SYSTEM_PROMPT`），而非只靠 prompt 软约束。
- **权限与数据隔离**：双 Token + RBAC（`app/api/deps.py`、`app/core/security.py`），知识库 read/write 分级，禁用账号即时掉线。

## 二、核心功能实现清单

### 1. 文档解析与切分（复杂表格处理）
- **PDF 跨页续表回填**（`app/rag/loader.py::_extract_pdf_pdfplumber`）：判定"上一页表被页尾截断（`_PAGE_BOTTOM_RATIO=0.78`）+ 本页表从页首开始（`_PAGE_TOP_MARGIN=100pt`）+ 列数一致 + 首行含数字（`_looks_like_data_row`）"→ 回填上一页表头。
- **正文/表格原位交错**（`_page_blocks_with_tables`）：按表格 bbox 纵向切条带，解决"单元格被重复拼进正文 + 表格全堆页尾与标题脱节"两坑（实测天猫旗舰店重复出现 2 次、token 翻倍）。
- **DOCX 原位遍历**（`_extract_docx`）：按 `body` 子节点真实顺序遍历 `w:p`/`w:tbl`，表格不再漂到文末（实测从 151 字符漂到 804）。
- **分块表头回填**（`app/rag/splitter.py::_table_prefixes` + `_split_by_lines`）：含表格走行对齐切分（行不拦腰截断），每个从表格中段开始的块自动前置「表头行 + 分隔线」，并把前缀长度计入 chunk_size 预算；超长单行（PDF 一整段）退化为字符硬切（`splitter.py:168-177`）。

### 2. 多路混合检索（向量 + BM25 + RRF）
- **双路召回**（`retriever.py::hybrid_retrieve`）：向量 `vector_store.query` + BM25 `index.search`，各自取 top_k。
- **RRF 融合**：`fused[id] += 1/(60 + rank)`，两路 rank 累加后降序（`retriever.py:115-123`）。
- **可选重排**：`kb.rerank_threshold > 0` 时取融合前 `top_k*3` 候选，算查询-块余弦相似度过滤并重排（`retriever.py:128-150`）。
- **降级纯 BM25**（v1.14）：外部 embedding 不可用（欠费/密钥失效）时，BM25 索引是本地内存缓存、不依赖外部服务，降级后仍可检索，充值自动恢复（`retriever.py:82-97`）。

### 3. 幻觉治理（核心亮点）
- **后置引用校验**（`app/rag/citation_guard.py::validate_citations`）：
  - 抽取答案里的**长数字（≥3 位）+ 日期** → 归一化（去千分位、`年/月/日`→`-`、去前导零）→ 与检索上下文子串比对，未命中标 `suspect`。
  - v1.11 补「无上下文却声称出处」：`[来源N]`、`《X》第N块` 在 direct 路由（无检索）下只能是编造，硬判 suspect。
  - v1.13 补**块号校验** `check_chunk_refs`：答案声称的《文档》第N块与上下文真实下发的块集合比对，抄错块号也能抓。
  - 设计取舍：**只标记不拦截**（误判代价小、拦截代价是"答对也不给答案"）；拒答文案放行（"未找到"无事实主张）；1~2 位数字忽略（避免把 `[来源1]` 当事实）。
- **冲突检测死命令**（`graph.py::_ANSWER_SYSTEM_PROMPT` + `app/rag/llm.py::_CONFLICT_RULE`）：多份资料矛盾时**严禁自行取舍折中**，必须客观并列 + 逐条注明来源。针对"模型对冲突资料凭空裁决出一个权威结论"这种最隐蔽幻觉。

### 4. 自动化评测（RAGAS 四指标 + A/B + Badcase 飞轮）
- **RAGAS 四指标**（`app/eval/metrics.py`）：faithfulness / answer_relevancy / context_precision / context_recall。
- **A/B 对比**：勾选两个 run → `POST /eval/runs/compare`（`app/api/v1/eval.py`）出对比报告。
- **点踩转 Badcase**（`app/api/v1/chat.py::chat_badcase` → `eval_service.add_badcase_from_message`）：被点踩回答一键沉淀到按知识库聚合的「用户反馈Badcase」评测集（幂等、只允许上报自己的消息）。`reference_answer` 刻意留空（填错答案会让 RAGAS 把幻觉当标准答案反向打分），因此 `context_recall` 需人工补录后才能算。
- **低分样本后端筛选**：`GET /eval/runs/{id}/badcases`（`eval_service.list_badcases`），按指标阈值 SQL 侧过滤，NULL 不参与筛选。

## 三、开发过程中遇到的真问题及解决（重中之重）

### 深水区 Bug 1：跨页表格表头丢失（已解决）
- **【痛点现象】**：PDF 跨页续表，第二页的表格没有表头，检索命中后模型看到的是"无列名的裸数据"，无法回答"第几列是什么"。
- **【根因排查】**：`pdfplumber` 抽表是按页独立的，跨页的同一张表被拆成两个互不知情的 `Table` 对象，第二页首行是数据行而非表头。
- **【代码级方案】**：`loader.py::_extract_pdf_pdfplumber` 维护 `prev_header` / `prev_ended_at_bottom` 跨页状态，四条件判定回填表头；用"页面高度比例 0.78"而非固定留白（实测固定 80pt 会漏判）。

### 深水区 Bug 2：分块后表格行脱离列名（已解决）
- **【痛点现象】**：chunk 从表格中段切开，后半段的行没有表头，回答时列名缺失。
- **【根因排查】**：字符滑窗分块不管语义边界，表格行被拦腰截断。
- **【代码级方案】**：`splitter.py` 拆出 `_table_prefixes` 为表格区每行准备"块首前缀"，`_split_by_lines` 按整行打包 + 块首自动前置表头，并把前缀长度计入 chunk_size 预算（防止补表头把块撑超上限）。

### 深水区 Bug 3：并发状态错乱 / 取消被覆盖（已解决）
- **【痛点现象】**：用户刚创建评测就点停止，任务仍变成 running，取消失效；`with ThreadPoolExecutor` 退出时要等队列跑完，等于没取消。
- **【根因排查】**：① "读 pending→改 running→commit"三步竞态：线程读到 pending 后、写回前用户已改 cancelled，再写 running 把取消覆盖；② `with` 的 `__exit__` 固定 `shutdown(wait=True)`，阻塞等全部样本跑完。
- **【代码级方案】**：① 原子认领 `UPDATE ... WHERE status=pending`（`eval_service.py:1406-1413`），`synchronize_session=False`；② 取消时 `pool.shutdown(wait=False, cancel_futures=True)` + 先断 asyncio↔concurrent 桥接（`eval_service.py:1348-1373`），队列未开跑样本直接丢弃。

### 深水区 Bug 4：得分丢失 / 长文本截断 / 拒绝语态（已解决，共三个）
- **得分丢失**：v1.13.1 前计数器/缓冲区在 `try` 内，异常即随栈帧蒸发，实测 run 33「9/30 成功、0 条得分」；`EVAL_SCORE_BATCH_SIZE` 默认由 10 改 **1（每样本即时落库）**，缓冲区提到 `try` 外，异常路径先 `_flush_scores` 抢救（`eval_service.py:1392-1399`、`config.py:135`）。
- **长文本截断静默**：`max_tokens` 命中不抛异常（HTTP 200 + `finish_reason=length`），半截回答当完整结果落库；`app/llm/truncation.py` 统一探测 `finish_reason`/`stop_reason`，`answer_node` 追加提示、`tracing.py` 置 `is_truncated`。
- **拒绝语态错误**：v1.18 前 system prompt 写死"仅依据资料回答"，direct 分支（用户关了检索/闲聊）没资料时模型硬答"知识库中未找到相关信息"；改为**条件式约束**——有资料才限资料，无资料用自身知识正常答（`graph.py:41-47`）。

## 四、硬核工程化落地

### 1. 高可用与防呆
- **Schema 启动自检**（`app/core/schema_check.py`）：`SCHEMA_CHECK_MODE=strict` 启动比对 ORM `metadata` 与真实库，缺表/缺列生成 `ALTER TABLE ... ADD COLUMN` DDL 并 `SchemaDriftError` **fail-fast**；`import_all_models()` 显式导入全量模型避免漏检（`eval_*`/`trace_*` 靠间接导入注册）；NOT NULL 无默认值先按可空加再给"回填后收紧" DDL。
- **参数热更新**（`app/core/runtime_config.py`）：覆盖值存 `data/system_config.json`，原子写入（临时文件 + `os.replace`）+ 进程内 `RLock`；读取侧永不抛错，文件损坏回退默认；`get_value`/`get_config` 实时生效，LLM 工厂按配置签名重建 client（`app/llm/factory.py`）。
- **配置防篡改**（`runtime_config.py::_validate` + `_validate_api_base`）：枚举白名单（`llm_provider` ∈ mock/openai/anthropic）、范围校验、**占位符检测**（真实故障：管理员复制了 `https://{WorkspaceId}.cn-beijing.maas...` 未替换就保存 → DNS 解析失败 → 前端只报"连接超时"指向不了真因，现在保存时直接拒绝）。

### 2. 并发与性能
- **异步评测执行**（`eval_service.py::_run_eval_background`）：后台线程内 `asyncio` 事件循环 + `run_in_executor(ThreadPoolExecutor)`，`max_workers = EVAL_MAX_CONCURRENCY`（默认 2）防上游 429；`as_completed` 逐个回收、每样本即时落库 + 进度上报，整体耗时 ≈ `ceil(N/并发数) × 单样本`。
- **Redis 分布式令牌桶限流**（`app/api/rate_limit.py`）：Lua 原子脚本（HMGET 读 tokens → 匀速补充 → HSET 写回 → EXPIRE），按 `uid` 限流（默认 30/min）；**Redis 异常 fail-open 放行**（限流是防护手段，不能因缓存故障把问答打挂）；`rate_limit_status()` 供 `/health` 暴露限流真实状态（防"看起来开着其实没开"的盲区）。
- **SSE 流式输出**（`app/api/v1/chat_stream.py` + `app/services/stream_service.py`）：`StreamingResponse` 逐条 yield，事件 `route/delta/report/done/error`；mock 模型也真流式（`app/llm/mock.py` 支持 `_stream`）。

### 3. 数据安全与合规
- **API Key 掩码**（`runtime_config.py::SECRET_MASK`）：`get_config`/`get_value` 对 `_SECRET_FIELDS`（llm/embedding/eval 的 api_key）永远返回 `******`，真实值仅 `get_secret`/`get_override` 提供；提交掩码/空值视为"未修改"（`_is_masked`），避免前端回显覆盖真实密钥。
- **SQL 注入防护**（`db_query_tool.py`）：**仅执行只读 SELECT，不接受用户输入的任意 SQL**，关键词意图识别后走固定列白名单查询（`SELECT id, device_name, ... FROM biz_devices`）。
- **输入长度护栏**（`app/api/v1/chat.py::ChatRequest`）：`question` `min_length=1, max_length=4000`，超长 5000 字直接 422 拒绝，**不 OOM、不超时**（`docs/边界异常测试用例清单.md` IN-002）。

### 4. 可观测性（双 Trace 通道，非 OpenTelemetry）
- **请求级 TraceID**（`app/core/middleware.py`）：每个请求生成/复用 `X-Request-ID` → 挂 `request.state.trace_id` + 写 `ContextVar`，日志经 `TraceIdFilter` 自动带 trace_id，响应头回写 `X-Trace-ID`；**不读 body、不落库**，纯 stdout。
- **全链路 Trace 落库**（`app/core/tracing.py::TraceCallbackHandler`）：LangChain 回调挂到 LangGraph，采集各节点耗时（`on_chain_start/end`）、token 用量（`on_llm_end`）、路由、截断，`flush()` 写 `trace_logs`/`trace_tool_calls`；**写失败仅告警不中断主流程**。v1.18 修复 `model` 取值同源（配置页覆盖 > .env > 兜底），避免"实际用 qwen3.7 跑、Trace 记成 deepseek-chat"的归因错误。
- **排查"AI 乱回答"三步法**：看 `agent_route` 是否走对分支 → 看 `citation_misses`/`suspect` 是否命中引用校验 → 看 `is_truncated` 是否截断。

## 五、项目局限性与未来演进（坦诚局）

### 当前真实局限（2 个）
1. **截断的极端情况未完全兜住**：输出截断感知（`truncation.py`）能探测 `finish_reason=length` 并追加提示，但**无法阻止截断发生**——长报表/长答案仍会被 `LLM_MAX_TOKENS`（默认 2048）硬切断，只能靠"截断 + 明示"而非"完整输出"。且 `rerank_threshold` 默认 0（正负例余弦区间重叠，阈值难定），**无 cross-encoder 精排**，复杂语义排序有上限（`retriever.py`）。
2. **特定大模型/配置兼容边界**：① qwen3.x 思考模式（`reasoning_content` 前置）与判分温度不兼容，需显式 `enable_thinking=false`（`runtime_config.py:105-109`），否则首字延迟翻倍、判分失真；② 带日期后缀的模型名只有免费额度，403 `FreeTierOnly` 表现为"聊天正常但 RAGAS 全空"；③ embedding 换模型必须重跑文档处理（向量空间不同，`runtime_config.py:111`）。

### v2.0 演进方向
- **检索**：引入 cross-encoder 精排替代/增强余弦阈值，解决 RRF 后语义排序上限；中文分词 BM25 优化。
- **评测**：RAGAS ≥0.7 达标结论自动化重跑闭环（当前需人工用真实 LLM 跑黄金集）；Badcase 样本参考答案的自动补全（当前 `reference_answer` 留空需人工补录）。
- **上下文**：滑动窗口升级为"滚动摘要 + 记忆检索"混合，兼顾长程事实与成本（当前 `load_history_window` 5 轮/2000 字，超窗丢事实）。
- **安全**：refresh token 增加绝对过期上限（当前滑动续期无绝对上限，`deps.py:41` 自陈"持续访问可无限期留系统"）；补齐问答内容级 PII 脱敏（当前仅 API Key 掩码）。
