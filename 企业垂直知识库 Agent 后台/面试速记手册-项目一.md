# 项目一 · 求职面试速记手册（Cheat Sheet）

> 用法：面试前 30 分钟通读；每个模块都按「面试官可能问 → 你怎么答」组织。
> 数据口径：**222 个全绿测试**（v1.6 安全与基建重构后基线，150→222）、约 60+ 接口 / 18 张核心表。
> 技术栈一句话：FastAPI + LangGraph + 向量库 + MySQL/Redis + Vue3 前端，RAG + Agent 编排 + RAGAS 评测闭环。

---

## 模块 1：一句话介绍项目（电梯陈述）

**这是啥**：企业垂直知识库 Agent 后台，把企业内部的制度、运维手册、工单/设备/告警等业务数据，灌进一个"能问答、能查库、能出报表、能对比文档"的 RAG + Agent 系统，让员工用自然语言就能把分散在各处的知识捞出来，并带出处。

**比"套壳 RAG"强在哪**：它不是"把文档塞进向量库再丢给 GPT"那么简单——
- 检索层是**向量 + BM25 双路召回再做 RRF 融合**，解决"要么只懂语义、要么只懂关键词"的偏科；
- 回答层是 **LangGraph 六节点路由**，会先判断"你这是要查知识库、查业务库、出报表、还是对比文档"，再走对应链路，而不是一股脑塞给大模型；
- 还内置了 **RAGAS 自动评测**和**全链路 Trace**，能量化"答得准不准、上下文对不对"，而不是靠肉眼盲猜。

**核心业务价值**：把"找制度要问行政、查故障要翻手册、做报表要导 Excel"的隐性知识，变成"一句话问、秒级出答案带引用"的能力；对企业来说就是**降低新人培训成本、减少重复咨询、把专家经验沉淀成可检索资产**。

## 模块 2：应用场景与业务闭环

### 1. 能落地的真实业务场景（举例）
- **IT 运维故障处置**："上个月的服务器宕机故障怎么处理？" → 检索运维手册给出标准步骤 + 引用出处。
- **人事/行政制度问答**："年假怎么申请？报销标准是多少？" → 走知识库路由，避免员工反复打扰 HR。
- **业务数据即问即查**："上周有多少未关闭的高危告警？" → 直接查业务库返回结构化明细。
- **一键出报表**："生成本月工单汇总报表" → 查库 + 生成 Markdown 报表。
- **文档对比**："对比 A 方案和 B 方案的差异" → 两路并行检索后做对比总结。

### 2. 用户角色怎么划分
- **普通员工（role=user）**：建自己的知识库、上传/解析文档、发起问答、查看自己的会话与评测结果。
- **管理员（role=admin）**：在普通员工能力之上，还能做**系统配置**（切 LLM 厂商/模型、调限流阈值）、**用户管理**（禁用/启用/降级账号）、**查看全量 Trace 日志**、管理任意知识库。
- **知识库级细粒度权限**：除了角色，知识库还可以单独授 `read` / `write` 给用户——管理员、创建者、被授权者三层可见/可写，越权一律 403。

### 3. 对比"全文检索 / 百度搜索"的核心优势
| 维度 | 传统全文检索 / 百度 | 本系统 |
|---|---|---|
| 理解能力 | 关键词命中，不会"懂你意思" | 语义向量召回，问"服务器挂了咋办"也能命中"宕机处理流程" |
| 答案形态 | 丢给你一堆链接自己翻 | 直接给**答案 + 引用段落**，开箱即用 |
| 数据边界 | 百度搜不到企业内部资料 | 只检索**企业授权范围内**的私有知识，不泄露 |
| 多源打通 | 文档和数据库是两套 | 同一句话既能查知识库也能查业务库、出报表 |
| 可解释/可审计 | 无 | 每句回答都能回溯到哪篇文档第几段，且有 Trace 留痕 |

## 模块 3：核心业务流转链路（大白话版）

**例子**：员工问——"上个月的服务器宕机故障，该怎么处理？"

1. **路由分类（classify 节点）**：系统先用规则/LLM 判断意图。像"怎么处理/如何…"这种操作类问题会被**直接短路判为走知识库（rag 路由）**（既满足"操作问题必须查知识库"的业务约束，又省一次 LLM 调用、结果还更稳）。
2. **混合检索（rag 节点）**：在绑定的知识库里做**向量召回 + BM25 关键词召回**，用 RRF 倒数排名融合成 top_k 候选片段；知识库配了重排阈值时再按余弦相似度过滤噪声。拿到的是带 `文档标题/段落序号/原文/得分` 的片段列表。
3. **生成答案（answer 节点）**：把"用户问题 + 检索到的片段"拼进 Prompt，调大模型生成最终回答，并**强制要求标注来源**（"依据《IT运维操作速查》第 3 段…"）；如果检索不到就说"知识库中未找到相关信息"，绝不瞎编。
4. **带出处返回 + 全程留痕**：答案连同引用片段返回前端；同时**全链路 Trace**把这次"走了哪条路由、检索耗时多少、模型花了多少 token"落库，方便事后复盘"AI 是不是乱答了"。

> 补充：如果问题走的是其它路由，链路会变成——`db_query` 直查业务库、`report` 查库后直接出 Markdown 报表（不再走 LLM 合成）、`parallel_compare` 两路并行检索后合并对比。但**最终都汇聚到同一个 answer/输出环节**，结构清晰、易扩展。

## 模块 4：硬核技术栈与架构设计（选型理由版）

- **混合检索（向量 + BM25 + RRF 融合）｜为什么做双路召回？**
  *痛点*：纯向量检索对"精确术语/编号/专有名词"（如错误码 `ERR-503`）不敏感；纯 BM25 又不懂语义（"服务器挂了"匹配不到"宕机"）。
  *方案*：两路各取所长，用 RRF（倒数排名融合，k=60）把排名"加权投票"合成最终结果；可选再叠加向量余弦重排过滤低质片段。一句话：**语义和关键词两条腿走路，召回率和准确率都上得去。**

- **LangGraph 六节点路由｜为什么不用传统单向 Chain？**
  *痛点*：用户问题五花八门（查文档/查库/出报表/对比），一条线性 Chain 只能"检索→生成"一条路，遇到要查业务库或做对比就傻了。
  *方案*：六节点 = `classify` →（条件边分发）→ `rag` / `db_query` / `report` / `parallel_compare` → `answer` → END。classify 用 LLM 结构化输出做意图分类，条件边把请求扇出到正确工具，再汇回统一生成器。**一句话：用图的有状态路由替代写死的串行链，扩展新能力只需加一个节点，且每个节点天然可观测、可重试。**

- **RAGAS 评测体系｜为什么要在系统里内置评测？**
  *痛点*：RAG 上线后"答得准不准"靠人肉看，没法量化、没法回归。
  *方案*：内置 RAGAS 四项指标——**Faithfulness（不胡说）、AnswerRelevancy（答其所问）、ContextPrecision（检索够精准）、ContextRecall（检索够全）**；判分用的 judge LLM 也走统一工厂（temperature=0 保证可复现）。一句话：**把"回答质量"变成可度量、可对比的数字，每次改检索策略都能跑分看涨跌。**

- **双 Token 鉴权 + RBAC 权限｜怎么保证企业数据不泄露？**
  *痛点*：企业知识是机密，账号被盗、被禁用后还能源源不断拉数据，是最大的风险。
  *方案*：
  - **双 Token**：access_token（会话，短期 30min，存 Redis）+ refresh_token（7 天，带**黑名单**和**一次性轮换**，登出即拉黑、防重放）；
  - **RBAC**：角色（admin/user）卡住管理操作；知识库级 `read/write` 授权 + 归属校验（你只能看自己的会话、被授权的库）；
  - **每次请求回查数据库权威状态**（不用 Redis 快照当真理），被禁用/删除的账号**下一次请求立刻 401 并吊销会话**。一句话：**登录态可无感刷新，但权限与账号状态永远以数据库为准，禁用即时生效。**

- **统一 LLM 工厂（Factory）｜为什么把所有大模型调用收口？**
  *痛点*：早期 Agent 链路恒用 ChatOpenAI、RAG 自己维护原生 SDK、评测又 new 一个客户端——三套互不连通，配置页切厂商只对其中一条生效，导致"同一个系统两套回答口径"。
  *方案*：新增 `app/llm/` 作为**唯一出口**，provider 分发、密钥热更新、超时重试策略全收一处；mock 不是假对象而是实现了完整 LangChain 接口的真模型（断网也能演示/CI）。还加了一条**架构守卫测试**：除工厂文件外全仓库禁止出现 `ChatOpenAI(`，双轨想悄悄长回来 CI 直接红。一句话：**换模型/换厂商/切 mock 改一处配置即可，且不靠文档靠测试守住架构。**

## 模块 5：系统防御性亮点（面试高频考点）

### 1. 限流与 Redis 隔离——怎么防刷、怎么不和别的项目互踩？
- **防刷**：AI 类入口（会话问答、流式问答、`/kbs/{id}/query` 三个最贵入口）全部挂**Redis 令牌桶**（Lua 原子脚本，支持突发 + 匀速补充），按用户 ID 限流，默认 30 次/分钟，超限返回 **429**；阈值还能在系统配置页热更新。Redis 故障时 **fail-open 放行**（限流是防护手段，不能因缓存挂了把业务打挂）。
- **隔离**：项目独占 Redis **db1**（原先和另一个项目共用 db0，db0 里 1800+ 个键是别的项目 checkpoint），任一方 `FLUSHDB` 或键前缀撞车都会互相伤害——切到 db1 后物理隔离，互不干扰。
- **可观测**：`/health` 新增 `redis_backend`（real/fake）和 `rate_limit`（enabled/disabled/degraded），这是判断"限流到底开没开"的唯一可信来源。

### 2. 用户禁用与降级——管理员禁用账号后，员工怎么"立刻掉线"？
- *痛点*：早期鉴权只读 Redis 里的用户快照、从不回查库，加上会话滑动续期，导致"禁用"永久不生效。
- *方案*：`get_current_user` 在解析完 session 后**再查一次数据库主键单行**（只投影 5 个字段，实测 0.32ms，复用每请求已有的连接，不加缓存）；状态非 active 就**删除会话 + 401**，角色也以库为准（降级即时生效）。
- *为什么不加 60s 缓存*：会牺牲"立刻失效"的语义，而 0.32ms 的成本几乎可忽略——**用数据决策，不加**。

### 3. 配置恢复默认——怎么处理 `.env` 和系统配置页冲突？
- *痛点*：系统配置页的"覆盖值"优先级高于 `.env`，管理员保存过一次后，改 `.env` 就**永久失效且无恢复入口**（压测时自己撞出来的）。
- *方案*：新增 `DELETE /system/config/{key}`——删掉覆盖值即回退 `.env`/代码默认值，**无需重启**；语义上**幂等**（没覆盖值时也返回 200）、**未知键返回 404**（避免拼写错误被静默吞掉）、返回体与查询接口同形状前端可直接刷新；`GET` 额外返回 `overridden_keys`，界面显示"当前有几项是服务端覆盖值"并可一键恢复。

### 4. 全链路 Trace 追踪——怎么排查"AI 乱回答"？
- *方案*：通过 LangChain **回调处理器（TraceCallbackHandler）**挂到 LangGraph 上，**不改业务代码**就能采集：本次走了哪条路由、每个节点（router/rag_tool/db_query_tool/report_tool/parallel_compare）耗时多少、模型花了多少 token、是否出错；最终 `flush()` 落库到 `trace_logs` / `trace_tool_calls`，前端 `/traces` 可查看。
- *排查路径*：用户说"乱答"→ 打开该会话 Trace → 看 `route` 是不是判错了（比如本该查库却走了 direct）、看检索节点有没有返回片段、看 answer 节点的输入上下文——**三步定位是"路由错 / 检索空 / 模型飘"**。且 Trace 写入失败绝不影响主问答（fail-safe）。

## 模块 6：项目局限性与未来演进（坦诚局）

> 面试官最吃"能客观讲缺陷 + 有清晰演进路线"的候选人。下面两条是真实存在、且已在代码注释/重构文档里记录过的。

### 局限性 1：RAGAS 评测的"达标结论"尚未闭环
- 现状：内置了 RAGAS 四项指标，但**历史跑批是在 `LLM=mock` 且评测数据集与知识库不匹配下做的，分数没有实际语义**；要得到"≥0.7 达标"的可信结论，必须用真实 LLM 重跑。
- 未来：在系统配置页把 provider 切到 openai/anthropic 后跑基线评测，建立**评测数据集与知识库对齐**的机制，把"改检索策略→跑分看涨跌"做成常态化回归。

### 局限性 2：检索与解析仍偏"轻量"
- 现状：BM25 对中文是**按单字切分**（不依赖分词器，简单但粗糙）；重排序用的是"查询向量 vs 片段向量"的余弦相似度，**不是真正的 cross-encoder 重排器**；文档解析以文本切块为主，对复杂 PDF/表格/图片的深层结构化能力不足。
- 未来：引入中文分词或子词级 BM25、接入 cross-encoder 重排模型提升精排质量、补齐复杂文档（表格/图片/版式）的解析管线。

### 额外可聊的演进点（加分项）
- **token 绝对过期**：当前会话是"用一次续一次"的滑动续期，极端情况下持 token 可无限续期；建议加"签发绝对过期时间（如 12h），超时必须重新登录"。
- **多模态 / Agent 工具扩容**：六节点图已预留扩展位，后续可加"联网检索""调用内部 API"等新节点，而不动主干。

## 🎁 附赠：高频追问应答卡（直接口述版）

**Q：讲一个你排查过的线上隐患。**
> 后台有"禁用用户"功能，界面显示已禁用，但实测被禁用账号还能调接口。根因是鉴权只读 Redis 用户快照、从不回查库，而会话又滑动续期——两个单独看都合理的设计叠加，让"禁用"永久失效。修复是在依赖里加一次主键单行投影查询，按库状态判定并顺手删会话。团队担心性能，我先量了：单行投影 0.32ms，复用已有连接，比本地 Redis 一次 RTT 还便宜，所以**不加缓存**（加了反而让"立刻失效"退化成"最长 60 秒仍可用"）。最后我把新逻辑改回旧版跑了一遍，6 条核心用例全红，证明测试真抓得住问题。

**Q：怎么做架构治理？**
> 系统原先有三套 LLM 客户端，配置开关只对一条链路生效，同一系统两套回答口径。我做了统一工厂，把 provider 分发、密钥热更新、超时重试收在一处；mock 不是假对象而是实现完整 LangChain 接口的真模型，所以路由和流式在离线下照样跑。更关键的是加了**架构守卫测试**：除工厂文件外全仓库禁止出现 `ChatOpenAI(`，改回双轨 CI 直接红。用测试守架构，比文档靠谱。

**Q：讲一个只有压测才能发现的问题。**
> 把 Redis 从内存模拟切到真实实例后压测限流，发现"看起来开着、实际一条都没限"。原因是客户端句柄被缓存成全局变量、只读一次配置，运行期切后端后句柄还是模拟实现，而模拟实现不支持 Lua，令牌桶脚本抛异常后被 fail-open 吞掉——故障被静默降级成"完全不设防"。修复是每次比对期望后端、不一致就重建句柄。这事之后我给所有"降级"逻辑都加了显式告警，不允许静默。

**Q：怎么处理配置与默认值的关系？**
> 配置有两层：管理员保存的覆盖值优先级高于环境变量。压测时把阈值调低，发现环境变量再也不生效——覆盖值永久遮蔽了 env 且无恢复入口。我加了 `DELETE /system/config/{key}`：删除即回退 env，幂等、未知键 404、返回体同形状前端可直接刷新；查询接口加 `overridden_keys` 让界面显示"哪几项是覆盖值"并支持一键恢复。配置从此有了完整的读写删生命周期。

> 一句话收尾：这个项目我从 0 搭起，又在 v1.6 独立完成"把看起来能跑改成经得起追问"的安全与基建重构——**能写业务、能扛安全、能用量化数据做决策**，是我最想带去新团队的三件事。
