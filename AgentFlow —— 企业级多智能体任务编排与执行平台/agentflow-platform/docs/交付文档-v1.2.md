> 本文档面向**零基础初学者 / 交付验收人员**撰写，全程使用大白话，不堆砌技术黑话。
> 你不需要懂编程，只要照着读，就能明白这个系统是什么、能做什么、怎么验收。

## 第一部分：项目总览

### 1. 项目全称

**AgentFlow 多智能体任务编排平台**（对接企业垂直知识库「项目一」）。

一句话理解：它是一个"AI 员工调度中心"——你交代一个任务，它会自动拆成几步、调用企业自己的资料库去查信息、自己检查做得对不对，做错了还能让人插手改，最后把所有过程留档。

### 2. 项目背景

现在不少企业想用 AI 帮忙干活（查资料、答问题、跑流程），但遇到几个现实问题：
- 通用大模型不懂企业自己的业务资料；
- AI 说出来的答案没人把关，可能出错；
- 任务一旦跑一半崩了，只能从头再来。

本项目就是为解决这些"企业真要用 AI 干活"的场景，搭了一套**可编排（自动拆分步骤）、可评审（自动打分把关）、可人工干预（人能随时插手）**的多智能体任务平台，并且能对接企业自己已有的知识库系统（项目一）。

### 3. 现存痛点（大白话版）

在引入本项目之前，企业在用 AI 时普遍卡在这几件事上：

- **AI 不懂企业内部资料**：原来的智能体只会调用公共大模型，企业自己的业务文档、历史工单、内部规范它一概不知道，答出来的东西脱离业务实际，不顶用。
- **做完没人把关，容易出错**：任务跑完直接给结论，没有可信度评审机制，错了也发现不了，错误结论可能被直接拿去用。
- **出错只能推倒重来**：任务执行中途一旦失败，没有断点保存、也不能人工批注干预，只能从头再跑一遍，既费时又费钱。
- **工具想关关不掉**：系统里接了知识库、SQL 查询等能力，但缺少统一管控，不能灵活开启/关闭某个工具，也就没法管控风险。
- **多人一起用就崩**：并发访问没有限流，好几个人同时点，服务容易被压垮，大家都用不了。
- **数据留不下来**：只能在前端临时导出，没有服务端归档，任务跑完的轨迹没法留存、没法事后复盘。

### 4. 系统解决的核心问题（逐条对应上面的痛点）

| 上面的痛点 | 本系统怎么解决 |
|---|---|
| AI 不懂企业内部资料 | 接入「项目一」企业垂直知识库，智能体在拆解任务时能直接检索企业自有资料，答案贴合业务实际。 |
| 做完没人把关、容易出错 | 内置"评审节点"（Reviewer），对每个子任务自动打分并计算可信度，低质量结果能被识别出来。 |
| 出错只能推倒重来 | 全程保存"断点"（存在 Redis 里），任务跑到一半人工中断或进程重启，都能从断点恢复，不用重跑。 |
| 工具想关关不掉 | 新增"工具注册表"，管理员可以在界面上随时启用 / 禁用某个工具（如知识库检索 kb-search），风险可控。 |
| 多人一起用就崩 | 新增"全局限流中间件"，给每类接口设了调用上限，超了就临时拦住并提示稍后再试，保护服务不垮。 |
| 数据留不下来 | 新增"服务端导出"，任务跑完可一键导出"任务归档文件"和"执行轨迹文件"，留档复盘。 |

### 5. 适用场景

- **企业运维问答**：把运维手册、故障案例接进知识库，员工提问，AI 查资料后给出贴合业务的答案。
- **业务数据查询**：通过 SQL 查询类工具，让 AI 按自然语言去查业务库并汇总。
- **文档检索**：从企业文档库里精准检索相关片段，作为 AI 回答的依据。
- **自动化任务流水线**：把"拆解任务 → 查资料 → 评审 → 出结论"串成一条可重复的自动流水线，适合周期性、标准化的工作。

## 第二部分：整体技术栈清单（分层展示）

下面按"后端 / 智能体框架 / 中间件（含数据库）/ 前端"四层来说明。每一项都讲清楚**它是干什么的**以及**为什么选它**。

### 第一层：后端（负责接收请求、跑业务逻辑）

- **Python**：一门易读、生态丰富的编程语言，AI 领域绝大多数工具都用它写。
- **FastAPI**：后端框架，负责接收网页发来的请求、返回数据。它有两个对本题很重要的能力：
  - **异步接口**：同时处理很多请求不卡；
  - **SSE 流式输出**：结果像"直播弹幕"一样一段一段推到前端，不用等全部算完才显示，体验更顺。

### 第二层：AI 智能体编排框架（负责把多个 AI 串成流程）

- **LangGraph**：专门用来编排"多智能体任务链路"的框架。它做两件关键的事：
  - 把"规划师拆解 → 执行员查资料 → 评审员把关 → 总结员收尾"画成一张可执行的流程图（各智能体角色详见第四部分"多智能体阵容"）；
  - 支持**断点持久化**：任务跑到哪一步、当时的状态都存下来，中断后能接着跑（本项目把断点存在 Redis 里）。

### 第三层：中间件 / 数据库（负责存数据、做缓存、做限流）

- **MySQL**：传统关系型数据库，用来存正式的业务数据——任务、子任务、审批单、执行轨迹、记忆等（共 8 张表）。选它是因为稳定、可靠、大家都会用。
- **Redis Stack**：一种超快的内存数据库，本项目里身兼多职：
  - 缓存、限流计数、保存断点、短期记忆、工具注册表。
  - 必须用它自带的 **Redis Stack** 版本（含 RediSearch 搜索模块 + RedisJSON 模块），否则断点保存会降级成"内存模式"，后端重启后审批断点会丢。
- **项目一「企业垂直知识库」（外部对接）**：企业自己的业务资料系统，通过 **HTTP 接口**（像网页请求一样）对接，作为 AI 的"外部资料来源"。它不在本平台内，是独立系统。

### 第四层：前端（负责好看的网页界面）

- **Vue 3 + TypeScript + Vite**：前端三件套。
  - Vue 3 负责页面和交互；
  - TypeScript 让代码更稳、更少出 bug；
  - Vite 负责把代码快速打包成能打开的网页。
  最终呈现给用户的是一套可点击、能看轨迹、能管工具的网页控制台。

### 核心能力组件（本次新增的"能力积木"）

这些不是某一种技术，而是本平台组装出来的关键能力，初学者了解名字即可：

- **MCP 工具注册**：把"知识库检索""SQL 查询"等能力登记成可管理的工具。
- **全局限流中间件**：给每类接口设调用上限，超出就拦。
- **评审节点（Reviewer）**：自动打分 + 算可信度。
- **人工干预中断**：低分 / 高风险任务自动挂起，等人批注。
- **分层记忆**：把信息按"短期 / 中期 / 长期"分层次保存，让 AI 越用越懂业务。
- **SSE 长连接**：结果实时推送到网页。
- **服务端导出**：一键导出任务和轨迹的归档文件。

### 部署方案

提供两种方式，任选其一（详见第五部分）：

- **Python 一键启动脚本**（`demo_up.py`）：一行命令拉起演示环境，适合本地快速演示。
- **Docker Compose 容器化部署**：把服务打包成容器，适合正式环境批量化部署。

> **红线说明（请放心）**：本次 v1.2 的所有新能力，都是**新增的节点和配置开关**，没有改动原有的断点持久化、分层记忆、SSE 流式、知识库适配器，也没有改动评审节点的原有打分逻辑。也就是说，老功能一个没动，只是在它旁边"加了新功能"。

## 第三部分：完整功能交付清单（分模块，带验收效果）

下面 5 个模块就是本次 v1.2 迭代的全部交付项。每条都写三件事：**做了什么 / 运行后能看到什么现象 / 怎么确认它生效**。

### 模块 1：MCP 工具注册管理（P0 核心功能）

- **做了什么**：新增"工具注册表面板"。系统把每个外部能力（如知识库检索 `kb-search`、SQL 查询等）登记成一个可管理的"工具"，管理员可以在界面上**单独启用或禁用**任意一个工具。工具的开关状态实时保存在 Redis 中。
- **运行后能看到什么现象**：在前端"工具注册"页面，能看到一张工具清单，每个工具有"启用 / 禁用"开关。把 `kb-search` 关掉，再去建任务，AI 就不会去查知识库了；重新打开，任务又能正常检索。
- **怎么确认功能生效**：
  1. 打开工具注册页面，确认列表里有 `kb-search`；
  2. 把它的开关从"启用"切到"禁用"并保存；
  3. 新建一个会触发检索的任务，观察它**不再调用**知识库（轨迹里没有检索步骤）；
  4. 再切回"启用"，重复建任务，确认检索恢复正常。

### 模块 2：全局限流防护中间件

- **做了什么**：新增一道"大门"——全局限流中间件。它按接口类型分别设了每分钟调用上限（默认值如下，可在配置里调）：
  - 普通接口：**300 次 / 分钟**
  - 会驱动 AI 的接口（建任务、断点续跑等）：**30 次 / 分钟**
  - 知识库检索接口：**60 次 / 分钟**
  - 单个任务维度的总闸门：**240 次 / 分钟**
  
  超过上限时，系统返回 **429（太多请求）**，并在响应头里带上 `Retry-After`（告诉你要等多久再试）。健康检查、接口文档等路径在白名单里不会被限流。
- **运行后能看到什么现象**：短时间内高频调用某个接口（比如连点"建任务"），当次数超过上限，接口不再正常返回数据，而是返回 429，并能从响应头里看到 `Retry-After` 提示。
- **怎么确认功能生效**：
  1. 用工具连续高频调用"建任务"这类 AI 接口，超过 30 次 / 分钟；
  2. 观察返回码变成 **429**；
  3. 检查响应头里是否带有 **`Retry-After`** 字段，有即为生效。

### 模块 3：评审可信度计算 + 人工批注干预节点

- **做了什么**：在原有"评审节点（Reviewer）自动打分、计算可信度"的基础上，**新增了一个"人工批注干预节点"**（通过 `REVIEW_HUMAN_INTERVENTION_ENABLED` 开关控制）。当某个子任务评分偏低、或被判定为高风险（例如"推送通知"类操作），任务会自动**挂起**为 `AWAITING_APPROVAL`（等待审批）状态。审批人在"收件箱"里看到后，可以填写**批注**并驳回；这条批注会作为"硬约束"交给规划智能体重新规划，子任务会**跟着批注的要求改变**。
- **运行后能看到什么现象**：构造一个会被评审拦截的任务（例如包含"推送运营群通知"这类高风险步骤），任务跑到该步骤会停住、进入"等待审批"。在收件箱填写批注（比如"不要推送，改成仅生成草稿"）并驳回后，系统会重新规划，新生成的子任务遵循批注要求。
- **怎么确认功能生效**：
  1. 提交一个含高风险步骤的任务，确认它停在 `AWAITING_APPROVAL`；
  2. 进入收件箱，填写批注并选择"驳回"；
  3. 观察系统触发**重新规划**，且新的子任务确实按批注内容调整（例如不再出现推送步骤）。

> 注意：评审节点的**原有打分逻辑没有改动**，本次只是"在它后面接了一个新的干预环节"，属于新增节点，不触碰老代码。

### 模块 4：任务与轨迹服务端导出功能

- **做了什么**：新增两个**只读**的导出接口（不会触发任何执行，只是把已经跑完的任务数据打包下载）：
  - **任务归档导出**：包含任务基本信息、子任务、评审结论、审批单、精简后的执行轨迹，文件名形如 `task-<任务ID>-export-<时间戳>.json`；
  - **轨迹导出**：纯执行轨迹（每一步、检查点、中断点），文件名形如 `task-<任务ID>-trace-<时间戳>.json`。
- **运行后能看到什么现象**：在任务详情页点"导出"，浏览器会下载一个 JSON 文件。打开后能看到这次任务从头到尾干了什么、每一步结果、谁审的、怎么批的。
- **怎么确认功能生效**：
  1. 进任意已完成任务的详情页，点击"导出任务归档"，确认下载到 `task-*-export-*.json`；
  2. 再点"导出轨迹"，确认下载到 `task-*-trace-*.json`；
  3. 用记事本打开文件，确认里面有子任务、评审、轨迹等内容，且文件首行带有 `schema` 版本标识。

### 模块 5：一键启动脚本 + 容器化部署配置

- **做了什么**：
  - **一键启动脚本** `scripts/demo_up.py`：一条命令体检并拉起缺失的演示服务。默认走 **Mock（离线）模式**；加 `--real` 参数则对接项目一真实知识库；还有 `--status`（只体检）、`--down`（仅停止本脚本拉起的服务）等。脚本只启动"缺失"的服务，不会乱杀别人的进程。
  - **容器化部署** `docker-compose.yml`：把 MySQL、Redis Stack、后端打包成容器，另含两个可选服务（前端、项目一），用 `--profile` 按需开启。
- **运行后能看到什么现象**：
  - 跑一键脚本后，后端、知识库、前端等服务按端口起来，打开网页即可演示；
  - 用 Docker 命令也能把整套环境拉起来，适合正式部署。
- **怎么确认功能生效**：
  1. 执行一键启动脚本，确认终端提示各服务"已就绪 / 已拉起"，且后端健康检查（`/healthz`）返回正常；
  2. 打开前端页面能登录、能建任务；
  3. Docker 方式：执行 `docker compose up -d --build`，确认三个必需服务（mysql / redis / backend）状态为 healthy。

## 第四部分：系统整体架构文字说明（纯文字讲流程）

下面用大白话把"一次任务是怎么跑完的"讲清楚，不需要看任何架构图。

**多智能体阵容：到底有几个"AI 员工"，各自干啥？**

本项目不是"一个 AI 包打天下"，而是由好几个**各司其职的智能体（AI 员工）**搭伙干活——这正是"多智能体"三个字的含义。它们通过流程图（LangGraph）一个接一个传活儿：

| 智能体 | 外号 | 负责的事 |
|---|---|---|
| 规划 Planner | 规划师 | 把你的目标拆成一串有先后的小步骤（子任务） |
| 执行 Executor | 执行员 | 对每个小步骤，挑对的工具去查 / 去算，拿到结果（失败会重试、降级） |
| 评审 Reviewer | 评审员 | 给每一步打分、算可信度，判断靠不靠谱（原有判定逻辑未改） |
| 总结 Summarizer | 总结员 | 把所有步骤的结果汇总成最终答案 / 报告 |
| 通知 Notifier | 通知员 | 负责"推送通知"这类动作（属高风险，会触发人工闸门） |
| 人工闸门 Human Gate | 安全闸 | 发现高风险 / 低分步骤，把任务挂起交人批注（本次新增节点） |
| 重规划 Replan | 重规划师 | 拿到人的批注后，重新拆解子任务（复用规划师） |

这几个智能体按顺序接力：**规划师画好步骤 → 执行员逐步干活 → 评审员逐条把关 → 总结员收尾**；中途一旦被安全闸拦下，就等人批注后由重规划师重新画步骤。

**正常流转链路（一步一步读）：**

1. **用户发起任务**：你在网页上填一句话目标（比如"帮我查一下上次服务器宕机的处理办法"），点提交。
2. **规划智能体（Planner）拆解**：系统里的"规划师"把这句大目标，自动拆成几个小步骤（子任务），比如"先去知识库搜宕机案例""再总结处理步骤"。
3. **自动调用已启用的工具**：每个小步骤如果需要查资料，就调用你**已经启用**的工具——最常见的是"知识库检索（kb-search）"，也可能调用 SQL 查询等。没启用的工具不会被调用（这就是模块 1 的价值）。
4. **结果进入评审节点（Reviewer）**：每一步做完，评审节点会**自动打分并计算可信度**，判断这一步靠不靠谱。
5. **低分自动触发人工批注中断**：如果某一步分数偏低、或属于高风险操作，任务会**自动挂起**，变成"等待审批"状态，交给你来处理（见模块 3）。
6. **填写批注后重规划**：你在收件箱写一句批注（例如"这个方向不对，换个思路"）并驳回，系统会把这句话当作硬性要求，让规划师**重新规划**，新的子任务会跟着你的批注变。
7. **全程保存断点、分层记忆、完整轨迹**：任务从开始到结束，每一步的**断点**（防中断重跑）、**分层记忆**（短期 / 中期 / 长期，让 AI 越来越懂业务）、**完整执行轨迹**都会被记录下来。
8. **支持一键导出归档**：任务完成后，你可以一键导出"任务归档文件"和"执行轨迹文件"，留档、复盘、给别人看都很方便（见模块 4）。

**关于项目一知识库（外部资料来源）：**

项目一的企业垂直知识库，是作为**外部资料源**接入本平台的——本平台通过接口向它"提问"，它把相关企业内部资料返回来，AI 据此作答。它是一套独立系统，本平台不修改它的代码。

**关于 Mock 模式（离线演示）：**

为了方便**不依赖外部服务**也能演示，系统提供 Mock（模拟）模式：开启后，知识库检索不再真正连项目一，而是用平台内置的模拟资料来跑。这样**纯本地就能把整套流程演示一遍**，非常适合答辩、离线展示；等需要真实业务检索时，再切到真实联调模式即可。

## 第五部分：环境与端口清单（初学者照着就能搭）

### 1. 全部服务端口

| 服务 | 端口 | 作用 |
|---|---|---|
| AgentFlow 后端（API + 编排） | **8000** | 系统的"大脑"，接收请求、跑任务、推结果 |
| 项目一「企业垂直知识库」 | **8010** | kb-search 的真实资料来源（真实联调模式才需要） |
| 前端网页 | **5173** | 你用浏览器打开的操作界面 |
| MySQL 数据库 | **3307** | 存任务、子任务、审批、轨迹、记忆等正式数据 |
| Redis Stack（缓存 / 限流 / 断点） | **6379** | 存断点、限流计数、短期记忆、工具注册表 |

> 小提示：MySQL 用 3307 而不是常见的 3306，是为了避开你电脑上可能已有的系统 MySQL 服务，避免端口打架。

### 2. 演示账号

- **用户名**：`admin_user`
- **密码**：`Passw0rd!`

用这个账号登录前端网页（5173）即可拥有管理员权限，能看到工具注册、审批收件箱等全部功能。

### 3. 两种运行模式

- **Mock 离线模式（默认）**：不调用真实项目一知识库，用平台内置模拟资料演示。**适合答辩、离线展示**，不需要项目一服务在线。
- **Real 联调模式**：真正对接项目一的「企业垂直知识库」，完成从检索到结论的**全链路业务检索**。**适合完整联调、真实业务验证**，需要项目一服务（8010）在线。

### 4. 启动方式

**方式 A：一键脚本（最简单，推荐本地演示）**

```bash
# 体检 + 拉起缺失服务（默认 Mock 离线模式）
python scripts/demo_up.py

# 走项目一真实检索（Real 联调模式）
python scripts/demo_up.py --real

# 只做环境体检，不启动任何进程
python scripts/demo_up.py --status

# 仅停止本脚本拉起的服务
python scripts/demo_up.py --down
```

**方式 B：Docker Compose（适合正式部署）**

```bash
# 1) 先准备环境文件
cp .env.example .env

# 2) 拉起三个必需服务（mysql / redis / backend）
docker compose up -d --build

# 3)（可选）额外起前端
docker compose --profile frontend up -d

# 4)（可选）额外起项目一（真实检索）
docker compose --profile project1 up -d

# 5) 停止（保留数据）
docker compose down
```

> 注意：Docker 方式在本机若遇到权限限制，请按本机 Docker 的提示处理；Compose 文件在本项目仅做语法校验，实际启动仍需手动执行上面的命令。
