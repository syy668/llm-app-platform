# 项目一 v1.13：评测模块运营闭环（补答案 / 删脏样本 / 建集导入 / A/B 参数透传）

> 触发问题：「这个项目是没有上传数据集的地方吗，这个设计合理吗」（RAGAS 评测 → 新建评测任务 → 选择数据集下拉）
>
> 结论：**后端 4 个接口齐全、前端 api 层也封装好了，但没有任何一个组件引用它们** —— 属于"接口先行、UI 缺失"的半成品，不是概念没设计。

## 1. 根因排查（证据）

### 1.1 能力在，入口不在

### 1.2 一句承诺落空（最硬的证据）

`views/Chat.vue` 点踩「加入评测集」成功后的 toast：

> 已加入「用户反馈Badcase」，**可在评测页补充参考答案**

但评测页没有这个功能，后端也没有编辑样本的接口（只有追加 / 查 / 删集）。于是：

`services/eval_service.py::add_badcase_from_message` 刻意把 `reference_answer` 写成空串（**理由正确**：填 AI 的错误答案会让 RAGAS 把幻觉当标准答案反过来打分），而 `ItemInput.reference_answer` 是 `min_length=1` 必填 —— **连重新 POST 一次都补不进去**。

结果：这批 badcase 样本的 `context_recall` 永远算不出来。v1.9 建的数据飞轮，进得来，出不去。

## 2. 设计判断：合理的那一半 + 不合理的两处

**合理的取舍**：评测集是黄金集，`reference_answer` 决定 RAGAS 分数可信度。让业务在页面上随手编 30 条标准答案，评测分数会虚高，反过来把幻觉"测合格"——比没有评测更糟。早期用脚本灌、可 review，方向没错。

**不合理的两处**：

1. **只读到底，闭环断了。** 基准只能由开发者用脚本灌 → 业务侧发现新坏例子没有任何自助通道 → 数据飞轮输入端形同虚设。分界线应该是「**读取与修正开放，从零编造黄金集受限**」，而不是一刀切全关。
2. **空状态是死路。** 干净环境部署时页面只剩「暂无可评测的数据集」警告，用户无法自救，整个 RAGAS 模块不可用。这是"功能不可用"级，不是体验瑕疵。

## 3. 本次改动（P0）

### 3.1 后端

| 文件 | 改动 |
|---|---|
| `app/schemas/eval.py` | 新增 `ItemUpdate`（PATCH 语义，三字段全 Optional）；`DatasetOut` 加 `missing_reference: int \| None` |
| `app/services/eval_service.py` | 新增 `update_item` / `delete_item` / `_audit` / `_get_item`；`list_datasets` 增参考答案覆盖率聚合 |
| `app/api/v1/eval.py` | 新增 `PUT /eval/datasets/{id}/items/{item_id}`、`DELETE /eval/datasets/{id}/items/{item_id}`（均 `require_admin`） |

关键设计点：

- **`reference_answer` 出现时必须非空**，空串被 pydantic 拦（422），显式 `null` 由服务层拒绝并给可读 400（`参考答案不能置空：留空会导致该样本的 context_recall 无法计算`）。两种入口两种反馈，避免用户只看到泛化 422。
- **PATCH 而非整条 PUT**：只提交改动字段。若前端补答案时把 `stratum`/`reference_contexts` 一起回传空值，覆盖式更新会清掉已有分层标签 —— 而历史样本 stratum 本来就是 NULL，这个坑很隐蔽。
- **归属校验**：`_get_item` 校验 `item.dataset_id == dataset_id`，不允许借 A 数据集的 URL 改 B 数据集的样本。
- **`delete_item` 重算 item_count 而非 `-= 1`**：历史上「badcase 增量 / 批量导入 / 删集」三条路径都动过这个计数，以 `COUNT(*)` 为准可顺带修掉漂移。
- **审计 best-effort**：改参考答案写 `operation_logs`（`action=update_eval_item`，含新旧值前 500 字）。黄金集被谁改过必须可查；但审计失败只告警 + rollback，绝不回滚已提交的业务变更。
- **`missing_reference` 用一次聚合**（`GROUP BY dataset_id`，口径：空串 / 纯空白 / NULL）而不是前端按集逐个拉样本 —— 避免 N+1。

### 9.2 交互设计

**勾选规则（三道闸，前两道在 UI、最后一道在按钮）**

1. `status !== 'done'` 的行不可勾 —— 没有得分，对比必然空。
2. 已勾满 2 个时其余行不可勾；已勾消的行永远可点（否则取消不掉）。
3. 第 2 个之后的 run 必须与第 1 个同 `dataset_id` —— 跨集后端会 400，提前挡掉比让用户看报错好。

换页/刷新会清空勾选（`loadRuns` 里 `selectedRuns = []`），避免「选中的 run 已不在当前页却仍能点对比」。

**报告弹窗四段结构**

1. **顶部信息对比**：A/B 两栏对称 —— `run #id · model`、`数据集 #id · 成功/总样本 · 时间`、实验参数（`top_k=5 · 混合` / `默认（KB 配置）`）。参数放这里是关键：A/B 的前提是知道两次跑的差异在哪。
2. **一句话结论**：`B 相对 A：3 项提升 / 1 项下降 / 0 项持平；变化最大的是 Context Recall +0.1200；逐样本有 12 条超过 Δ 阈值 0.1`。**先给结论再给表**，否则对方要自己算。
3. **四项指标表**：指标名 + 一句人话解释（如 Recall = 该召回的是否都召回了）/ A / B / Δ。`Δ = B − A`，绿 ↑ 表示提升、红 ↓ 表示下降、灰 `=` 表示持平或任一侧缺值。
4. **逐样本明细**：`问题 | 四项各一列（A → B + Δ）`，`is_diff` 的行打「差异」chip；顶部开关「只看差异样本」直接过滤到后端标记的那批。只在单侧出现的样本，问题文字置灰并说明（另一侧无得分）。

**配色说明（刻意与股市相反）**：本页 `绿=提升、红=下降`，与项目里状态标签（done 绿 / failed 红）同一套语义色。这不是行情图，别按「红涨绿跌」读。
