# 项目一 v1.17：RAGAS「静默空分」修复

> 现象：评测任务进度正常走、状态正常流转，但**每一条样本的四项指标都是 NULL**。
> 首页汇总列全是「—」，明细表全是「-」，而界面没有任何一处说这是故障。

## 一、真实现象（不是推测）

真实库 run 63 / 64 / 65 三连：

| run | 状态 | 进度 | 得分行 | 四项指标非空的行 |
|---|---|---|---|---|
| 63 | failed | 28/30 | 28 | 15（早期判分还可用） |
| 64 | failed | 28/30 | 28 | **0** |
| 65 | running → done | 28/30 | 28 | **0** |

同时用户侧看到的两个"症状"：

1. **进度 11/30，展开却显示「该运行暂无得分记录」** —— 明明有得分行在写入；
2. **得分明细列全是「-」** —— 有行、无值。

第 2 个是根因，第 1 个是前端缓存 bug 造成的独立误导。

## 二、根因链（四层，每层都"合法"）

```
判分模型 qwen3.7-flash-2026-07-15（带日期后缀）→ 上游仅允许免费额度访问
        ↓  额度耗尽
每次判分调用 403 AllocationQuota.FreeTierOnly（实测：换成 qwen3.7-flash 短名即 200）
        ↓  ragas 内部把指标异常吞成 NaN（raise_exceptions=False）
evaluate_one 把 NaN 翻成 None → 返回 {faithfulness: None, ...}
        ↓  handle() 只看 kind=="ok" 就 success += 1
"一条指标都没算出来" 被记成"评测成功"，run 最终 done、metrics 全空
```

关键在于**每一层单独看都合理**：ragas 吞异常是为了"单个指标失败不影响其他指标"；
`evaluate_one` 把 NaN 转 None 是为了 JSON 友好；`handle` 按 kind 计数是为了并发统一。
但叠起来就变成"故障伪装成成功"。

同一时间问答链路是好的（`qwen3.7-plus` 有额度），所以现象特别迷惑：
**聊天正常、只有评测出空值**。

## 三、修复

### 1. 配置：判分模型换短名（直接止血）

`eval_llm_model`: `qwen3.7-flash-2026-07-15` → `qwen3.7-flash`

实测可用性（同一 key，同一 base）：

| 模型名 | 结果 |
|---|---|
| `qwen3.7-flash-2026-07-15` | ❌ 403 `AllocationQuota.FreeTierOnly` |
| `qwen3.7-flash` | ✅ |
| `qwen3.7-plus` / `qwen-plus` / `qwen-max` / `qwen-flash` | ✅ |

判分(flash) 与生成(plus) 仍是不同规格，v1.7 的「避免自评偏差」解耦没有被破坏。

### 2. `app/eval/metrics.py`：指标全空必须抛，不能返回全 None

新增 `RagasScoringUnavailable`（`retryable=False`）：

- `preflight()`：用一次最小请求探活判分模型，失败抛带可读原因的异常；
- `evaluate_one()`：四项**全部**为 None → 先 `preflight(force=True)` 拿到真实原因，
  再抛 `RagasScoringUnavailable`；
- 只有一两项为空（如 contexts 为空只打穿 faithfulness）→ 保留原语义，仅 WARNING。

为什么区分"全空"与"部分空"：部分空是样本内容特征，全空只可能是判分链路故障。

### 3. `app/services/eval_service.py`：三层保护

| 保护 | 行为 | 拦住什么 |
|---|---|---|
| **开跑前探活** | `EVAL_PREFLIGHT_ENABLE`（默认 true）→ `preflight()` 失败即 `run=failed` + 可读原因，**一条样本都不跑** | 30 个样本 × (检索+生成+4 次判分) 的整段白烧 |
| **不可重试异常** | `except RagasScoringUnavailable` 直接记 failed，不重试 | 把同一条 403 再打 `EVAL_RETRY_ATTEMPTS` 遍 |
| **连续失败熔断** | 连续 3 条失败**且零成功** → 抛 `_EvalAborted`，status=failed | 探活之后才挂掉的情况（额度中途耗尽的典型形态） |

熔断的两个条件是 AND，刻意如此：一旦有过成功样本就证明链路是通的，此时偶发失败
不该中止（跑完仍对用户有价值）；反过来，连续三发全败且零成功，几乎不可能是抖动。

`metrics` 落库口径同步收紧：零成功时写 `None` 而不是 `{"faithfulness": None, ...}`
—— 后者是"有数据但全空"的假象，会让后续回填与大盘误判为已有指标
（与 v1.13.1 异常收尾路径的口径对齐）。

### 4. `frontend_vue/src/views/RagasEval.vue`：两处误导

**(a) 空数组缓存锁死明细**

```diff
- if (!isOpen || scoresMap[row.id]) return      // [] 是 truthy → 一次空拉取永久锁死
+ if (!isOpen) return
+ if (!isActiveRun(row) && scoresMap[row.id] !== undefined) return   // 只有终态才吃缓存
+ await loadRunScores(row.id)
```

配合轮询：`refreshRunsSilently` 现在会同时刷新**已展开且非终态**任务的明细。
此前只刷列表，用户盯着进度条从 11/30 涨到 30/30，展开区却一直是展开那一刻的快照。

顺带修了 `catch` 里无条件写 `scoresMap[id] = []`：一次网络抖动会把已经展示出来的
28 条明细清空，而且因为上面的缓存判断，之后永不重拉。

**(b) 指标全空必须点名**

明细表上方新增红色 alert（`metricsAllEmpty`）："这些样本跑完了，但四项指标全部为空
—— 判分模型没有产出结果"，并指向「系统配置」。以前这里只是一排「-」，
看起来像"分数还没算出来"。

运行中任务的空态文案也从「该运行暂无得分记录」改成「样本得分尚未落库（每 5 秒自动刷新）」。

### 5. `app/core/llm_errors.py`：403 单独分类

新增 `_HINT_QUOTA_DENIED`，并在关键词兜底里把 `403` 放在 `quota/insufficient` **之前**：
额度类错误文本同时含这两个词，但 403（未开通/免费额度用尽）与 402（余额不足）
对用户是不同动作。

## 四、实测

单样本真实链路（run 65 的 item 219，用真实 answer + 5 条召回上下文）：

```
[preflight] OK 0.9s
[evaluate_one] OK 35.5s ->
  {'faithfulness': 0.928571, 'answer_relevancy': 0.912914,
   'context_precision': 1.0, 'context_recall': 1.0}
```

修复前同一条样本：四项全 `None`。

**端到端**（新建 3 条样本的数据集，真实链路跑完，run 66）：

```
status=done  success=3/3  failed=0
metrics={"faithfulness": 0.984127, "context_recall": 1.0,
         "answer_relevancy": 0.838095, "context_precision": 0.777778}

item 253 VPN密码忘了怎么弄？        f=1.0      ar=0.910932 cp=1.0      cr=1.0
item 254 公司WiFi怎么连，访客网络用哪个？ f=0.952381 ar=0.815249 cp=0.5      cr=1.0
item 255 打印机卡纸了怎么处理？      f=1.0      ar=0.788104 cp=0.833333 cr=1.0
```

3 条得分行 0 条 NULL。修复前同链路是 30 条全 NULL。

> 实测踩到的坑（值得记）：验证脚本里 `db.expire_all()` 之后仍读到 `status=pending`，
> 因为 MySQL 默认 REPEATABLE READ —— `expire_all` 只让对象过期，**事务快照不变**。
> 这正是 `_is_cancel_requested` 必须用独立短会话的原因（见该函数注释）。
> 判断落库结果必须开新连接查。

**存量脏数据修正**（只改状态，不改得分）：

| run | 修前 | 修后 | 说明 |
|---|---|---|---|
| 65 | `done` + 30 条全 NULL | `failed` + `metrics=NULL` + 写明原因 | `done` 是误记：30 条样本一条指标都没算出来 |
| 64 | `failed` + 28 条全 NULL | 不变（仅前端新增红 alert） | failed 已表达"不完整"，得分保留作故障证据 |
| 63 | `failed` + 28 条（15 条有效） | 不变 | 有效分数仍可用于对比 |


## 五、测试

新增 `tests/test_eval_scoring_guardrails.py`，**13 例**：

| 分组 | 覆盖 |
|---|---|
| 403 文案（3） | 403+quota → 额度文案且含动作；无 status_code 的 403 不被误判成 402；402 回归不受影响 |
| 异常语义（3） | `retryable=False`；配置性故障只调用 1 次；普通异常仍重试 3 次 |

| 熔断（3） | 连续 3 败零成功 → 只跑 3 条即中止 + metrics=None；有过成功后不再熔断（跑满 5 条，done）；端到端判分恒失败 → 0 条得分行 |

`tests/conftest.py` 新增 autouse fixture：单测默认关闭探活（不得向真实上游发请求）。

全量：**524 passed / 0 failed**（真实 MySQL 3306 + 真实 Redis db1）。前端 `vue-tsc` 0 error。

## 六、存量数据说明

run 63 / 64 / 65 的得分行**保留原样**，没有删除也没有补值：

- 全 NULL 的得分行是"确实跑过、确实没算出分"的事实记录，删掉等于抹掉这次故障的证据；
- 前端现在会在这三条的明细上方显示红色 alert，不会继续误导；
- 有效分数（run 63 的 15 条）继续可用于对比。

run 65 的 `status` 从 `done` 改为 `failed`：它确实是 30/30 跑完的，但一条指标都没产出，
记成 `done` 会让大盘把它算作"已完成任务"。这是纠正错误状态，不是修改数据。

run 66 是本次修复的验证任务（数据集「v1.17 判分修复验证（3 条）」），
用于留证；不需要时在评测页删除即可（会级联删除 3 条得分）。

## 七、还没做的边界

1. **判分模型可用性没有持久化状态**。探活只在 run 启动时发生，配置页不会提示
   "当前判分模型不可用"。理想形态：配置保存时探一次并回显。
2. **额度耗尽的成本已经花掉了**。探活能防止"后续"白跑，但对已在跑的任务无效
   （熔断最多再浪费 3 个样本）。
3. **`answer_relevancy` 依赖 embedding**。当前 embedding 走硅基流动，与判分模型不是
   同一家额度体系；embedding 挂掉时这一项会单独变 None（部分空，不触发熔断）。
   这是刻意的降级，但意味着"四项里有 3 项可用"仍会被记成功 —— 目前只写 WARNING 日志，
   未做前端提示。
